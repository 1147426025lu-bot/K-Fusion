# 同窗口 空闲 vs CPU 负载 读写抖动对照（2026-11-17）

## 一句话结论

**同样的 60 s 窗口、同样 3 轮、同样的任务与二进制，把 CPU 打满（非测量核）后：
硬中断读写的读抖动中位数几乎不动（4.1 → 4.0 µs），而用户态线程读写的读抖动中位数抬升
（80.0 → 110.4 µs）、且两者极差都很大。** 即硬中断侧的读时刻对 CPU 负载不敏感，
线程侧对负载敏感——但 3 轮样本不足以做显著性断言（见口径纪律）。

## 实验设计（单变量）

- **唯一变量**：有无 CPU 负载（`MODE=idle` vs `MODE=load`）。
- 两组均为：同一份任务（`let_pc_shared`）、同一块板、同一实时核（CPU3）、同一周期（1 ms）、
  同一优先级、同一构建脚本、同一统计口径；各 3 轮 × 60 s。
- 负载方式：`stress-ng --cpu $((nproc-1))`（4 核板 → 3 个核打满，测量核 CPU3 留空），
  时长覆盖每轮测量窗口；命令记录在脚本 `run_let_jitter_exp__读写抖动实验.sh` 的 `start_load()`。
- 数据源（Pi `~/kfusion_results/`）：
  - 空闲：`let_jitter_idle_60s_3x60s/`（本轮新跑，为同窗口配对）
  - 负载：`let_jitter_load_cpu_3x60s/`（本轮新跑）
  - 原始逐拍日志（`<arm>/repN/*.kf_let_log.bin` + `*.samples.csv`）与 `*.meta.json` 均在各自目录。

## 口径纪律（哪些话能说，哪些不能）

1. **只比同窗口**：本表两组都是 60 s×3。**不要**拿这里的 thread 80–110 µs 与
   `let_jitter_idle_3x15m` 的 138–195 µs 比大小——窗口不同，尾部随时长右移，
   这恰好从侧面再次印证"极值不可跨窗口比"。
2. **报中位数 + 极差 + 每轮散点，不报均值**：均值会被个别异常拍拉偏（项目里已有此教训）。
3. **3 轮不足以做显著性断言**：load 相对 idle 的 thread 读抖动 3/3 轮同向抬升，
   符号检验 `p = 0.125`（单侧），未达 0.05——只能说"该条件下稳定偏高"，不能说"显著变大"。
4. **max 只是尾部四种风险之一**：本表是 p100（max），不含 p99 中位 / max 中位 / 超期率，
   不可由本表单独下"整体抖动如何"的结论。写抖动尤其明显：load/irq 的 max 从 5.34 到 10.39，
   是尾部个别拍，不代表写路径整体退化。
5. **硬中断臂读抖动极稳这一条相对扎实**：idle 三轮极差 0.0 µs、load 0.2 µs，
   两组中位都在 4.0–4.1 µs；在同窗口、同口径下，读时刻几乎不随 CPU 负载变化。
6. **中断影响维度（victim cyclictest 对照、hrtimer 回调全程耗时）仍未做**，
   本实验只回答"读写侧抖动对负载的敏感性"，不回答"中断对其他任务的影响"。
