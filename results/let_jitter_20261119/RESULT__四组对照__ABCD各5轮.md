## 1. 四组到底差在哪

> 以下"计算体完全相同"的描述与源码复核结论不符，保留原文仅作历史记录，见文首取代声明。

四组的**周期、相位、计算体、写桩/读桩语义、日志格式（36 字节/样本）完全相同**，唯一变量是
读写桩的执行上下文：

| 组 | 读写桩执行位置 | 实现 | 日志标识 |
|---|---|---|---|
| **A** | 用户态 SCHED_FIFO 线程，`clock_nanosleep` 绝对时刻唤醒 | `kfusion/src/kf_let_userspace__用户态LET读写.c` | `arm_path=3`，`ctx=task` |
| **B** | 内核 kthread（`kf_worker_fn`） | Pass 生成模块，`path=thread` | `arm_path=0`，`ctx=task` |
| **C** | 手写 hrtimer 硬中断回调 | `kfusion/src/kf_hand_let__手写硬中断读写.c` | `arm_path=2`，`ctx=hardirq` |
| **D** | 编译器生成 hrtimer 硬中断回调 | Pass 生成模块，`path=irq` | `arm_path=1`，`ctx=hardirq` |

统一口径：`抖动 = |t_after_ns − nominal_ns|`，读、写**分开统计**，只统计 `status=ok`。

## 2. 必须先说的一件事：预热截断

A 组首次 60 s 实测暴露了一个如果不处理就会导致"短测长测互相矛盾"的现象：

| 开跑后时间 | 读 p50 |
|---|---:|
| 0 – 4.5 s | **8.72 µs**（极窄，p90 = 8.79） |
| 4.5 s 之后 | **22.4 µs**（极窄，p90 = 22.5） |

5 s 短测因 90% 样本落在瞬态里，报 8.7 µs；60 s 长测报 22 µs。**两者都是"真的"，差的是观测窗口。**

处理方式：所有臂统一丢弃开跑后前 **10 s**（`--warmup-sec 10`），原始 raw.bin 全部保留可复核。
下表所有数字均为**截断后**统计（A/C 硬中断段为事后重算，样本数 12 万 → 10 万）。

> 预热期的物理成因本轮**未归因**（可能是 tick/调速/缓存状态未定）。这里只把它当作必须排除的启动瞬态，
> 不声称知道它为什么存在。

## 4. 五个可下结论的发现

### 4.1 读写钉到硬中断把抖动压到个位数微秒，D 组还额外把尾部压平

读 p50 排序：**D 3.32 ≈ C 3.46 ≪ A 22.24 < B 46.50**。

A 对 B：**5/5 轮同向**，单侧符号检验 `p = 0.031`（n=5，未做多重比较校正）——即"用户态 FIFO 线程
比内核 kthread 更准时"在本条件下成立。原因可解释：B 组每周期多一层"硬中断唤醒 kthread"的握手，
A 组没有这层。

### 4.2 A 组的 22 µs 几乎全部是"唤醒并返回用户态"，不是读写本身

这是本轮**最干净的一组机制证据**。同一份 A 组程序，只把"等待"从 `clock_nanosleep` 换成
忙等（`--mode spin`，隔离核上 100% CPU），其他一切不变：

| A 组等待方式 | 读 p50 | 读 p99 | 读 max |
|---|---:|---:|---:|
| `clock_nanosleep`（主口径） | 22.24 µs | 23.13 µs | 31.64 µs |
| 忙等 `spin`（诊断） | **0.153 µs** | **0.184 µs** | **0.185 µs** |

60 s、5 万样本、max 仅 185 ns。也就是说：读写桩 + 测量开销合计只有 **0.15 µs**，A 组那 22 µs
的 99.3% 是「定时器到期 → 调度器选中 → 返回用户态 → 开始执行」的路径开销。

> 对命题的意义：讨论"用户态读写慢"时，慢的不是 `memcpy`/赋值，而是**每次唤醒**。
> 把读写搬进硬中断回调，等于把这段唤醒路径整个删掉。

spin 模式的两个约束（诚实标注）：① CPU 100% 占用，负载形态与主口径不同，**只作机制分解，不替主口径**；
② 不关 `sched_rt_runtime_us` 会撞 RT throttling（实测 p90 达 309 ms），本轮把它临时设为 `-1` 再跑，跑完恢复。

### 4.3 C 组内部单变量对照：软中断回调会被推迟到毫秒级

同一份手写模块，唯一差异是 hrtimer 回调跑在硬中断还是软中断（`hrtimer_hard=1/0`）：

| C 组回调上下文 | 读 p50 | 读 p99 | 读 max | 写 skip 次数 |
|---|---:|---:|---:|---:|
| 硬中断 | 3.46 | 4.11 | 20.85 | 0 / 0 / 0 / 0 / 0 |
| 软中断 | 21.02 | 22.15 | **2405.84** [1355–9998] | 13 / 5 / 2 / 4 / 3 |

- p50 差 **6×**，但真正的差别在尾部：软中断臂 max 达 **9.998 ms ≈ 10 个周期**。
- 软中断臂还出现了**跳拍**（`skip` 5 轮全非零）——计算 worker 的唤醒被推迟，写桩拿不到新值只能跳过发布。
  硬中断臂 5 轮 skip 恒为 0。
- 结论：**"读写必须在硬中断上下文"不是风格偏好，是尾部风险和跳拍风险的直接来源。**

> 注意：C 组软中断臂的 `max` 由个别毫秒级推迟决定，与微秒级尾部**不是同一种风险**，
> 不能和硬中断臂的 max 做比值当"改善倍数"。

### 4.4 C 与 D 的差别不在中位，在尾部

读 p50：C 3.46 vs D 3.32（C 高 4%，5 轮中 4/5 同向，`p = 0.1875`，**未达 0.05，不下断言**）。
但读 max：C 20.85 vs D 3.72（**5.6×**），且 C 的 max 极差极大（15.81–39.31），D 只有 3.57–4.71。

实现差异（本轮仍未分离）：C 组 4 个相位全走 HARD timer 编程，D 组只有 400/500 µs 两个读写相位走硬中断。
C 组每秒的 timer 编程次数约为 D 组的 2×，尾部差异更可能来自这里，而不是"手写 vs 生成"本身。

### 4.5 新增探针：硬中断里最慢的一步不是读写桩

本轮给 C 组加了回调全程耗时探针（入口→出口，含 `kf_arm_next` 重装定时器）：

| 量 | 5 轮范围 |
|---|---|
| 单次读写桩 `let_op_dur_max_ns` | 0.389 – 2.445 µs |
| 写槽回调全程 `let_cb_wr_dur_max_ns` | 4.04 – 7.37 µs |
| 读槽回调全程 `let_cb_rd_dur_max_ns` | 2.69 – 4.02 µs |
| **全周期回调全程** `let_cb_dur_max_ns` | **14.61 – 24.70 µs** |
| 超 10 µs 的回调次数 | 5 – 95 次/轮（每轮 6 万周期） |

读写槽回调最多 7.4 µs，但全周期峰值到 24.7 µs —— 峰值必然落在 **group0（唤醒计算 worker）** 槽，
因为 slot3 只做计数和重装定时器。也就是说 `wake_up_interruptible` 在 C 组是硬中断里最贵的一步。

> 这条同时解释了 4.4 的尾部差异为什么"手写 4 相位全 HARD"更吃亏：唤醒/编程次数都翻倍。

## 5. 本轮不能主张什么

1. **不主张"A 组代表开题的用户态方案最优解"**——A 组只是"用户态 + 用户态读写"这个基线的实测，
   它 22 µs 里 99% 是唤醒开销（4.2），换个定时机制就会变，不能当作"用户态固有成本"的普遍结论。
2. **不主张"C 比 D 差"**——只有尾部差，中位差 4% 且 4/5 同向未达显著（4.4）。
3. **不主张软中断臂的 max 与硬中断臂 max 可直接比倍数**（量纲不同的风险，4.3 注）。
4. **不主张 GPIO 外部计时已验证**——本轮全部是软件时间戳，GPIO + 逻辑分析仪仍未取证。
5. 所有 p 值均为**单侧符号检验且未做多重比较校正**；5 轮全同向才勉强到 0.031，只能说"在该条件下稳定成立"。

## 6. 复现

```bash
# 平台：Pi4B / 5.15.49-rt47 PREEMPT_RT，隔离核 CPU3
# 一次跑齐四组（A → C 硬 → C 软 → B/D），各 5 轮 60s，最后自动出图
cd /home/pi/K-Fusion
bash kfusion/scripts/build_hand_module__编译手写中断模块.sh
REPS=5 DURATION_SEC=60 WITH_SOFT=1 \
  RUN=/home/pi/kfusion_results/let4_$(date +%Y%m%d_%H%M%S) \
  REUSE_KO_DIR=/home/pi/kfusion_results/let_jitter_idle_3x15m \
  bash kfusion/scripts/run_let_four_arms__四组对照5轮.sh

# 机制分解（4.2）：同一份 A 组程序改忙等
gcc -O2 -o /tmp/kf_let_userspace "kfusion/src/kf_let_userspace__用户态LET读写.c"
sudo sh -c 'echo -1 > /proc/sys/kernel/sched_rt_runtime_us'   # 否则撞 RT throttling
sudo /tmp/kf_let_userspace --cycles 60000 --mode spin --cpu 3 --prio 80 --out spin.bin
sudo sh -c 'echo 950000 > /proc/sys/kernel/sched_rt_runtime_us'
python3 kfusion/scripts/let_log_dump__导出读写日志.py --bin spin.bin -o . --tag spin_r1 --warmup-sec 10
```

参数默认值：`WARMUP_SEC=10`（预热截断）、`PERIOD_US=1000`、`PHASE_WR_/RD_US=400/500`、`CPU=3`、`PRIO=80`。
