# K-Fusion 统一架构方案：一条编译流水线 + 一套部署规划 + 分层隔离执行

我建议对 K-Fusion 做一次架构收敛，而不是继续维护“旧 LLVM 内核化 Pass”和“新 AST/TEIR/STKP 宿主生成”两套相互独立的流程。

重新检查仓库后，我认为最需要解决的不是增加新的优化算法，而是三个工程与研究问题：

1. 编译决策没有完整落实到最终机器代码。 新流水线已经能够分析阶段、产生 `plan.json`、生成宿主，但内核分支还存在直接复制原始 `stage_impl.c` 的情况，不能证明最终链接的计算体一定经过原有 LLVM 内核化 Pass。
2. 内核执行方式与任务分组过度耦合。 当前专用内核宿主采用每组一个 hrtimer、一个内核线程的结构。对于一个逻辑 PLC 任务，这会引入额外线程、唤醒关系和跨组时序验证负担。
3. 隔离尚未成为编译与部署的一部分。 编译器可以决定执行域，但还需要统一管理 CPU 归属、中断亲和性、内存、状态边界以及运行时故障处理，否则部署方案的实测结果很容易随系统环境变化。

## 一、我的核心建议

保留现有 AST、LLVM Pass、TEIR、STKP 和 Linux 宿主的研究成果，但将它们重组成一条固定顺序的编译流水线。

输入：一份 PLC 周期 C 程序

函数、状态变量、周期、期限、允许的执行域

① Clang AST + LLVM IR 分析

找函数、识别读写、检查调用与状态

② 统一任务表示与合法性检查

阶段、依赖、周期、跨拍状态、禁止操作

③ 联合部署规划

阶段融合 + 用户/内核划分 + 释放时间 + CPU 隔离

④ 依据同一个已验证计划生成代码

用户代码保留用户态；内核计算经过 PLCFusionPass

用户态执行文件

原始计算 + 生成的周期驱动

内核模块

kernel.o + 生成宿主 + 严格运行时接口

⑤ 隔离部署、板上验证和测量反馈

CPU / IRQ / 内存 / 状态 / 故障 / 证据身份

这里的统一，不是强迫用户态程序和内核模块使用完全相同的线程实现，而是要求：

一个输入程序、一个语义模型、一个被验证的部署计划、一套代码生成接口，以及一套可以验证最终执行结果的标准。

这样你就能对导师明确说明：LLVM Pass 负责把被选中的计算函数转换成内核可链接代码，部署规划器决定哪些函数需要转换，宿主生成器根据同一计划决定它们何时运行。三个部分真正构成了同一个编译器。

## 二、统一后的完整编译流程：每一步究竟做什么

我建议新的流水线严格按照下面的顺序执行。不能先把整个用户程序内核化，再让 STKP 决定哪部分应该放在内核里。 否则前面的转换不知道真正需要保留什么，后面的规划又不能保证实际目标文件与计划一致。

### 第 1 步：输入原始 PLC C 程序

以仓库里的 `mixed_pid_stateful__积分混合.c` 为例，原程序包含：

```
int32_t g_in;
int32_t g_integ;
int32_t g_out;

void stage_sample(void)
{
    /* 采样更新 g_in */
}

void stage_pid(void)
{
    int32_t err = 0 - g_in;

    g_integ += err;

    if (g_integ > 10000)
        g_integ = 10000;
    else if (g_integ < -10000)
        g_integ = -10000;

    g_out = (err << 1) + (g_integ >> 3);
}

void stage_sink(void)
{
}

void loop_main(void)
{
    stage_sample();
    stage_pid();
    stage_sink();
}
```

这段代码的关键特点是：`g_integ` 不是临时值，它会在不同扫描周期之间保留。

所以你不能简单地把 `stage_pid()` 拿出来作为无状态函数运行。

同时，仓库中的 `stage_sample()` 和 `stage_sink()` 带有用户态限制。这意味着当前 PID 示例的全内核方案不能作为默认合法候选。

### 第 2 步：只做一次统一前端分析

保留现有：

- `frontend/ast/ast_tool__AST工具.cpp`
- `frontend/stage_extract/stage_extract.py`
- `analysis/EffectSummaryAnalysis__副作用摘要.cpp`

但不再让它们各自建立一套互不相干的任务模型。

建议前端产生一份统一的分析结果，继续使用已有 `task.teir.json` 作为主要输入，不需要重新发明一个中间表示。

它应当记录：

| 信息    | 从哪里得到              | 后续用途      |
| ----- | ------------------ | --------- |
| 函数入口  | Clang AST          | 确定周期任务    |
| 调用关系  | AST + LLVM         | 确定需要保留的函数 |
| 全局读写  | LLVM EffectSummary | 检查数据交接    |
| 跨拍状态  | TEIR 分析            | 保证积分状态不丢失 |
| 阶段相位  | 程序声明及时间契约          | 生成释放表     |
| 禁止调用  | AST + LLVM         | 决定可否内核化   |
| 执行域限制 | 源码声明与平台能力          | 限制候选部署    |

这里还有一个需要补强的地方：应该明确区分“建议相位”和“必须遵守的相位”。

如果某个阶段必须在第 400 µs 更新真实硬件输出，就不能因为融合方案响应更短，而直接将它提前到第 0 µs。只有在时间契约允许时才能改变释放结构。

### 第 3 步：生成并验证统一的 `plan.json`

STKP 保留，但改变它的最终职责。

以前它主要回答：

> 哪些阶段分组，放入哪个执行域？

现在它要生成一份足以直接指导最终代码与运行时生成的部署计划。

建议扩展后的结构如下。这是我提出的新字段设计，不是说仓库目前已经全部支持。

```
{
  "task": "mixed_pid",
  "period_us": 1000,
  "deadline_us": 1000,

  "groups": [
    {
      "id": "g0",
      "stages": ["stage_sample"],
      "domain": "user",
      "phase_us": 0
    },
    {
      "id": "g1",
      "stages": ["stage_pid"],
      "domain": "kernel",
      "phase_us": 200
    },
    {
      "id": "g2",
      "stages": ["stage_sink"],
      "domain": "user",
      "phase_us": 400
    }
  ],

  "state_ownership": {
    "g_seq": "user",
    "g_integ": "kernel"
  },

  "handoffs": [
    {
      "from": "user",
      "to": "kernel",
      "fields": ["g_in"],
      "method": "ioctl"
    },
    {
      "from": "kernel",
      "to": "user",
      "fields": ["g_out"],
      "method": "ioctl"
    }
  ],

  "runtime": {
    "cpu": 3,
    "policy": "SCHED_FIFO",
    "priority": 80
  }
}
```

最重要的是增加三类明确的信息：

状态归谁所有。 例如积分器 `g_integ` 由内核保持，不能每拍从用户态重新初始化。

跨域需要传递什么。 用户态的 `g_in` 必须明确传入内核，内核计算出的 `g_out` 必须明确返回。两边即使定义了同名全局变量，也不会自动共享数据。

具体由谁负责释放。 不能出现用户态驱动和内核 hrtimer 同时认为自己是同一任务的周期调度负责人。

只有通过语义检查、接口检查、时间检查的计划，才能进入下一阶段。

## 三、真正统一 LLVM Pass 与代码生成

这是本次重构最重要的工作。

### 3.1 先根据计划拆出需要内核化的函数

以 U–K–U 为例：

```
原始源文件
   |
   +-- stage_sample() ---> 用户态代码
   |
   +-- stage_pid() ------> LLVM 内核化 Pass
   |
   +-- stage_sink() -----> 用户态代码
```

不要将原始 C 文件整体转换后直接放进 `.ko`，也不要在专用宿主生成后直接复制原始 C 文件来冒充 LLVM 内核化。

应由编译器根据计划计算出内核函数及其依赖函数的完整集合。

例如：

```
kernel_roots:
    stage_pid

required_kernel_state:
    g_integ

copy_in:
    g_in

copy_out:
    g_out
```

这里还必须分析 `stage_pid()` 调用的辅助函数。如果辅助函数不满足内核安全条件，整个候选应当被拒绝。

### 3.2 再让 PLCFusionPass 转换这部分计算

统一后的关键过程是：

```
原始 task.c
     |
     v
Clang 生成 task.ll
     |
     v
读取经过验证的 plan.json
     |
     v
提取被选中的内核函数及依赖
     |
     v
PLCFusionPass
  - 检查和映射允许的 API
  - 保留必需的函数与状态
  - 清理无关函数
  - 执行经过验证的类型转换
     |
     v
kernel_stage.ll
     |
     v
llc
     |
     v
kernel_stage.o
```

这样才可以清楚地证明：

最终内核模块中的计算代码，确实来自 Clang/LLVM 对原始用户程序的编译与转换。

### 3.3 不能再允许缺失函数被静默替换

我建议正式部署模式固定以下规则：

```
unmapped external    → 编译失败
unknown indirect call → 编译失败
unsafe allocation    → 编译失败
unverified sleep      → 编译失败
unsupported floating → 编译失败
```

已有 `PLCFusionPass` 的默认未映射调用策略是 `error`，应继续保留。

旧工具链中的自动桩生成、`blackhole` 删除调用等行为，只能用于明确标识的开发实验；正式版本不能为了生成 `.ko` 而把设备操作或同步操作替换成无效果的函数。

此外，浮点转换为定点数会改变数值行为，必须单独做误差和溢出验证，不能把“能成功编译”视为“语义完全相同”。

### 3.4 生成内核计算包装器

转换后的业务函数需要一层明确的输入、输出和状态接口。

例如，可以由编译器生成类似的包装代码：

```
/* 示意：由计划生成，非当前仓库现成产物 */

struct kf_pid_input {
    int32_t value;
};

struct kf_pid_output {
    int32_t value;
};

void kf_pid_execute(
    const struct kf_pid_input *input,
    struct kf_pid_output *output)
{
    g_in = input->value;

    stage_pid();  /* 来自 LLVM 内核化目标文件 */

    output->value = g_out;
}
```

注意这层代码只是调用包装器，不重新手写 PID 算法。

其中 `g_integ` 保持为内核侧的持久状态，由一个确定的初始化与复位流程管理。

对用户态和内核态的状态应该建立明确的所有权规则，不能一份状态在两个执行域各自修改，又假定它们自然保持一致。

## 四、宿主也需要统一：一个 PLC 任务优先使用一个执行线程

这是我建议修改的第二个关键点。

当前 `linux_kernel_emitter.py` 是：

> 一个阶段组，一个 hrtimer，一个 kthread。

对多个独立任务，这种结构可能有意义。

但对于你现在研究的单个 PLC 逻辑任务，我建议默认改成：

一个周期任务、一个 hrtimer、一个实时内核工作线程、一个按相位排列的事件表。

一个 PLC 任务：P = 1000 µs

相位表：0、200、400 µs

一个 hrtimer

按照绝对时间触发对应阶段组释放

预分配的释放事件队列

记录周期序号、组 ID、名义释放时间

一个 SCHED_FIFO 内核线程

按照事件依次执行 g0 / g1 / g2

### 为什么我更推荐这样做？

原来每组一个线程，三个组就有三个执行实体。它们可能发生抢占、跨周期重叠，并需要额外检查数据依赖是否被正确实现。

改成同一线程按释放事件执行，可以自然保证这个任务的阶段不会被自身的另一个线程并发执行，从而简化状态管理。

但必须明确：一个线程并不代表每周期只能唤醒一次。

如果时间契约要求三个独立释放相位，仍然需要三个释放事件。减少线程数不能成为绕过相位约束的手段。

建议事件结构如下：

```
struct kf_release_event {
    uint64_t cycle_id;
    uint32_t group_id;
    uint64_t nominal_release_ns;
};
```

hrtimer 回调将事件写入预先分配的有界队列，并唤醒工作线程。

工作线程读取事件，确认周期序号与执行顺序，然后调用对应的计算包装器。

队列满时，必须明确记录溢出和超期，而不能静默覆盖旧事件。定时器下一次到期时间应基于统一的绝对时间基准计算，不能因为上一阶段执行迟到就随意改变整个周期表。

这项设计应作为新的宿主实现，与现有每组一个线程版本做对照，不能在未测量前直接声称新宿主抖动更小。

### 三种部署方式如何统一？

| 部署形式      | 周期释放负责人          | 计算如何执行              |
| --------- | ---------------- | ------------------- |
| 全用户态      | 生成的用户态周期驱动       | 在用户线程中调用阶段函数        |
| 全内核态      | 生成的内核 hrtimer 宿主 | 内核线程调用 LLVM 转换后的计算体 |
| U–K–U 混合态 | 用户态周期驱动          | 用户线程同步 ioctl 执行内核阶段 |

这三种模式使用相同的编译计划和相同的时间语义，但各自使用与执行域匹配的操作系统机制。

尤其需要强调：现有 UKU 是同步 ioctl 方式，它并不会自动绕过用户态唤醒延迟。应当保留为受约束的混合部署候选，而不是默认认为它优于全用户态。

# 五、隔离策略：这是新架构必须补上的一层

这里建议分成五类，分别解决不同问题。

## 5.1 CPU 隔离：减少周期任务受到普通任务干扰

以四核树莓派作为实验平台，可以先采用下面的初始实验布局：

### 建议的四核职责分配

CPU 0

系统管理

CPU 1

后台任务

CPU 2

I/O 服务

CPU 3

PLC 实时核

这是待验证的实验配置，不是所有硬件和 I/O 场景下的固定最优配置。

CPU 0～1 承担系统后台活动。

CPU 2 可承担可迁移的 I/O 服务、中断线程和实验数据整理。

CPU 3 留给本轮正在测试的 PLC 周期执行路径。

如果测试全用户态，就让用户态实时线程使用 CPU 3；如果测试全内核态，就把周期内核线程及对应定时器部署到 CPU 3。

这样两种执行域的比较才能使用尽量相同的 CPU 资源条件。

Linux 官方现在更推荐在适当内核配置下使用 cgroup v2 的 isolated cpuset partition 做可动态调整的调度域隔离，而不是始终依赖难以动态改变的 `isolcpus=domain` 启动参数。

[image](https://www.google.com/s2/favicons?domain=https://docs.kernel.org\&sz=32)

The Linux Kernel documentation+1

但要注意：

cgroup 负责用户进程的资源组织，不能替代内核模块对 kthread 的 CPU 亲和性、线程优先级和内存行为的显式管理。

也不要默认给实时控制线程设置 CPU 配额限制。普通 CPU 带宽配额可能造成周期性节流，反而破坏实时实验。

## 5.2 中断隔离：避免无关 IRQ 打断控制任务

仅仅把 PLC 线程绑定在 CPU 3，不能保证该 CPU 不会受到中断影响。

建议在部署工具中增加 IRQ 检查与配置步骤：

- 列出当前中断及其 CPU 亲和性。
- 将可迁移的网络、存储和其他无关中断尽量转移到 housekeeping CPU。
- 对 PLC 实际依赖的输入设备中断，单独制定优先级和 CPU 放置策略。
- 记录真实生效的 IRQ 分布，不能只记录申请的 affinity。

`irqaffinity` 和 `/proc/irq/*/smp_affinity` 可以参与配置，但部分 managed IRQ 不能像普通 IRQ 一样任意迁移，隔离只能做到尽力而为。

[image](https://www.google.com/s2/favicons?domain=https://docs.kernel.org\&sz=32)

The Linux Kernel documentation+1

对于 PREEMPT_RT，还有一个特别重要的问题：许多中断处理会转入可调度的线程上下文，内核锁的行为也和普通 PREEMPT 内核不同。你的实时线程优先级必须与设备 IRQ 线程的实际优先级关系一起检查。

[image](https://www.google.com/s2/favicons?domain=https://docs.kernel.org\&sz=32)

The Linux Kernel documentation+1

因此，不建议一开始就把所有线程都设为 FIFO99。先配置一套可控的优先级，再通过实验确认是否需要调整。

## 5.3 内存隔离：禁止实时路径发生不可控的内存操作

建议将运行时划分为初始化阶段和周期执行阶段。

| 行为      | 初始化阶段  | 周期执行阶段        |
| ------- | ------ | ------------- |
| 分配任务状态  | 允许     | 原则上禁止动态分配     |
| 创建线程    | 允许     | 禁止            |
| 初始化定时器  | 允许     | 不重复初始化        |
| 建立跨域缓冲区 | 允许     | 只读写已分配缓冲区     |
| 输出日志    | 允许必要日志 | 禁止逐拍 `printk` |
| 装载配置    | 允许     | 不做文件系统 I/O    |
| 执行控制算法  | 测试/初始化 | 主要执行内容        |

用户态实时进程可以使用 `mlockall()`、预触碰栈与缓冲区等方法降低运行中的缺页风险。Linux CPU 隔离文档也明确强调避免缺页、CPU 频率变化和深度空闲状态等干扰源。

[image](https://www.google.com/s2/favicons?domain=https://kernel.org\&sz=32)

The Linux Kernel documentation

内核模块则应在加载期间预分配有界缓冲区、状态空间和事件队列；实时执行路径不应临时分配大块内存。

但这里必须说明：

CPU 隔离与内存预分配只能降低干扰，不能把不可信内核代码安全地隔离在内核之外。

内核态代码与 Linux 内核共享特权地址空间。一个错误指针可能影响整个系统。因此，只有通过严格语义与接口检查的受信任计算代码才应该被编译进 `.ko`。

对未知指针、不可分析外部调用、复杂动态分配等情况，应该留在受进程保护的用户态，而不是强行内核化。

## 5.4 数据隔离：用户态和内核态只通过明确接口交换状态

这是选择性内核化必须建立的安全边界。

建议规则：

用户态不允许直接控制内核中的任意指针。

内核态不允许直接假定用户态全局变量与内核中的同名变量是同一份数据。

所有跨域数据由编译器自动生成固定布局的接口。

例如：

```
struct kf_request {
    uint32_t seq;
    int32_t input;
};

struct kf_response {
    uint32_t seq;
    int32_t output;
};
```

内核使用 `copy_from_user()` 将经过检查的数据复制到内核缓冲区，再执行计算，最后使用 `copy_to_user()` 返回结果。

跨拍持久状态只允许由指定执行域维护。

这里我还发现了现有 UKU 代码中一个值得优先修正的问题：

当前 `mixed_uku_codegen__混合交接.py` 生成的 ioctl 路径，先执行可能修改内核全局状态的阶段函数，再调用 `copy_to_user()`，最后才增加期望序号。

如果计算已经修改积分状态，但 `copy_to_user()` 失败，内核状态已经前进，而序号尚未提交。调用方如果重试同一请求，可能让积分计算执行两次。

建议将状态计算改为受控的临时状态计算，成功交付后才提交；暂时无法实现事务式提交时，至少在此类失败后将会话标记为故障状态，拒绝继续重试，直到经过明确复位。

这项问题比单纯优化 ioctl 开销更应该优先处理。

## 5.5 故障隔离：实时任务失效时怎么办？

编译器应为运行时生成明确的错误策略，而不是只记录一个 `missed` 计数。

至少要覆盖：

| 故障         | 检测方式            | 建议处理           |
| ---------- | --------------- | -------------- |
| 释放事件队列溢出   | 队列容量/事件序号       | 记录失拍，执行预定义过载策略 |
| 控制任务超期     | 完成时间超过截止期限      | 计数并触发应用规定的处理   |
| ioctl 序号错误 | `seq` 不连续       | 拒绝错误调用         |
| 输入数据过期     | 数据年龄或周期序号       | 拒绝旧数据或进入预设安全处理 |
| 内核计算错误     | 接口返回/异常检测       | 停止会话，禁止静默重试    |
| 模块初始化失败    | 定时器、线程、内存资源建立失败 | 撤销已初始化资源，拒绝启动  |

对于真实控制系统，输出保持、关闭或进入安全状态必须由具体设备的安全需求定义，编译器不能自己假设“保持上一拍输出就是安全的”。

## 六、把隔离信息也写入编译计划

隔离不能只是实验结束后手工执行的一组命令。

我建议增加一个配置文件，例如 `isolation.yaml`：

```
target:
  board: raspberry-pi
  require_preempt_rt: true

cpu:
  housekeeping: [0, 1]
  io: [2]
  control: [3]

runtime:
  sched: SCHED_FIFO
  priority: 80
  timer: absolute
  worker_per_task: 1

memory:
  preallocate: true
  forbid_hotpath_alloc: true
  forbid_hotpath_printk: true

irq:
  move_unrelated_irqs: true
  verify_effective_affinity: true

safety:
  unknown_external: reject
  unsupported_pointer: reject
  invalid_state_transfer: reject

evidence:
  require_environment_match: true
```

这是一个建议新增的部署描述格式，不是现有可直接执行的配置。

它应在编译之前用于检查平台能力，并在代码生成后指导部署工具配置 CPU、线程、IRQ 和资源。

同时要将实际生效的配置写回 `environment.json`，供实验与反馈系统使用。

尤其是 PREEMPT_RT 类型、内核配置、编译器版本、源代码哈希、部署计划哈希、CPU/IRQ 布局、调度策略，都应该纳入可复用画像的身份判断。

当前新增的 `bringup_check__换卡自检.sh` 已经检查部分这些信息，但最后的旧画像匹配主要比较内核 release 和板型，还不够全面。建议改为完整身份匹配，不满足条件时不得直接复用旧 Q99 数据。

另外，我不建议默认打开 `nohz_full`。它主要针对满足特定限制的近乎纯用户态独占 CPU 工作负载；对频繁进入内核的 UKU 路径或由内核线程运行的周期任务，不应在未经实验前假设一定有收益。

## 七、给你一条最终统一的执行实例

假设编译器最终选择全内核态、单阶段组的合法任务。

整个过程应当是：

```
用户编写 plc_task.c

        |

        |
        +---------------------------+
        |                           |
        v                           v
提取需要内核化的函数           生成宿主配置
        |                           |
        v                           v
PLCFusionPass                  hrtimer / worker
        |                      / release table
        v                           |
kernel_stage.ll                    |
        |                           |
        v                           v
      llc                   generated_host.c
        |                           |
        v                           v
kernel_stage.o              generated_host.o
        |                           |
        +-------------+-------------+
                      |
                      v
               Linux Kbuild
                      |
                      v

                      |

                      |
```

这条链里，旧版 PLCFusionPass 不再是一个独立演示工具，而是统一后端必经的转换阶段。

而新的 `plan.json` 不再只是画图和对比成本的分析结果，而是直接决定最终代码链接什么、由什么线程执行、使用什么释放相位和 CPU。

对于全用户态及混合态，也使用同一份计划，只是分支生成用户执行文件或 ioctl 接口，不改变编译器的整体流程。

# 八、具体应该怎么修改仓库？

我不建议现在推翻已经实现的代码。应该在保留历史实验可复现的前提下，逐步替换主入口。

下表是建议实施计划，不表示这些修改已经提交。

| 实施阶段              | 主要修改位置                                                | 验收目标                             |
| ----------------- | ----------------------------------------------------- | -------------------------------- |
| U-1 统一前端          | `frontend/ast/`、`frontend/stage_extract/`、`analysis/` | 一份 C 程序产生一致的阶段、函数及读写语义           |
| U-2 固定计划接口        | `ir/temporal_effect_ir.py`、`ecos_plan_joint.py`       | `plan.json` 完整描述分组、域、时间、状态所有权    |
| U-3 连接 LLVM 后端    | `backend/pass/PLCFusionPass...cpp`、新建分域构建入口           | 只把入选的 K 计算函数编译为 `kernel_stage.o` |
| U-4 统一代码生成        | `backend/synthesis/emit.py`、`body_emit.py`            | 从同一计划生成宿主、包装器与构建文件               |
| U-5 单工作线程宿主       | `linux_kernel_emitter.py`                             | 一任务、一工作线程、有序释放事件与周期序号            |
| U-6 隔离控制          | 新增 `scripts/isolation/`                               | 验证 CPU、IRQ、内存和内核环境               |
| U-7 统一验证与测量       | 现有语义校验、PR11～PR18 测量工具                                 | 代码生成结果、状态和时间证据可追踪                |
| U-8 PREEMPT_RT 验证 | 新建独立 RT 实验产物目录                                        | 在 RT 内核上获得新的、不能与旧平台混表的数据         |

### 第一轮应当优先完成的三项修改

第一优先：真正打通内核计算目标文件。

让：

```
chosen.plan.json
   → 选中的内核阶段
   → PLCFusionPass
   → kernel_stage.o
   → 专用宿主
   → .ko
```

真正运行一次。

以此替代当前专用宿主分支直接复制原始 `stage_impl.c` 的做法。

第二优先：修复状态所有权与 ioctl 提交语义。

先确保跨拍积分状态不会因为失败调用、重新连接或重试而产生错误更新。

另外，PID 示例的 `err << 1` 在 `err` 为负数时涉及 C 语言有符号左移未定义行为，应当在语义验证前先修正为经过范围证明的整数运算。否则即使不同版本得到相同 digest，也不足以证明程序对所有输入都具有相同语义。

第三优先：实现单工作线程专用内核宿主。

保留旧版每组一个线程作为实验对照，不立即删除。

新宿主先针对一个全内核、单阶段组任务跑通，再加入多相位事件表。这样可以将“计算代码转换正确”与“复杂释放调度正确”分开验证。

## 九、实验应该怎样设计，才能证明统一架构有价值？

我建议分成三类实验。

### 实验 A：编译器正确性

对同一份 PLC C 程序，比较原始用户态参考执行和编译后的执行产物。

检查每拍输入、输出、持久状态和周期序号，而不是只判断 `.ko` 能加载。

同时必须加入非法调用、未知指针、依赖顺序冲突、状态重试等负例，证明编译器确实能拒绝错误转换。

### 实验 B：执行机制和隔离贡献

在同一平台、同一任务和一致的测量口径下，比较：

| 方案 | CPU 隔离 | 执行机制            |
| -- | ------ | --------------- |
| U0 | 无专用隔离  | 用户态 FIFO 周期线程   |
| U1 | 有      | 用户态 FIFO 周期线程   |
| K0 | 无专用隔离  | hrtimer + 单内核线程 |
| K1 | 有      | hrtimer + 单内核线程 |
| K2 | 有      | 旧版每组一线程内核宿主     |
| M1 | 有      | 同步 UKU 混合态      |

其中 K0/K1/K2 只有在该任务整体允许内核执行时才合法；对于带用户态 pin 的 PID，不能为了补齐矩阵强行运行非法方案。

重点测量：

\\[ L=s-r,\qquad R=f-r \\]

以及 Q99、最大观测响应时间、超期数、积压事件数、CPU 迁移和中断干扰情况。

隔离配置需要单独成为实验变量，避免把“CPU 隔离收益”误写成“LLVM 内核化收益”。

### 实验 C：自动部署选择是否有效

使用不同的合法 PLC 负载，验证编译器能否依据成本和已有证据作出正确选择。

比较固定全用户态、固定内核化与自动选择。

这里最重要的结果不一定是“自动选择了内核”。

如果某个任务用户态已经更好，编译器选择留在用户态也是正确决策。

但要证明自动选择具有研究价值，不能只重复同一个 PID。需要选择不同阶段结构、不同计算成本和不同交互成本的任务，并采用训练与测试分离的评价方式。

当前 PR-19 的跨源码校准只能证明未知迁移会被拒绝，不能声称已实现性能泛化。

## 十、论文中的研究问题也应该统一

完成上述调整后，我建议论文不再分成“LLVM 内核化”和“STKP 部署规划”两个看起来独立的研究项目。

改成一条主线：

> 面向具有周期和状态约束的 PLC C 程序，研究一种基于 Clang/LLVM 的安全选择性内核化编译方法。通过程序语义分析与时间依赖建模，自动确定可内核化阶段、生成统一部署计划，将选定计算函数转换为内核目标代码，并生成匹配的周期执行宿主；结合 CPU、内存和中断隔离，以及板上测量反馈，对不同部署方式的实时响应和期限行为进行验证与优化。

可以形成三个相互依赖的技术贡献：

1. 语义约束下的自动内核化转换。 解决哪些用户态计算能安全放入内核、状态和函数调用如何保持正确的问题。
2. 编译计划驱动的周期执行代码生成。 解决阶段分组、时间释放、计算代码和宿主之间如何保持一致的问题。
3. 隔离与实测反馈驱动的部署决策。 解决不同执行域、调度结构和系统干扰条件下如何选择合适部署的问题。

第三项目前仍需要新的实验支撑，不能作为已证实的创新成果直接写进论文结论。

## 十一、最终的技术取舍

我会明确采用下面这组原则：

| 问题                 | 最终选择                      |
| ------------------ | ------------------------- |
| 是否保留 LLVM Pass？    | 保留，且成为所有入选内核计算路径的必经步骤     |
| 是否保留 TEIR/STKP？    | 保留，作为统一编译规划核心             |
| 是否保留原通用宿主？         | 保留用于历史兼容，不再作为新周期任务的默认生成路径 |
| 是否每组都创建内核线程？       | 新设计默认每任务一个工作线程，旧版保留做对照    |
| 是否所有 PLC 代码都放入内核？  | 否，只转换被证明合法且有部署必要的阶段       |
| 是否默认使用 UKU？        | 否，它是合法候选之一，不预设性能优势        |
| 是否默认启用最激进 CPU 隔离？  | 否，采用可验证、逐级增加的隔离配置         |
| 是否将 CPU 隔离等同于内核安全？ | 绝对不能                      |
| 是否优先开发跨程序残差迁移？     | 暂不优先，先完成统一端到端编译和 RT 实测    |

我认为最适合你当前课题的版本，是“LLVM 负责真正转换计算代码，TEIR/STKP 负责决定转换什么，自动生成的单任务宿主负责执行，隔离配置负责约束运行环境，测量反馈负责验证选择”。

这比维持两套编译入口更完整，也避免了为了追求更低抖动而不断堆叠新技术。

尤其要记住：你的核心创新应该发生在编译器如何理解、转换、选择和生成程序的过程中，而不是把 CPU 隔离、hrtimer 或 SCHED_FIFO 本身包装成新的算法。

这套方案尚未实际修改仓库或完成板上验证；上面给出的重构项和新宿主都是下一阶段的实施设计。现有代码能够复用的部分很多，第一步应从 U-1 到 U-3 入手，先把真正的“AST/LLVM → 内核计算目标文件 → 专用宿主 → `.ko`”打通，再开展隔离与性能优化。
