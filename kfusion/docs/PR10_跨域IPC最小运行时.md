# PR10 —— 跨域 IPC 最小运行时（IVSHMEM 发布-订阅）

> 状态：**两端实现 + 板上实测完成**（2026-10-25）。
> 目标：给 ECoS 的跨域边一个**可测的代价**，而不是拿单域融合的 `c`（唤醒税）去糊。
> 结论先说：**通路本身是亚微秒级，但控制回路里跨域依赖的代价是"一个周期"**。
> 这两件事差三个数量级，混用会把跨域优化的收益算到天上去。

---

## 1. 为什么不是"把旧 PoC 扩大一下"

仓库里原有 `xshm` + `ivshmem_probe`：直接拿 rw_section 起始 16 字节当 mailbox，
四个 32 位字，单向写、对端轮询。它能证明"通路通了"，但做不了三件事：

| 缺口 | 后果 |
|---|---|
| 只用一个方向的一段内存 | 两个方向要同时跑就得各写一套偏移，两端一旦不一致就是"都跑得动、数据不对" |
| 无提交语义（读者可能读到半个槽） | 跨域场景下这个窗口比单核大得多 |
| 无"这一轮"概念 | cell 重建**不清零** IVSHMEM，上一次的残留会被当成有效状态 |

PR10 的运行时有四条硬设计：

1. **一份头，两个宿主**：`kfusion/runtime/xshm/ecos_xipc.h` 被 root 侧（Linux 用户态）
   与 inmate 侧（NuttX）同时 `#include`，布局与环操作**只有一处定义**。
   仓库里不允许有第二份（自测里查）。
2. **按 peer 分片**：rw_section 是 3 peer × 12 KiB（0x9000）。peer0 片放 root→inmate 环，
   peer1 片放 inmate→root 环，peer2 片放统计。补上了旧 PoC 明确留下的 TODO。
3. **SPSC 无锁环**，每个环唯一写者、唯一读者，`head`/`tail` 各占一条 cache line；
   提交靠 `slot.seq`：先写负载 → 再写 seq → 最后推进 head，读者只认 `seq == tail+1`。
4. **session 号**：owner 每轮用 `CNTVCT` 生成一个新 session 写进环头，对端必须看到
   session **变化**才认为"新一轮开始了"。这一条是实测踩出来的，见 §5 的坑 3。

```
rw_section @ 0x1faf1000（root: /dev/uio0 map2；inmate: 同一物理地址同虚拟地址）
  0x0000  peer0 片  ┌─ struct xipc_ring  root → inmate  （224 槽 × 16 B）
  0x3000  peer1 片  ├─ struct xipc_ring  inmate → root
  0x6000  peer2 片  └─ struct xipc_stats（各字段归属固定，避免伪共享）
```

环头：`magic 0x00 | version 0x04 | cap 0x08 | slot_bytes 0x0C | session 0x10 |
head 0x40 | tail 0x80 | drops 0xC0 | slot[224] 0x100`，总共 3840 B，装进一页。
这些偏移在头文件里由 `XIPC_ASSERT_EQ` 编译期断言，另有
`kfusion/scripts/ecos/xipc_layout_check.py` 在本机（无编译器）做同一套算术校验。

### 消息与控制面

| kind | 方向 | 语义 |
|---|---|---|
| `HELLO` | inmate→root | 上线，a=版本，b=CNTFRQ |
| `PING` | root→inmate | a=序号，b=发送时刻（counter 低 32 位） |
| `ECHO` | inmate→root | a=序号，b=**读到 PING 那一刻**的 counter |
| `TICK` | inmate→root | 周期数据，b=产生时刻 |
| `MODE` | root→inmate | a=tick_every，b=period_us（运行时切模式） |
| `STOP` | root→inmate | 收工 |

`MODE` 不只是省一次交互：那块板子的串口**只能看不能敲**（只接了 Pi TX → 适配器 RX），
没法在 NSH 里输参数。让 root 侧用一条消息切换实时侧的工作模式，等于把"控制面"
也架在同一条环上——正好是要证明的东西：一条 SPSC 环 + 两类消息就能跑一个跨域控制回路。

## 2. 为什么两端都是轮询（门铃的硬约束）

IVSHMEM 门铃 = 往寄存器区 offset `0x0C` 写 `(target<<16 | vector)`，由 hypervisor
陷获后向目标 cell 注入中断。它成立的前提是**寄存器区被注册成可陷获的 MMIO**，而这
要求本 cell 的 PCI 命令寄存器置了 `MEM` 位：

- root 侧：`uio_ivshmem` 驱动置了 → 门铃路径存在（`/proc/interrupts` 里能看到
  `uio_ivshmem[0001:00:00.0]`，GICv2 182）。
- NuttX 侧：**没有 PCI 枚举**，这个位不会置。此时 cell 配置里 0x1faf0000 只给了
  `JAILHOUSE_MEM_READ`，对该地址的写不是"没效果"，而是**故障**。

所以本轮两端都是轮询。对周期性控制任务这不是妥协：实时侧本来就要在周期边界采样，
边界上的轮询是零额外代价的。门铃要等 NuttX 侧补一个最小 PCI 配置访问（置 `CMD_MEM`
+ 启 INTx）才谈得上，记在 §6。

## 3. 实测（Pi4，root cell ↔ NuttX inmate，1 kHz 参考周期）

条件：Pi4B / jailhouse v0.12-342 / 内核 5.15.86 / NuttX cell 独占 CPU1 /
root cell 0,2-3 / 未绑核 / `CNTFRQ = 54 MHz`。
分位数为原始样本排序后的精确值（不用直方图近似，原因见 §5 坑 6）。

### 3.1 通路下限（inmate 忙等，3000 次一问一答）

| 量 | p50 | p90 | p99 | p99.9 | min | max |
|---|---|---|---|---|---|---|
| 单程 root→inmate | **0.65 µs** | 0.65 | 0.70 | 71.61 | 0.59 | 71.85 |
| RTT | **1.24 µs** | 1.26 | 1.31 | 72.28 | 1.19 | 76.85 |

- 单程/RTT ≈ 1.9 —— 这是**时间基准自洽的经验证据**：两侧都读 `CNTVCT_EL0`，
  Jailhouse 不设 `CNTVOFF`，所以是同一个计数器。异常样本 0 / 3000。
- 尾部 72 µs 不是通路本身，是偶发的调度/中断介入（未绑核，未做归因）。

### 3.2 控制回路里的真实代价（inmate 按 1 ms 周期采样，500 次）

| 量 | p50 | p90 | p99 | min | max |
|---|---|---|---|---|---|
| 单程 | **1005.26 µs** | 1005.33 | 1005.37 | 285.70 | 1006.18 |
| RTT | **1005.87 µs** | 1005.94 | 1006.00 | 286.30 | 1017.44 |

**p50 ≈ 1.005 个周期**，不是半个周期。原因不是"运气差"，而是调用方被相位锁死：
root 收到 ECHO 后立刻发下一个 PING，而此刻 inmate 刚好做完本轮 drain 去睡，
于是下一个请求必然等满一整拍。min 285.7 µs 对应"恰好在 drain 前到达"的少数样本。

对 ECoS 的含义很直接：**跨域边是一条 ≥1 个周期的延迟边**。评估"该不该把这段搬到
另一个域"时，必须用 `≈ period` 而不是 §3.1 的微秒数。

### 3.3 消费侧轮询粒度（inmate 每 1 ms 推一个 TICK）

| root 的 drain-sleep | p50 | p90 | p99 | max |
|---|---|---|---|---|
| 0（忙等） | **0.74 µs** | 0.78 | 0.80 | 15.78 |
| 250 µs | 166.56 µs | 296.04 | 323.07 | 363.22 |
| 500 µs | 286.20 µs | 509.83 | 563.33 | 698.91 |

p50 ≈ `sleep/2 + 40 µs`。那 40 µs 是 `usleep()` 的固有超调（Linux 的 sleep 粒度），
不是通路开销——把它算进"IPC 延迟"会高估一个数量级以上。

## 4. 三个必须分开说的判断

1. **通路延迟 ≠ 依赖代价。** 0.65 µs 是"两个 cell 都空转时"的下限；1.005 ms 才是
   "实时侧按周期采样"时的真实值。论文里只能引用后者作为跨域边的代价。
2. **门铃不是"还没做"，是"这侧没有 MMIO 陷获"。** 写门铃会撞只读映射。不写清楚
   这一点，后来的人会以为加个 `write()` 就行。
3. **时间可比是有前提的。** 两侧共基准靠"Jailhouse 不设 CNTVOFF"这个事实，
   不是协议保证的。所以运行时自带经验校验（单程 > RTT 就单列计数），
   一旦换 hypervisor / 换核，异常计数会立刻暴露。

## 5. 踩到的坑（每条都花了不止一轮）

| # | 症状 | 根因 | 处理 |
|---|---|---|---|
| 1 | root 侧 `SIGILL`，且**一行输出都没有** | `mrs cntpct_el0` 在 EL0 是未定义指令（内核没置 `CNTKCTL_EL1.EL0PCTEN`）；stdout 走管道是块缓冲，崩了什么都不留 | 改用 `CNTVCT_EL0`（VDSO 用的就是它）；root 侧 `setvbuf(_IOLBF)` |
| 2 | 单程**恒为负**、可见值溢出到量程顶 | 环槽只有 32 位，我把截断值和 64 位值直接比较 | 两端统一用"32 位回绕差"：`(uint32_t)(b - a)`，@54 MHz 可表示 79 s |
| 3 | root 等 30 s 收不到 HELLO，inmate 日志说"已发过" | **IVSHMEM 内存不随 cell 重建清零**，inmate 看到上一轮的 magic 就上线，HELLO 被 root 随后的 init 抹掉 | 加 session：owner 每轮写新的 `CNTVCT` 值，对端必须看到 session **变化** |
| 4 | 改了代码、构建报成功、跑起来还是老行为 | `cp -a` 保留 PC 侧 mtime（还差 8 小时时区），make 认为源码没变；而"镜像里有 xipc"的校验串从第一版就存在 | 构建脚本强制 `touch` + 删 `*.o`；校验串换成**本版专有**标记 `xipc: session 0x` |
| 5 | 开机只打一行 `usage: xipc ...` 就结束 | `task_spawn` 会把 `CONFIG_INIT_ARGS` 塞成 `argv[1]`（argc=2），参数解析遇到不认识的直接 `return 1` | 未知参数只告警并继续；所有参数有缺省值 |
| 6 | "周期"档 p50 报出 `819.10 µs` | 100 ns × 8192 = 819 µs 的直方图，样本全撞桶顶，报出来的是**桶顶假值** | 改存原始样本再排序求分位数（几千个样本，不值得用近似） |
| 7 | 忙等档"2000 万次迭代"0.4 秒就跑完，实验还没开始就退出 | 退出条件写成迭代数，而忙等一圈只有几十纳秒 | 退出条件改成**时间**（deadline），迭代数只作上限 |

另外两条不是坑但值得记：
- inmate 侧日志必须**纯 ASCII**（中文经 mini-UART 出去是乱码）；
- 开机入口从 `fiveloop_main` 换到 `xipc_main` 而不是"关掉 CONFIG_BENCHMARK_FIVELOOP"
  ——关配置项后旧 `.o` 还会赖在 `libapps.a` 里（上一轮踩过）。

## 6. 没做 / 下一步

- **门铃（中断）**：需要 NuttX 侧最小 PCI 配置访问（置 `CMD_MEM`、启 INTx、
  接 IRQ 184）。届时可对比"门铃唤醒"与"轮询"在**空闲**场景下的差。
- **按 peer 分片的形式化**：现在用了 peer0/1/2 三片，但没有实现 Jailhouse 内置
  协议的 peer 状态表语义（`State Register` / `State Table`）。
- **未绑核**：尾部 72 µs 未归因；把 inmate 任务与 root 线程钉到固定核后应能压低。
- **接进 ECoS 规划器**（下一轮 PR10-B）：跨域边进入 DAG 后，规划器应
  ① 禁止跨域融合（除非显式允许），② 用 `≈period` 而不是 `c` 计代价，
  ③ 由验证器独立复核该代价。

# 8. PR10-B：跨域边进入 ECoS（规划 / 验证 / 生成三处都按"拍"计）

上一节量出来的数如果不能改变决策，就只是博客。这一节把它接进工具链。

## 8.1 语义：跨域边 = 只能跨拍满足

跨域边和 z⁻¹ 闭合边是**同一类东西**：生产者在一个 cell 跑完，消费者在另一个 cell，
两者没有共享的"这一拍"，消费者只能在下一个周期边界看到它。因此：

| 结论 | 依据 |
|---|---|
| 不约束同一拍内的先后 | 消费者本来就读的是上一拍的值，同拍顺序对它无意义 |
| 每条给端到端加**一整拍** | 实测 1 kHz 下跨域 RTT p50 = 1005.26 µs（≈1.005 拍） |
| 环上 C 条跨域边 ⇒ 死区至少 C 拍 | 同上，每跨一次域就得多等一个边界 |
| **跨域融合不存在** | 融合 = "一次释放里连续跑几个阶段"；两个 cell 各有内核与调度器 |

最后一条写成**硬约束，不给开关**。设一个 `--allow-cross-domain-fusion` 只会让人以为
"调一下就能跨域融合"，而那是物理上做不到的事。规划器拒绝、验证器独立复核、代码生成器
也拒绝（`emit` rc=6，因为一个宿主不可能同时属于两个 cell）。

## 8.2 实现

```
kfusion/scripts/ecos/domain_model.py   ← 域语义唯一实现（规划器与验证器共用）
kfusion/scripts/ecos/plan_verify.py    ← 独立复核 DOMAIN_MIXED / XDOM_DEADLINE
kfusion/scripts/fusion_plan__融合规划.py ← 组内域纯度 + 端到端按拍计 + 死区按拍计
kfusion/backend/synthesis/emit.py      ← 跨域方案拒绝合成（rc=6）
```

DAG 里节点级 `domain` 字段即可声明（`"domain": "nuttx"` / `"root"`）；不写就是单域，
**现有所有夹具行为不变**。域信息出现在三处：`plan.meta.cross_domain`（统计）、
每个组的 `domain`、`cost.cross_domain_periods / cross_domain_extra_us`。

## 8.3 实测（夹具 `xdom_loop`：同一条闭环，前三段 NuttX，后两段 root）

```
方案：2 组
  g0   stage_sample + stage_fir + stage_pid        （nuttx）
  g1   stage_clamp + stage_plant                   （root）
代价
  释放税 2×21 = 42 µs ｜ 段内 R̂ ≈ 621.8 µs
  跨域：2 条跨域边 stage_pid→stage_clamp, stage_plant→stage_sample
        ｜ 端到端多 1 拍 × 1000 µs = 1000 µs ⇒ **含跨域 1621.8 µs**
反馈环
  闭合边 stage_plant→stage_sample 间隔 200 µs → **1400 µs**（×7.00）
```

三个值得看的点：

1. **段内只有 621.8 µs，看着很健康；加上跨域那一拍就是 1621.8 µs。**
   期限如果按 1000 µs 给，规划器报 `跨域期限` 并拒绝——而"段内"检查会一路放行。
   这就是必须按拍计的原因：差三个数量级。
2. **死区从 200 µs 变成 1400 µs**：1 拍来自 z⁻¹，另 1 拍来自跨域。两笔都要算。
3. **不能全融合了**：`不可合并：…（跨域：段内成员分属 nuttx / root，融合要求同一次
   释放…）`。同样一条闭环，单域时 1 组、跨域时 2 组——省下的唤醒税也不同。

## 8.4 顺带修掉一个真的 bug（域切开后才暴露）

规划器的"不可分性"检查原来用**全边**传递闭包（含 z⁻¹）。有环的图里这会造成假阳性：
`stage_clamp` 经由 `plant→sample` 的 z⁻¹ 边能绕回 `stage_sample`，于是
`stage_sample + stage_fir` 被判成"clamp 必须夹在中间"——跨域切开后**每一对**相邻阶段
都被误拒。

修法：不可分性只用**同拍**可达（摘掉闭合边与跨域边后再算闭包）。验证器一直是这么算的
（它只喂 `same_cycle` 边），规划器不是——两边不一致本来就会产出"规划说不可行、
验证说合法"的鬼故事。修完规划器给出正确的 2 组。

## 8.5 回归

- 融合自测 79 → **88**（§27 域纯度 / §28 代价按拍 + 死区 2 拍 / §29 验证器独立复核）
- 后端自测 50 → **55**（§11：跨域方案 emit 拒绝 rc=6、拒绝即停、不误伤单域）

## 8.6 没做

- **两个域各自合成一份产物**：现在 `emit` 直接拒绝跨域方案。正解是把 plan 按域拆开、
  各配自己的阶段源码分别 emit，再用 PR10 的环把两端连起来——需要 `ecos_build` 支持
  `--split-by-domain`。这是 PR10-C。
- 跨域边的**相位对齐**没有建模（现在只算拍数，不算"哪个边界"）。
- 多域（>2）只在 unit 层面支持，没有夹具。

# 9. 一个被 bug 掩盖的旧结论：环**可以**部分融合

修掉不可分性的假阳性之后，两个既有夹具（`loop_phasepin`、`loop_fb_limit`）的结论变了，
这个变化比 bug 本身更值得记。

## 9.1 旧结论错在哪

项目里长期记着一条判据：**"SCC 上不可分性自动成立 ⇒ 环只能整体成组"**。它来自同一个
全边闭包：环里任意两个成员之间总能找到第三个成员（绕 z⁻¹ 边绕回来），于是任何切分都被
判"不可分"。但这恰恰是假阳性——**z⁻¹ 边跨的是两拍**，"中间夹着"在拍内不成立。

摘掉延迟边后，周期性环是一条**链**：

```
sample(0) → fir(200) → pid(400) → clamp(600) → plant(800) →[z⁻¹]→ sample(下一拍 0)
└────────────── 同一拍，顺序固定 ──────────────┘   └── 跨拍 ──┘
```

所以部分融合是合法的，条件是两条：**同拍边顺序不变**、**死区上限不被突破**。

## 9.2 实际变化

| 夹具 | 旧（假阳性） | 新 | 死区 |
|---|---|---|---|
| `loop_phasepin` | 5 组（被"环"强行全拆） | **2 组**：`sample+fir+pid+clamp` ｜ `plant` | 200 → 200 µs |
| `loop_fb_limit` | 5 组（同上） | **2 组**：`sample+fir+pid` ｜ `clamp+plant` | 200 → **400 µs**（上限 500，合法） |
| `five_stage_loop`（无上限） | 1 组 | 1 组（不变） | — |

`loop_phasepin` 里挡住全融合的其实是**相位钉住**（`plant` 读外部输入，前拉 800 µs 等于
提前采样），跟环是不是 SCC 无关。`loop_fb_limit` 里死区上限 500 µs 是**硬约束**、
不是优化目标：拉到 400 µs 没越限就合法，而 2 组的 R̂（621.8 µs）比 5 组（821.5 µs）更好。

两个夹具的新方案都过了独立验证器——规划器与验证器给出同一个结论，这正是修好一致性后
该有的样子（以前是两边都错得一样）。

## 9.3 因此改判的判据

> ~~SCC 上不可分性自动成立 ⇒ 环只能整体成组~~
>
> 正确判据：**不可分性只由同拍边决定**（摘掉 z⁻¹ 闭合边与跨域边）。
> 周期性环摘掉延迟边后是链，可以部分融合；真正拦住它的是相位钉住、
> 死区上限、控制窗这些**独立**约束。

# 10. PR10-C：按域拆成两份产物，跨域数据过环

PR10-B 定了"跨域融合不存在"，PR10-C 把这条约束**落到产物上**：一份跨域 plan 拆成
每域一份，各自生成各自的宿主，中间的共享全局改成过环的消息。

## 10.1 为什么必须改成交信，不能继续共享全局

单域部署里 `g_act` 是一次 store + 一次 load。跨域部署里如果两端仍然各自读写自己的
`g_act`，**跑起来不报错、结果全错**——两个 cell 的 `g_act` 是两份独立内存。

所以拆分器要把"哪些全局要过环"从 DAG 边的 `evidence`（`@g_act`）里读出来，写进
接口描述；生成器据此在阶段调用前后插发布/订阅。没有证据的跨域边**直接报错退出**，
不生成"两端互不相干"的产物——那不是降级，是错的。

## 10.2 产物形态

```
plan.json（跨域，已验证）
   └─ split_plan ─► OUT/interface.json        （哪条边、哪个全局、哪个方向）
                 ├─ OUT/nuttx/{plan,meta}.json
                 └─ OUT/root/{plan,meta}.json
                        │
        emit --xdom meta.json（每域各跑一次）
                        │
        ├─ nuttx/  ecos_nuttx_main.c + ecos_fused_body.c + ecos_xdom.c + Makefile
        └─ root/   ecos_fused_linux.c  + ecos_fused_body.c + ecos_xdom.c + Kbuild
```

生成的周期体（nuttx 侧，注意插点位置）：

```c
void ecos_body_g0(void)
{
	ecos_xdom_sub(1, &g_plant);	/* 跨域输入：通道 1，来自 root 域 —— 在 sample 之前 */
	stage_sample();
	stage_fir();
	stage_pid(1000);
	ecos_xdom_pub(0, g_act);	/* 跨域输出：通道 0，发往 root 域 —— 在 pid 之后 */
}
```

两个插点位置都是**语义要求**，不是排版偏好：
- 订阅必须在消费阶段**之前**：晚一个周期，可用时刻就晚一个周期。
- 发布必须在产生阶段**之后**：同理。

## 10.3 桥本身（`ecos_xdom.c`）

只做三件事：init 时按本域角色把两个环的地址定下来、pub 把 int32 塞进槽、
sub 把本通道**最近一条**取回。没有线程、没有锁、没有定时器——调度归宿主，桥只搬字。

环的选择写在生成物里，不靠运行时猜：root 域 out=`0x0000`/in=`0x3000`，
nuttx 域相反（与 PR10 的 peer 分片一致）。

订阅只取最近一条、丢弃积压——跨域读的本来就是上一拍的值，攒着只会读到更旧的数据。

## 10.4 门（三条，都有负向用例）

| 情况 | 行为 |
|---|---|
| 父方案没有验证凭据 | 拆分拒绝（rc=3）。拆分不产生合法性 |
| 方案里有组跨域 | 拆分拒绝（rc=3），理由写"融合要求同一次释放" |
| 跨域边没有 `evidence` | 拆分拒绝（rc=3）。否则会生成两端互不相干的产物 |
| 拿**未拆分**的跨域 plan 直接 emit | rc=6（PR10-B 的门 0，仍然有效） |

## 10.5 回归

后端自测 55 → **79**（§12：拆分组网/接口内容/方向、三条拒绝门、桥的生成与接线、
Kbuild/Makefile 把桥编进去、桥里没有调度原语）。

## 10.6 还没做（下一站）

- **两端一起上板**：现在是"生成完毕"，还没有在 Pi4 上一次跑通 nuttx 端 + root 端，
  用 `--digest-var g_act` 对两侧的值。这是 PR10-D。
- 桥目前只传 **int32**。控制量够用，但结构体/数组要另定帧格式。
- 订阅没有超时/陈旧检测：对端没起来时读到的是初始值，不会报错。

# 11. PR10-D：两端一起上板 —— 跨域闭环跑通，以及一个被算出来但没人看的数

§8.3 的规划器早就算出一个数：跨域闭环的**死区从 200 µs 变成 1400 µs（×7）**。
那一节把它当作"代价变大"的记录，没人问下一个问题：**这个延迟下，回路还稳不稳？**

这一节上板回答了这个问题。

## 11.1 装置

```
Pi4B ｜ jailhouse v0.12-342 ｜ 内核 5.15.86
  cell 0（root）  = CPU 0,2,3    ← root 端：stage_clamp + stage_plant
  cell 1（inmate）= CPU 1        ← NuttX 端：stage_sample + stage_fir + stage_pid
两域之间：PR10 的 IVSHMEM 环（r2i / i2r 各 224 槽）
参考周期 1 kHz（1000 µs）
```

同一份 `five_stage_loop__闭环五阶段示例.c` 拆成两份 `stage_impl.c`（各自编译），
周期体 `ecos_fused_body.c` 两端**逐字节相同**。

## 11.2 跑通了：数据真的过环

NuttX 侧（inmate，只有物理 mini-UART，看得到输出）每 1000 拍报一次：

```
ecos: periods=4000  g_act=1253 g_plant=1066
ecos: periods=5000  g_act=1189 g_plant=1076
ecos: periods=6000  g_act=1014 g_plant=1285
```

root 侧（`/sys/module/five_stage_loop/parameters/`）：

```
periods=5009 g_act=1088 g_plant=821
periods=8025 g_act=687  g_plant=703
```

三条独立证据，说明"环通了"不是错觉：

1. **通向前 `g_plant` 恒为 0**：root 模块还没加载时，NuttX 侧订阅不到任何东西，
   `g_plant=0`（发了 4,024,000 拍都是 0）。root 模块 `insmod` 之后，
   `g_plant` 立刻变成 1066/1076/1285/821/1335… 并且持续在变。
2. **反向也通**：root 侧的 `g_act` 同样在变（1088 → 687），说明 NuttX 发的
   `g_act` 被 root 收到了。
3. **同一个值出现在两侧**：root 侧读到 `g_plant=821` 的那一拍，NuttX 侧
   `periods=7000` 报出的也是 `g_plant=821`。跨域传输的是**同一个数**，
   不是两个各自算出来的相似数。

环本身的可靠性也量了：整个实验期间 **386738 条消息，drops = 0**。

## 11.3 但值在发散 —— 而单域不发散

跑起来之后 `g_act` 不在 1000 附近，而是长到 ±90000：

```
root   14:17:36 g_plant=6332   g_act=-66712
       14:17:39 g_plant=19616  g_act=-73962
nuttx  periods=157000 g_act=-87880 g_plant=-3236
```

先排除"是不是这个回路本来就不稳"。用 §3 的参考模型（与 C 侧逐位相同的整数语义）
跑单域轨迹：

| 拍数 | 单域 g_out | 单域 g_plant |
|---|---|---|
| 100 | 1776 | 1435 |
| 1000 | 1240 | 1147 |
| 10000 | 907 | 1072 |
| 50000 | 1386 | 1062 |

**单域稳定收敛在 1000 附近**（积分项始终在 ±100000 限幅内、没打满）。所以发散
不是 plant 的动力学，是**跨域引入的**。

## 11.4 根因：跨域边让反馈延迟从 1 拍变成 2 拍

把参考模型里"sample 读到的 plant"改成读 k 拍前的值：

| 反馈延迟 | n=100 | n=1000 | n=20000 | 形态 |
|---|---|---|---|---|
| **1 拍**（单域） | g_out=1103 | 446 | 1783 | 稳定在 ~1000 |
| **2 拍**（跨域） | g_out=-1452 | **-42632** | **-39796** | ±60000 振荡、积分打满 |
| 3 拍 | 6479 | 60000 | -17236 | 同样发散 |

**2 拍延迟的形态与板上实测完全同构**（±60000 量级振荡、积分项打到 ±100000 限幅）。

时序上也能对上：

```
单域（一拍一次释放，五个阶段都在同一拍）
  t=0    sample 读 g_plant   ← 上一拍 800µs 写的值，延迟 1 拍
  t=200  fir
  t=400  pid   → g_act
  t=600  clamp → g_out
  t=800  plant → g_plant     ← 下一个 t=0 才被读

跨域（两个 cell 各有内核与调度器，没有共享的"这一拍"）
  NuttX 拍起点(0µs)  sample / fir / pid → 发 g_act
                                      ↓ 过环（≈1 拍，PR10 §3.2 实测 1005 µs）
  root  拍中(600µs)  clamp / plant     → 发 g_plant
                                      ↓ 过环（≈1 拍）
  NuttX 拍起点(0µs)  sample 读到的，是**两拍前**的 g_plant
```

反馈边的延迟 = 原有 1 拍（z⁻¹） + 跨域那 1 拍 = **2 拍**。§8.3 的规划器算的
"死区 200 → 1400 µs"就是这件事（200 + 1000 + 200）。

**这不是 bug，是设计使然**：PR10-B §8.1 已经把"每条跨域边加一整拍"写成了硬约束，
死区按拍计也是这么算的。**缺的从来不是算，是没人拿这个数去问闭环还稳不稳。**

## 11.5 工具链缺的那一扇门

先说清楚**已有的**是什么：`plan_verify.py` 里有一条反馈死区检查（`FEEDBACK_FUSED`），
它判的是"反馈边若并入同一组（= 融合），死区≈一整拍，超过契约上限就报错"。
这条检查本身是对的，但它只覆盖**融合**那一种让死区变大的成因。

而**跨域是另一种成因，它完全没被判**：反馈边跨了组时（`gid_of[a] != gid_of[b]`），
上面那条检查直接跳过——于是"死区因为跨域而翻倍"这件事，在验证器里是**静默**的。

于是链路上出现了一个具体的洞：

- 规划器算出了死区拍数（§8.3 的"死区 200 → 1400 µs"），并写进方案；
- 验证器独立复核了死区拍数（跨域边按拍计那部分），也通过了；
- 但**没有任何一处**拿"死区 = 2 拍"这个数去问"这个延迟下闭环还稳不稳"。

后果是具体的：一条 `xdom_loop` 夹具在单域下是稳定的闭环，
拆到两个 cell 之后就发散，而工具链一路绿灯放行、两个后端都构建成功、
板上也确实在跑——**所有环节都"成功"了，只有一个数不对**。

要补的检验（下一站）：把被控对象 + 控制器 + 反馈延迟做成可分析的形式，
在规划阶段就判"这个跨域拆分会不会让闭环失稳"，失稳就**拒绝拆分**并说清
"延迟从 1 拍变 2 拍，这个夹具在 2 拍下发散"。

判据可以挂在现成的契约字段上（`feedback_delay_max_us`）：反馈边的**总**延迟
（原有拍数 + 跨域带来的拍数）与上限比，超了就报错。

两个实现上的坑（查的时候踩到的）：

1. **反馈延迟的拍数不能把闭合边自己算两遍**。跨域闭合边既带原有的 1 拍，
   又带跨域那 1 拍；环上**别的**跨域边才额外加拍。算重了会得到 3 拍。
2. **`xdom_loop.contract.json` 的字段位置和其他契约不一样**：它把
   `feedback_delay_max_us` 放在**顶层 `control`** 下，而 `plan_verify.py` 与
   `contract_validate.py` 读的都是 `timing_constraints`。所以这个夹具的上限
   **从未被读到过**（其余 7 个契约都在 `timing_constraints` 下）。
   校验器也不报错——它压根没看那个字段。跨域夹具的契约要么挪位置、
   要么校验器认两种位置，这笔账得在实现稳定性门的时候一起结。

注意这不能靠"跑几拍看看"来判——那就退回到实测了。可行的方向是：
对线性化的闭环算离散特征根，或者退一步做"延迟预算 vs 对象时间常数"的
必要条件筛查（这个夹具的对象是一阶 `(3y+u)/4`，时间常数 4 拍，1 拍延迟能稳、
2 拍就压不住）。

## 11.6 踩到的坑（这一版修的）

### 坑 1：NuttX 入口名与 PROGNAME 必须一致（链接期才炸）

NuttX 的 builtin 注册表由 `apps/Make.defs` 的 `REGISTER` 宏**按 app 的 `PROGNAME`
自动生成**，注册项引用的符号固定是 `<PROGNAME 去横线>_main`；同时 `Application.mk`
给 MAINSRC 传 `-Dmain=<PROGNAME 去横线>_main`，把源码里的 `main` 改名成它。

跨域那版把 `PROGNAME` 设成 `fiveloop`（复用板上已打开的
`CONFIG_BENCHMARK_FIVELOOP`）、入口函数却叫 `xdom_main` → 注册表引用
`fiveloop_main`、源码只给 `xdom_main` → 链接期 `undefined reference`。

**第一次构建能过纯属侥幸**：NuttX 的 `libapps.a` 会保留历史成员，上一轮构建的
`fiveloop_main.c.o` 还在归档里顶着这个符号。等到注册表被重新生成、归档被重建，
这个符号消失，缺陷才暴露。

修法：入口名**由 `PROGNAME` 派生**（`--nuttx-progname`），显式给不一致的
`--nuttx-main` 就在**生成期**报 rc=2，不留半成品目录。板上构建脚本也改成
从 Makefile 读回 `PROGNAME`、派生符号、核对源码里的入口名，不一致直接退出。

### 坑 2：改了 `.config` 之后不要并行重建 NuttX

NuttX 的 `.depend` 依赖 `$(TOPDIR)/.config`。改了 `.config`（本例是开机入口）
→ 全树 `.depend` 失效 → `make` 要重跑 `pass1dep`/`pass2dep` 重新生成 `.ddc`。
`-j` 下两个 make 可能在同一目录里互删 `.ddc`，报：

```
cat: mm_initialize.ddc: No such file or directory
make[2]: *** [Makefile:103: makedepfile] Error 1
```

改用 `-j1` 重建依赖、只在链接阶段并行。

### 坑 3：跨域共享内存的映射类型（NuttX 侧读不到 root 写的值）

root 侧原来用 `ioremap()` 映射 IVSHMEM 块 → 那是 device/nGnRE 映射，**内核绕过
cache 直读内存**。而 NuttX 侧的 `up_clean_dcache` 只清到 PoU（L2），数据不一定落到
DRAM。于是现象是：**用户态看得见、内核看不见**（模块里 `xr_in->head` 恒为 0，
而对端明明在发）。

改用 `ioremap_cache()`（与对端 MT_NORMAL 的内存类型一致）后立刻通。

反向也有一条对称的要求：NuttX 侧等待环就绪的循环**必须先失效再读**。
那一侧的映射是 cacheable 的，而 owner 是**另一个 cell**；第一次读若发生在 owner
初始化之前，那一行就带着旧值常驻缓存，之后永远看到"未就绪"（实测等满 30 s 放弃）。

### 坑 4：不要用"periods 在涨"当正确性证据

`periods` 在涨只证明调度在跑。真正证明"算得对"的是：单域用参考模型逐位比对
（`ref_model_five_stage.py --compare`），跨域用**同一个值在两侧都出现**来比对。
§11.2 的第 3 条证据就是后者。

# 12. PR10-E：把"反馈死区"变成一条真的会拒绝的门

§11.5 把洞说清楚了：规划器算出了死区（200 → 1400 µs），验证器也复核了跨域拍数，
但**没有任何一处**拿"死区 = 2 拍"去问"这个延迟还合不合约束"。这一节把它补上。

## 12.1 三个具体的漏判

动手前先把洞拆成三条可验证的，而不是笼统的"缺少稳定性检查"：

1. **上限根本没被读到。** `xdom_loop.contract.json` 把
   `feedback_delay_max_us` 写在**顶层 `control`** 下，而 `TemporalModel` /
   `contract_validate` 读的是 `timing_constraints`。于是这份夹具的反馈上限
   **从未生效**，校验器也不报错——它压根没看那个字段。
2. **验证器只判"融合"，不判"跨域"。** `plan_verify.py` 的反馈死区检查条件是
   `gid_of[a] == gid_of[b]`（反馈边并入同一组）。反馈边跨组时——**跨域恰恰
   就是跨组**——检查直接跳过，死区翻倍这件事在验证器里是静默的。
3. **两套实现。** 死区公式 `(1+xd)*period + t_cons - t_prod` 只存在于
   `fusion_plan__融合规划.py::recurrence_report` 里。验证器没有这份公式，
   自然也就没有判据。上一轮（P0-2）已经吃过一次"算得出的和验得出的不是一个
   定义"的亏，这里是同一类病。

## 12.2 改法：公式只留一份，判据也只留一份

死区计算搬进 `temporal_model.py`（这个项目里"时间语义唯一实现"的地方）：

```python
dead_us = (1 + xd) * period + t_cons - t_prod      # xd = 1 表示跨域
```

- `1` 是闭合边自身的 z⁻¹：生产者相位晚于消费者，一拍之内不可能满足，
  只能等到下一个周期边界；
- `xd` 是跨域附加的那一拍（PR10 实测 1005.26 µs ≈ 1.005 拍）；
- `t_cons - t_prod` 是两者在各自组内偏移之差（含释放代价与执行时间）。

⚠ **两笔不能分开各加一次**。跨域闭合边"既是 z⁻¹ 又是跨域"，但它们在描述
同一个"等到下一个边界"，所以合并成 `(1+xd)`。分开累加会把 2 拍算成 3 拍——
PR10-E 实现时确实先写成了 3 拍，靠"代入夹具应有 1399 µs"才发现。

新增两个接口，规划器与验证器**都调它**：

| 接口 | 作用 |
|---|---|
| `TemporalModel.feedback_delays(groups, dom, sched)` | 给出每条闭合边的总死区 + 来源分解（z⁻¹ 几拍、跨域几拍、生产/消费偏移） |
| `TemporalModel.feedback_violations(...)` | 按契约上限判，返回 `(errors, warnings)` |

`sched` 用统一时间线的**实际开始时刻**（含组间积压），不是名义相位——
被积压推后的组只会让死区更长，用名义相位会低估。

## 12.3 三条新判据

| 诊断码 | 触发条件 | 为什么是**错误**而不是提示 |
|---|---|---|
| `FEEDBACK_DEADZONE` | 反馈边**跨组**且死区 > 契约上限 | 跨域会把死区多加一整拍；超限就没有任何证据说这一步保住了时序语义 |
| `FEEDBACK_CONTRACT_MISSING` | **这条反馈边自己跨域**，但契约没给上限 | 没有上限就无法证明；按 fail-closed 拒。反馈边不跨域（只是方案别处跨 domain）不强行要求——那种情形死区仍是一拍，与单域同构 |
| `FEEDBACK_MODEL_UNPROVEN` | 契约声称 `evidence.exec=bounded` 却没有 `wcet_us` | 只有实测均值却标"已证明"，等于拿经验预测冒充硬实时证明 |

原有的 `FEEDBACK_FUSED`（反馈边并入同组 ⇒ 死区≈一整拍）保留，只是现在
和跨域那一条共用同一个死区公式。

另外把契约校验器改成**拒绝** `control.feedback_delay_max_us` 这个位置，
并明确提示"放错位置等于这条约束不存在"——静默忽略是这次事故的起点。

顺带修掉一句已不准确的提示：原来 `feedback_delay_max_us ≥ period` 时警告
"等于没有限制"。有了 2 拍判据之后这句是错的：它拦不住一拍以内的死区（融合），
但**仍然约束两拍以上的情形**——跨域夹具正是 1400 µs 被 1000 µs 的上限挡住。

## 12.4 为什么用两份契约而不是改一份

`xdom_loop.contract.json` 的 2500 µs 是这个夹具的**应用要求**，不该为了让测试
变红就篡改它。所以：

| 契约 | 反馈上限 | 期限 | 期望 |
|---|---|---|---|
| `xdom_loop.contract.json` | 2500 µs | 2500 µs | 跨域方案**合法**（死区 1400 在内） |
| `xdom_loop_strict.contract.json` | **1000 µs** | 2500 µs | 跨域方案**被拒**（死区 1400 超限） |

两份契约只差反馈上限，其余（DAG、期限、执行时间）完全相同。于是"拒绝"这件事
只能归因于反馈死区，不能赖到期限或域能力上——这也是负向用例该有的形态。

## 12.5 实测（工具链内部，不是板上）

```
宽契约（2500 µs）：规划器 rc=0 ｜ 验证器 rc=0
  闭合边 stage_plant → stage_sample   间隔 200 µs → 1400 µs（×7.00）
  ⚠ 反馈边 stage_plant→stage_sample 死区 1400 µs，跨域 +1 拍（上限 2500 µs）

严契约（1000 µs）：规划器 rc=3 ｜ 验证器 rc=3   ← 同一份方案、同一句理由
  ❌ [FEEDBACK_DEADZONE] 反馈边 stage_plant→stage_sample 跨组（g1 → g0），
     死区 = 2 拍（z⁻¹ 1 拍 ＋ 跨域 1 拍）＝ 1400 µs，超过上限 1000 µs
```

**"规划器和验证器给出同一个结论"是这一节真正要交付的东西**，不是那条 1400。
以前规划器算 1400、验证器不看，两边都"成功"，只有板上发散。

## 12.6 这一节**没有**证明什么

- 死区在上限内 **≠ 控制稳定**。编译器只能证明"满足声明的时间契约"，
  稳定与否要靠被控对象模型独立分析。文档与拒绝消息都写明了这一点。
- 这条门拦的是"反馈延迟超限"，**不是**"回路一定发散"。xdom_loop 在 1400 µs
  下确实发散了（§11.4），但那是这个夹具的对象特性；换个对象，同样 1400 µs
  可能很稳。工具链不该假装知道对象动力学。
- 逐拍数据版本（第 k 拍读到第几拍的数据）还没有。这是 PR10-F。

## 12.8 给下一站的两条限制

**一、时间模型还是单核顺序递推。** `TemporalModel.schedule()` 用的是

```
S_g = max(φ_g, F_{g-1}) + L
F_g = S_g + Σ C_i
```

这个递推对**单域融合**是对的（同一次释放里串行跑），但它描述不了
"Linux 在 CPU 0,2,3、NuttX 在 CPU 1 **同时**执行"这件事。所以 PR11-B 不能
只是给这个公式加一个通信常数——那等于假设两个域仍然串行。要建的是
**多执行域事件图**：每个域各自约束 CPU 占用，跨域依赖单独约束
"生产完成 → 通信可用 → 目标消费"三个时刻。

本节新增的 `feedback_delays` 之所以要 `sched` 参数代入而不是自己再算一遍，
就是为了将来换成多域时间线时，死区判据能**自动跟着换**，不用改两处。

**二、PR10-F 的两个已知缺陷（还没修）。** 逐拍数据版本要动 IPC 协议之前，
先把这两条记下来：

- `xdom_bridge.py` 生成的订阅循环返回的是**第一条**匹配消息，不是注释写的
  "最近一条"——注释与实现不符。
- 多个通道共用一个接收环时，为找 A 通道可能在遍历中把 B 通道的消息**消费掉**
  （`xipc_pop` 是出队）。环通的实验里没暴露，是因为这个夹具两通道各用一条环。
  正确做法是"每拍先统一排空、按通道更新本地缓存；阶段消费时只查缓存"，
  而不是在共享环上直接找。

> ⚠ 上面两条已在 **§13（PR10-F）** 修复：订阅改成按通道分桶缓存、取最近一条；
> 版本化协议也一并做了（release_id / session_id / publish_tick 三个标识各归其位）。
> 另外 Linux emitter 的 `pending` 裸 bool 仍未替换——那是 PR10-F 之后、
> 严格周期配对实验（PR11-A）之前要做的前置，见 §13.7。

# 13. PR10-F：版本化跨域 IPC —— 三个标识各归其位，订阅不再吞通道

§12.8 记了两条待修缺陷，这一节把它们落地，并把"逐拍追踪"需要的版本化字段补齐。
改动集中在三个文件：`kfusion/runtime/xshm/ecos_xipc.h`（协议与环）、
`kfusion/backend/synthesis/xdom_bridge.py`（生成的桥）、两个宿主发射器
（`linux_kernel_emitter.py` / `nuttx_emitter.py`）。

## 13.1 三个标识必须分清（不是"三个字段"）

审查指出：把环槽 `seq` 叫 `release_id` 不严谨——一个周期发两条、或某周期不发，
`seq` 就和"第几拍"对不上。修正后的口径：

| 概念 | 落点 | 说明 |
|------|------|------|
| **消息序号** | 环槽 `seq` | 每提交一条 +1，随 session 复位。只回答"第几条消息"，**不是**释放编号。 |
| **会话/轮次** | 环头 `session` | owner 用 `xipc_counter()` 生成。相同 session 只说明"同一轮实验"，**不代表两域第 N 拍在物理时间上对齐**。 |
| **生产周期** | 环槽 `tick` | `publish_tick = xipc_counter() / period_ticks`，由**共享物理计数器**派生，与启动相位无关。 |
| **消费周期** | 运行时 `ecos_xdom_cycle_now()` | 同口径：同一物理时刻两侧算出同一个周期号。 |
| **数据年龄** | `age = consumer_cycle − publish_tick` | 真实时间差（拍），不含"各自 init 起算"的偏移。 |

> ⚠ **修订（回应审查问题 1/2）**：PR10-F 初稿曾用宿主 `ecos_xdom_cycle = periods`
> 当 `publish_tick`。但 `periods` 从各自域 init 起算 ⇒ 两侧周期零点不同，`age` 会
> 掺进启动相位偏移，不能当真实数据年龄。现改为**共享物理计数器派生**
> （`xipc_counter() / (period_us × CNTFRQ / 1e6)`）：两侧同一物理时刻算出的周期号相同，
> `age` 才是真实时间差。`ecos_xdom_cycle` 全局已删除，宿主不再喂周期号。

## 13.2 扩槽：16 → 20 字节，协议版本 1 → 2

旧槽只有 `seq/kind/a/b`（16 B），放不下 `tick`。改动：

- `XIPC_VERSION` 1 → 2（HELLO 携带的协议号同步变，两侧必须同时重编——本来就共用同一份头）。
- 槽加 `volatile uint32_t tick;`，`XIPC_SLOT_BYTES` 16 → 20。
- 容量约束从"一个环 ≤ 4096"放宽到"≤ peer 片 `XIPC_PEER_STRIDE`（0x3000）"。
  224 槽 × 20 B + 256 B 头 = 4736 B ≤ 12288，**槽数 224 不变**，控制回路的环容量一点没降。
- 新增 `xipc_pub_ticked(r, kind, a, b, tick)`；旧 4 参 `xipc_pub` 保留（管理消息 `tick=0`），
  所以 `root_side.c` 与 `xipc_main.c` 这一版**不用改**。

## 13.3 多通道消费 bug：改成按通道分桶缓存、取最近一条

旧 `ecos_xdom_sub`（PR10-C）是

```c
while (xipc_pop(xr_in, &s)) {
    if (s.kind == XIPC_KIND_DATA && s.a == channel) { *dst = s.b; break; }
}
```

两个毛病（§12.8 已点名）：

1. 返回的是 **FIFO 最旧**匹配消息，不是注释写的"最近一条"——同通道连发两次只会拿到第一次的。
2. 为找本通道，可能把**别的通道**排在它前面的消息 `pop` 掉并丢弃（消费即出队）。
   只要某周期 A 通道消息前恰好排了 B 通道消息，且 `sub(A)` 先于 `sub(B)` 执行，B 就丢失。

新实现：每个域一份**按通道分桶的本地缓存**，一次 `sub` 调用把 in 环**抽干**到各桶
（最近一条覆盖旧的），再从自己的桶取。这样 `sub(A)` 不会饿死 `sub(B)`，且取到的是
本通道最新值。新增 `ecos_xdom_sub_tick(channel, &v, &tick)` 顺带把 `publish_tick` 带出，
供宿主做按拍追踪。

> PC 端无 C 编译器，这份新语义用 `kfusion/scripts/test/xipc_versioned_model.py`
> 纯 Python 复刻并断言（§32 融进融合自测）；该模型也**复现了旧桥的两个 bug**，
> 证明修复不是空谈。板上编译验证见 §13.7。

## 13.4 跨域按拍追踪 + 逐拍证据

- **生产**：`ecos_xdom_pub` 在发布时算 `publish_tick = xipc_counter() / period_ticks`
  （`period_ticks = period_us × CNTFRQ / 1e6`，init 时算好），戳进消息 `tick`。
- **消费**：`ecos_xdom_sub_tick` 取回值 v 与 `publish_tick`；同时用
  `ecos_xdom_cycle_now()`（同口径）算 `consumer_cycle`，得
  `age = consumer_cycle − publish_tick`。
- **证据记录**：每通道记 `struct ecos_xdom_evid{prod, cons, age, n, n_stale, max_age}`，
  每次 sub 更新；`ecos_xdom_evidence()` 读、`ecos_xdom_report_evidence()` 逐通道打印。
  NuttX 宿主在周期上报里调用它，把逐拍 `prod/cons/age` 打到串口（root 侧有 sysfs）。
- **过期拒收（可选）**：`ECOS_XDOM_MAX_AGE > 0` 时，`age` 超上限的版本**不更新 dst**
  （阶段沿用上一次/默认值），并计 `n_stale`——拒绝要看得见，不能静默。默认 0 = 只记录不拒。

因为 tick 与 consumer_cycle 都来自**共享物理计数器**，`age` 天然包含 PR10-D/PR10-E
论证的"z⁻¹ 一拍 + 跨域一拍"，且**不受两域启动相位差污染**。宿主不再写任何周期号，
`ecos_xdom_cycle` 全局已删除。

## 13.5 epoch（session）与周期对齐是两件事

`session` 由 `xipc_counter()` 生成，Jailhouse 不陷获/偏移 `CNTPCT`/`CNTVCT`，两侧读
同一个物理计数器（§4 已 grep 确认），所以 `session` 是**同一轮实验**的标识——这部分成立。
但 ⚠ **session 相同 ≠ 两域第 N 拍在物理时间上对齐**：Linux 用 `ktime_get()`、NuttX 用
`clock_gettime()` 各自取启动基准，周期零点可差一个任意相位。真正保证"拍号可比"的是
§13.4 的**绝对周期号**（共享计数器派生），不是 session。`ecos_xdom_epoch()` 只用来核对
"是不是同一轮"，不能拿它当时间对齐依据（这是审查问题 1 的直接修正）。

## 13.6 这一节**没有**证明什么

- 桥的 C **已在 Pi 上 `gcc -O2 -Wall -Wextra` 编译通过**；但完整融合模块 / 完整 fused
  app **尚未上板跑**，`sub_tick` 的运行时逐拍证据仍待 §13.7 的完整闭环实验。
- 协议版本升到 2，意味着 root cell 与 inmate 必须**同时**用新头重编；旧 v1 镜像与新 v2
  镜像混跑会因槽布局不一致而数据错乱。上板前要把 `ecos_xipc.h` 同步到 NuttX 侧并整编。
- 同 §12.6：版本化只证明"携带并核对了时间标识"，**不等于**控制稳定。

## 13.8 PR11-A 前置：宿主释放从裸 bool 换成原子计数（已做）

```

xdom ch1 prod=50942104 cons=50942104 age=0 n=1001  stale=0 max=1
xdom ch1 prod=50943104 cons=50943104 age=0 n=2001  stale=0 max=1
...
（连续 39 条，n 到 39001，stale=0，max=1）
```

- 年龄是**整拍分辨率**（1 拍 = 1000 µs）；`age=0` 表示"同一墙钟周期内、<1 拍"，

- 本次**没开** `--digest-var`，没同时记录 `g_plant/g_act` 的值，所以**不能**用年龄直接
  断言回路收敛或发散。要接上 PR10-D 的"发散"结论，下一跑应加值摘要，做"年龄 vs 值漂移"
  的对照——这是紧接着该做的事。

  变量：① 新桥把订阅从"FIFO 最旧"改成"最近一条"（有效延迟变小）；② 两跑的实际相位/起动
  时机不同。要归因，必须做**受控 A/B**（同一编译、只切"最旧/最近"和相位之一）。
- 因此 §13.9/§13.10 证明的是"**逐拍证据链 + 有界运行**"，不是"某机制导致稳定"。

## 13.11 受控 A/B：注入数据年龄 ⇒ 复现发散（把"年龄"和"发散"钉成因果）

§13.10 只证明了"有界 + age 0–1"，没证明**是年龄导致有界**。这一节做受控 A/B：**同一份
生成代码**，只切桥的编译期 `ECOS_XDOM_LAG`（消费者取"LAG 拍前"的值），plan/相位/构建/装置
全部相同。

| 臂 | LAG | 实测 age（max） | g_plant 范围 | g_act 范围 | 结论 |
|----|-----|----------------|--------------|------------|------|
| A | 0 | 0–1（1） | 874…1546 | 267…1541 | **有界** |
| B | 2 | 2–3（3） | −44993…53046 | −98870…87134 | **发散（±9e4）** |

B 臂值轨迹（NuttX 串口，每 1000 拍）：

```
periods=1000 g_plant=0      g_act=14606     ← insmod 前
periods=5000 g_plant=-44993 g_act=-7634
periods=7000 g_plant=-21766 g_act=-75436
periods=9000 g_plant=25054  g_act=-98870    ← 已到 PR10-D 的量级
periods=13000 g_plant=42880 g_act=23114
...
periods=30009（末值，sysfs）g_plant=35057 g_act=-80771
```

结论（因果，不是相关）：

- **实测 `age` 正确跟随注入的 LAG**：LAG=0→age 0–1；LAG=2→age 2–3 ⇒ **age 指标可信**，
  它测到的确实是"这条数据比本拍老了几拍"。
- **数据年龄 2–3 拍 ⇒ 回路发散；0–1 拍 ⇒ 有界**。B 臂的 ±9e4 与 PR10-D 的"发散到 ±90000"
  是同一现象——这是把"年龄"与"发散"钉成因果的那次实验。
- ⇒ 反过来说：PR10-F 让订阅取**最近一条**（age 0–1）是本轮能保持有界的必要条件之一。

边界（不越界）：

- 这**不**证明"取最近一条 ⇒ 稳定"是**唯一**原因。A/B 两臂都用新桥、只切 LAG，它证明的是
  "**年龄是原因**"。PR10-D 当年为何 age≈2（旧桥"取最旧"？相位？）仍可另做 A/B 拆这两个
  来源；但"age=2 ⇒ 发散"这一环已实证。
- LAG=2 是在自然 0–1 之上**再加** 2，故总 age 2–3，略大于 2；不是"精确 2 拍"。
- 值轨迹是**每 1000 拍**采样的，发散的高频细节没全捕获；但量级（1e5 vs 1e3）与 age 的对应
  足够清楚。

## 13.12 剂量-反应：发散阈值在"多 1 拍"，相位协调够不到（PR11-A 前提要改）

§13.11 只测了 LAG=0 与 LAG=2 两点。补 LAG=1 得完整曲线（同代码、同装置，只切 LAG）：

| LAG | 实测 age | g_plant | g_act | 回路 |
|-----|---------|---------|-------|------|
| 0 | 0–1 | 874…1546 | 267…1541 | **有界** |
| 1 | 1–2 | −45951…31197 | −74774…77483 | **发散** |
| 2 | 2–3 | −44993…53046 | −98870…87134 | **发散** |

**结论：回路只在 age 0–1 有界；多 1 拍（age 1–2）即发散——几乎没有延迟裕度。**

两个直接推论（都修正了 PR11-A 的前提）：

1. **PR10-D 的发散最可能就是这个机制**：旧桥"取最旧"，环形一旦有 >1 条积压，age 就从 0–1
   升到 1–2 以上 ⇒ 跨过阈值 ⇒ 发散。PR10-F 改成"取最近一条"把 age 压回 0–1，是本轮有界的
   必要条件（这个对象上实测也够用）。
   ⚠ 这一条没在**旧桥**上直接量 age（那要再编一个"取最旧"臂）；但与本 A/B 的阈值完全吻合。
   ⚠⚠ **已推翻（§13.13）**：直接量了。"取最旧"臂实测 age 仍是 0–1、回路**有界**——
   因为本夹具生产者:消费者严格 1:1，环里永远只有 ≤1 条消息，三种取数语义**等价**。
   所以 PR10-D 的病因**不是**取数语义；能让 age 抬到 1–2 的是"消费者比生产者慢"（积压）
   或人为延迟（LAG），不是"同一批里挑哪条"。
2. **相位协调（PR11-A 原义）救不了这个发散**：1:1 节奏下消费者每拍都读最新，子周期相位只能
   把 age 在 0↔1 之间翻，**推不到 1–2**。所以"用相位协调恢复一拍反馈"在这里不成立。
   PR11-A 应对准"**保证 age ≤ 1 的契约/调度**"（例如环形积压时强制丢弃旧消息、把 age 钉在
   0–1），而不是调相位。

诚实的边界：

- 阈值是"1 拍"还是"1.x 拍"未细测（LAG 只能整拍）；已知 0–1 稳、1–2 散。
- 值轨迹每 1000 拍采样，发散高频细节未全捕；量级（1e3 vs 1e4~）足够清楚。
- LAG 是"数据侧人为延迟"，与"相位/起动时机"不是一回事；正因相位够不到 1–2，才说相位不是
  这里的杠杆。

# 14. PR11-A：把"数据年龄 ≤ 1 拍"做成契约，并直接量 PR10-D 的病因（负结果）

§13.12 里"PR10-D 发散来自旧桥取最旧"是**推断**（靠阈值吻合）。PR11-A 要两件事：
把年龄预算变成**契约 + 运行时强制**，以及**直接量**那条推断。结论先说：
**推断被推翻**——取数语义在本夹具里根本不构成差异；而预算虽然生效，但**救不回**回路。

## 14.1 契约：一处声明、一处强制

| 位置 | 作用 |
|------|------|
| 契约 `timing_constraints.xdom_max_age_ticks` | **声明**"这个部署允许的数据年龄上限（拍）" |
| 生成代码 `ECOS_XDOM_MAX_AGE` | **强制**：`age > 预算` 时拒收该版本（不更新 dst）并计 `n_stale` |
| 证据 `stale` / `max`（串口、`ecos_xdom_evidence`） | **可观测**：拒了多少、见过多大年龄 |

`emit` 从契约读预算；命令行 `--xdom-max-age` 只允许**核对一致**，不一致 rc=2
（与 `cost_model` 同一套规矩：声明与生成不能各说一套）。契约校验补三条硬规则：
预算写在顶层 `control` 下判**错**（PR10-E 就是这么静默失效的）、`< 1` 判**错**
（0 拍等于要求零延迟）、`≥ 2` 给**告警**（实测 1–2 拍已经发散）。

夹具：`xdom_loop.contract.json` 与 `xdom_loop_strict.contract.json` **都加** `= 1`，
保持"两份只差 `feedback_delay_max_us`"这条不变量；另存
`xdom_loop_nobudget.contract.json`（只缺这一个字段）供 A/B 的"无预算"臂使用。

## 14.2 三条取数语义臂（同一份代码只切 `ECOS_XDOM_PICK`）

旧桥的行为其实是**两件事**，之前混在一起说：

- **选择顺序**：`while(pop){ if(匹配) break; }` ⇒ 同一批里拿到**最旧**那条。 → `PICK=1`
- **消费速率**：那个 `break` 之后剩下的消息**留在环里**，每拍只消化一条。 → `PICK=2`
- 修正后的行为：每拍把环**抽干**、每通道留**最新**一条。 → `PICK=0`（默认）

## 14.3 板上四臂（同一 plan / 相位 / 构建 / 装置）

| 臂 | PICK | LAG | 预算 | age（max） | stale | g_plant | g_act | 判定 |
|----|------|-----|------|-----------|-------|---------|-------|------|
| C  | 0 latest | 0 | 1 | 0–1（1） | 0 | 617…1335 | 405…1541 | **有界** |
| O1 | 1 oldest | 0 | 无 | 0–1（1） | 0 | 677…1335 | 405…1541 | **有界** |
| O2 | 2 one    | 0 | 无 | 0–1（1） | 0 | 655…1335 | 846…1541 | **有界** |
| G  | 0 latest | 1 | 1 | 1–2（2） | **24824 / 42998** | 14387 冻结 → −60000 | **134928** | **发散** |

（`n` 与 `periods` 在 C/O1/O2 三臂都严格 1:1，例如 O2：`n=42997` @ 42997 拍。）

## 14.4 三个结论

**① 负结果：取数语义不是 PR10-D 的病因。**
O1 复刻"取最旧"、O2 复刻"每拍只取一条"，两臂 age 都是 0–1、回路都有界，与对照 C 无差别。
原因很硬：本夹具生产者:消费者 **1:1**，环里永远只有 ≤1 条消息 ⇒ "同一批里挑哪条"和
"这拍消化多少"都**无事可做**，三种语义退化成同一件事。
⇒ §13.12 那条推断推翻。"取最旧把 age 抬一拍"这句话在 1:1 下不成立。

**② 预算真的生效，而且看得见。**
G 臂（人为注入 1 拍延迟 + 预算 1）里 `stale=24824/42998`：过半样本被拒，`g_plant` 被
**冻在 14387** 几千拍（拒收 = 不更新 dst）。这是"违规可见"而非"违规被修好"。

**③ 但拒收救不回回路。**
同一 G 臂最终还是发散到 `g_act=134928`——比不设预算的 LAG=1 臂（±7.7e4）更差。
原因直白：**"拒收"= 保持旧值 = 又一种延迟/错配**。所以运行时年龄预算只能当
**可观测性 + 失效保护**（宁可不出数，也不把已知过期值喂进控制律），
**不能当成"跨过阈值之后的修复手段"**。真正的保证必须**事前**成立：

> 要么让消费速率不低于生产速率（不积压），要么把降采样显式建模，
> 而不是等到 age>1 再拒。

## 14.5 这一节把问题定位到哪

能推高 age 的**充分条件**只有两条：① 消费者比生产者慢 ⇒ 环积压 ⇒ age 单调上升；
② 人为/结构延迟（LAG、多级 z⁻¹）。"挑哪条"不推高 age。
⇒ PR10-D 要在 1:1 下发散，其装置必然在**速率或相位**上与本次不同；这正好是多速率
场景（1 ms vs 2 ms）要回答的事——那里消费者天生比生产者慢，积压是结构性的，
PR11-A 的"保证 age ≤ 1"才有非平凡内容。

诚实的边界：

- 只测整拍；三臂都在同一 plan / 相位 / 温度 / 镜像下，一次开机内完成。
- PR10-D 当年的周期、相位、应用代码已无法完整复原，所以这里只能**否定**"取数语义"
  这一条，**不能**断言 PR10-D 的真正病因。
- G 臂的 `stale` 计数含"第一拍还没数据"的样本（n 从 0 起算），比例是量级参考，不是精确率。

# 15. PR11-B：多速率（1 ms / 2 ms）+ 相位 A/B —— 相位第一次有非平凡作用

## 15.1 前置：v2 的 `tick` 在多速率下是垃圾，必须先换成 µs

v2 的 `publish_tick = counter / period_ticks`，**period 是本域周期**。多速率下两侧周期不同
⇒ 两个"第几拍"不是同一量纲，`age = cons − prod` 会随周期比缩放（1 ms vs 2 ms 就差 2 倍），
根本不是时间。所以 v3 把槽里那个字段改成**绝对时间戳**：

```
ts_us = xipc_counter() * 1000000 / CNTFRQ      /* 共享计数器 → µs，32 位 ≈ 71 min 回绕 */
age_us = now_us − ts_us                        /* 与两侧速率、相位都无关 */
age(拍) = age_us / ECOS_XDOM_PERIOD_US         /* 要"几拍"再除以**本域**周期 */
```

`XIPC_VERSION` 2 → 3（字段含义变了，两端必须同头重编）。证据打印同时给
`age_us` 与 `age`，`MAX_AGE` 判据仍按**本域的拍**（因为"几拍"才是控制语义）。

## 15.2 装置开关：不绕过验证，但要能换部署

多速率不可能靠改契约实现——契约是**已验证**的那一份，改它等于让验证结论失效。所以加了
两个**显式**的实验开关，规矩与 `--allow-unverified` 一致：

| 开关 | 作用 |
|------|------|
| `--experiment-period-us N` | 覆盖本域周期（如 root 2000） |
| `--experiment-shift-us N` | 把每个组相位整体平移 N µs（按周期取模），用于相位 A/B |
| `--allow-experiment-deploy` | **必须**同时给，否则 rc=2 |

产物里写 `EXPERIMENT.txt`：**"装备实验产物 —— 不得用于论文主张"**，并列出偏离项。
理由写在文件里：合法性的唯一凭据是 `ecos/plan_verify.py`，不是"它跑起来了"。

## 15.3 结果（同一方案、同一镜像流程，只改装置参数）

装置：nuttx（控制：sample+fir+pid）**1 ms**；root（执行器+plant：clamp+plant）**2 ms**。

| 臂 | root 相位 | 稳态 `age_us` | age（拍） | max | stale | g_plant | g_act | 判定 |
|----|-----------|---------------|-----------|-----|-------|---------|-------|------|
| M0 | 600 µs | **1083…1254** | 1 | 2 | 48 / 42998 | 1098…1388 | 538…1456 | 有界 |
| M1 | 1600 µs | **152…326** | 0 | 2 | 62 / 42997 | 1070…1384 | 639…1321 | 有界 |

两臂 `root periods=14004`（28 s ÷ 2 ms）、`missed=0`；nuttx 侧 `n≈42998`（每 1 ms 消费一次，
而 root 每 2 ms 才发一条，所以**同一消息被用两次**——这正是多速率的常态）。

## 15.4 三个结论

**① ⚠ 已撤回（§16.4）：M0/M1 的 age_us 差不能归因于相位。**
当时的读法是"平移 1000 µs ⇒ age_us 掉一个相位步长"。**这是错的**：`P_p = 2·P_c` 时年龄
只在 `{a, a+P_c}` 两个值之间**交替**，而证据是每 1000 拍打一次——两臂各自只命中了**不同
的奇偶**。集合 `{254,1254}` 与 `{326,1326}` 的差是"打印到哪个奇偶"，不是相位效应。
仪器缺陷（只打"最近一次"）已修：证据现在同时给 `min_us`/`max_us`（§16.1）。

**② 相位在多速率下确实是杠杆，但它改的是 age_us，不一定改 age(拍)。**
两臂 age(拍) 都 ≤ 预算，所以都没发散。相位决定"这一拍读到的是同一拍还是上一拍的
数据"，在 1 ms 的控制口径下，1000 µs 的相位差正好落在"0 拍 ↔ 1 拍"的边界上——
这也解释了 §14 里"相位看起来没用"：那是 1:1 同速率，相位只能在同一拍内滑动。
⚠ 严格版见 §16：真正决定 age 的是**两域网格的相对偏移 ρ**，且 `ρ mod P_c` 就决定了
年龄集合——所以"相位"这个词必须落到 ρ 上才有意义。

**③ 两宿主的节拍在**漂**。** M0 臂的稳态 `age_us` 在同一跑里从 1254 单调降到 1083
（约 11 s 掉 171 µs ≈ **15 ppm**），M1 也一样（326→152）。两侧共用同一颗晶振、`CNTFRQ` 相同，
所以漂的不是计数器，而是**两个宿主各自"什么时候真正跑到周期体"**（hrtimer vs 绝对时刻睡眠）。
⇒ 编译期钉死的相位**不会长期成立**：要么周期性重同步，要么把相位差当成有界量来设计。
这一条直接影响 LET/相位协调的可实现性。

## 15.5 边界

- M0/M1 是**装置实验**（`--experiment-*` + `EXPERIMENT.txt`），没有过 `plan_verify`，
  不得作为"多速率部署合法"的主张。合法性的证明需要多执行域事件时间线，
  `TemporalModel` 目前仍是单核串行模型（外部审查已指出这一点）。
- 两域各自的绝对起点不可控（各自 init 时刻不同），所以 M0→M1 有意义的是**相对偏移的差
  = 1000 µs**，不是"绝对相位 600/1600"。
- `age(拍)` 用**本域**周期折算，跨速率直接比"拍数"没有意义，要比 µs。
- 回路两臂都只是"不发散"，不是"跟踪得好"（`g_act` 仍有 ±1e3 幅度摆动）。

# 16. PR11-C：多执行域事件时间线 —— 模型第一次把板上的 age 算准

§15 的读数被仪器坑了（只打"最近一次"，多速率下撞上奇偶混叠）。这一节做三件事：
把仪器修到看得见结构、建一个**多执行域事件时间线**模型（外部审查点名缺的那块）、
用它**预测**并把板上量到的数对上。

## 16.1 先修仪器：三个必须打出来的量

| 量 | 为什么必须有 |
|----|-------------|
| 每窗口 `min_us` / `max_us` | 多速率下 age 在**几个值之间交替**，只打最近一次会撞奇偶混叠（§15 就栽在这） |
| `xdom init t0_us` | 每域的初始化时刻（诊断用） |
| `xdom anchor`（**首拍真正跑起来的时刻**） | 算两域相对偏移 ρ 的唯一可用锚点 |

⚠⚠ **`init` 时刻 ≠ 周期零点**。root 侧实测：`init t0_us=106678251`、
`anchor now_us=106679119`，**差 868 µs**（init 之后还要建线程、起 hrtimer）。
用 init 去算 ρ 会直接错 868 µs。这和 PR10-F 栽过的"各自 init 起算"是同一个坑，
所以这次把锚点单独打出来、并且在自测里守住（`xdom anchor` 断言）。

窗口 min/max 打完就重置——否则整跑累计会被启动瞬态（第一条数据 age≈1 µs）
和 ρ 的缓慢漂移一起撑满，看不出"成对出现"这个结构。

## 16.2 模型：`kfusion/scripts/ecos/xdom_timeline.py`

两个**独立**事件网格（不是单核串行时间线）：

```
生产域：t_p(m) = t0_p + φ_p + m·P_p      样本在 exec_p 之后才可见
消费域：t_c(k) = t0_c + φ_c + k·P_c
age(k)  = t_c(k) − t_p(m*)，m* = 此刻已就绪的最新（抽干取最新）/最旧/未消化的一条
```

三个用法：

1. `simulate(pick=latest|oldest|one)`：逐拍环模拟。**环空时沿用上一次的值**
   （桥只在有数据时写 dst）——漏掉这些拍会把年龄低估，而"消费者比生产者快"的
   稳态恰恰一半是这种拍。
2. `age_band()`：把年龄序列压成"区间 + 去重值集合"。
3. `safe_phase_window()`：扫 ρ ∈ [0, lcm(P_p,P_c))，问**哪些 ρ 的最坏年龄 ≤ 预算**。

关键结论（可解析）：`P_p = k·P_c` 时年龄只能取 `{a, a+P_c, …, a+(k−1)P_c}` 这 k 个值，
其中 **`a = ρ mod P_c`**。所以：

> 决定跨域年龄的是**两域网格的相对偏移 ρ**，不是某一个域的相位；
> 而且 k 个值成对出现——这就是 §15 那个"差 928 µs"的真身（打印命中不同奇偶）。

## 16.3 板上验证（nuttx 控制 1 ms / root 执行器+plant 2 ms）

一次开机内取到：

```
root  xdom init   t0_us=106678251  period_us=2000
root  xdom anchor now_us=106679119  period_us=2000     ← 首拍
nuttx xdom anchor now_us=103676251  period_us=1000     ← 首拍
```

`ρ = (anchor_c − anchor_p) mod P_c = (103676251 − 106679119) mod 1000 = 132 µs`

| | 数值 |
|---|---|
| 模型预测年龄集合 | `{132, 1132}` µs |
| 实测每窗口 `min_us` | 84 … 114 |
| 实测每窗口 `max_us` | 1157 … 1210 |
| 实测 `max−min` | 1066 … 1096（预测 1000，差的是抖动） |
| 预测中点 632 vs 实测中点 648 | 差 < 20 µs |

⇒ **模型第一次把板上量到的年龄算准了**（残差 ≈ 抖动，量级 40 µs）。
这比"和某个阈值吻合"强一档：它给出的是**数值预测**，不是区间自洽。

顺带量到 ρ 自己在走：窗口带宽从 1136 单调降到 1095（3000 拍 = 3 s 掉 41 µs）
⇒ **≈13.7 ppm**，与 §15 独立估的 15 ppm 同量级。两域共用一颗晶振、`CNTFRQ` 相同，
所以漂的不是计数器，而是**两个宿主"何时真正跑到周期体"**。

## 16.4 §15.4 ① 撤回

原写法："只把 root 相位平移 1000 µs，age_us 就从 ~1.2 ms 掉到 ~0.3 ms ⇒ 时间戳自证正确"。
**撤回**：那是奇偶混叠。§16.2 给出正确读法，§16.3 用 ρ 与数值预测重新做了这件事
（时间戳仍然是对的，但理由必须换成"ρ 与预测集合对得上"）。

## 16.5 硬结论：有些速率组合**根本没有安全相位**

用 `safe_phase_window()` 扫（预算按控制拍折算）：

| 速率组合（生产/消费） | 预算 | 安全相位窗总宽 |
|---|---|---|
| 2000 / 1000 | 1 拍（1000 µs） | **0 / 2000 µs（0%）**，只剩两个孤立点 |
| 2000 / 1000 + **15 ppm 漂移** | 1 拍 | **空集** |
| 2000 / 1000 | 2 拍（2000 µs） | 1997 / 2000（≈100%） |
| 1000 / 1000 | 1 拍 | 999 / 1000（≈100%） |

读法：

- **"执行器 2 ms + 控制 1 ms，且要求数据年龄 ≤ 1 控制拍"这个部署，在相位上不可实现**
  ——除非运气好到 ρ 恰好等于 0（测度零），而 ρ 还在以 ~14 ppm 走。
- 编译器该做的事因此很清楚：**事前**判"这个速率组合在预算内没有安全相位"就拒（或要求改速率），
  而不是生成代码然后在运行时靠拒收兜底——§14 已经实证**拒收救不回**（拒收=保持旧值=又一种延迟）。
- 1:1 同速率为什么"相位没用"也在这里有了答案：安全窗本来就是 100%，调相位不改变任何事。

## 16.6 这个模型没有替代什么（边界）

- **不是** `plan_verify` 的替代，也不判断控制稳定。它只算"事件时间线上的数据年龄"。
- 抖动没有建模：模型是确定性的，实测残差 ≈40 µs 就是抖动。要写成界，得给抖动一个上界
  并把它加进 `budget`（`safe_phase_window` 现在没做这件事）。
- ~~目前只覆盖一条跨域边、整数倍速率比~~ —— **非整数比已由 §22 处理**（模型本就按事件网格
  模拟，扫 ρ 的 horizon 用 lcm，非整数比只是 lcm 变大）。
- ρ 的可观测性依赖 `xdom anchor` 那一行；锚点本身有 ±几十 µs 抖动，
  所以 ρ 的精度也就是这个量级——判"窗口是否为空集"够用，判"差 10 µs"不够。

# 17. PR11-C 判据入门：排不出安全相位，就不许生成

§16 只把"安全相位窗"算了出来，但那是**报告**；这一节把它变成**门**。
合起来是一条完整的判据链：

> 发现问题（§13.11 注入延迟 ⇒ 发散）→ 建立约束（§14 年龄预算）→ 观测（§13.9/16.3）→
> **事前拒绝**（§17：事件时间线上的安全相位窗不存在就不生成）

## 17.1 判据是什么、判在哪

| 位置 | 判什么 | 不通过 |
|------|--------|--------|
| `xdom_timeline.check_edge(P_p, P_c, budget_us, drift)` | 单条跨域边：安全相位窗**为空**或**总宽 0（只有孤立点）** | 判不可行 |
| `xdom_timeline.check_contract(dag, contract)` | 从 DAG 找跨域边 × 契约域周期 × 预算 | 返回 errs |
| `contract_validate`（`ecos_build.sh` 第一道门） | 契约层：结构 + 部署可行性 | **rc=3** |
| `emit.py`（生成层） | 用**最终**节拍复判（含 `--experiment-*` 覆盖），**双向**都看 | **rc=3** |

两条附带规则（都是踩过的坑）：

- **有跨域边却没声明 `xdom_max_age_ticks` ⇒ fail-closed**。"预算无穷大"等于没有约束，
  判据无从判起——和 PR10-E 的 `FEEDBACK_CONTRACT_MISSING` 同一个立场。
- **契约声明即实现**：`timing_constraints.domain_period_us[域]` 现在会真的落到生成代码
  （`ECOS_XDOM_PERIOD_US`、宿主的 `period_us`）。之前契约说 root=2000、生成的仍是 plan 的
  1000——那样的判据其实在算一个**不存在的部署**。与 `--experiment-period-us` 冲突时 rc=2。

## 17.2 为什么必须双向看

`P_p` 与 `P_c` 互换后可行性**完全不同**：

- 快生产 + 慢消费（2 ms 执行器 → 1 ms 控制）：age 只能在 `{a, a+P_c}` 摆动 ⇒ 预算 1 拍时窗为空。
- 慢生产 + 快消费（1 ms 生产 → 2 ms 消费）：消费者每拍都能拿到"新得多的"数据 ⇒ 安全。

只判"我消费谁"，会漏掉"谁消费我"——而站在 root 侧看，出问题的恰恰是后者。
所以 `emit` 对 `subscribe`（我是消费者）与 `publish`（我是生产者）**两个方向都判**。

## 17.3 判据效果（自测里固化的六种情形）

| 情形 | 结果 |
|------|------|
| 1:1，预算 1 拍 | 通过（窗 999/1000 µs ≈100%） |
| 2 ms / 1 ms，预算 1 拍，drift 15 ppm | **拒绝**：窗为空 |
| 2 ms / 1 ms，预算 1 拍，drift 0 | **拒绝**：窗总宽 0（只有两个孤立点，测度零） |
| 2 ms / 1 ms，预算 **2 拍** | 通过（窗 1997/2000 µs） |
| 有跨域边但没预算 | **拒绝**（fail-closed） |
| 装置开关把周期改成 2000 也照样判 | 与被判据约束（实验口子不是暗道） |

拒绝文案会给三条出路，并明说"这不是跑起来才知道的事"：

```
❌ 跨域部署不可行：本域(2000 µs) → nuttx(1000 µs)，预算 1 拍，漂移 15 ppm
   ⇒ 无任何安全相位（预算 1000 µs 内排不出）
   → ① 放宽 xdom_max_age_ticks  ② 让两域同速率  ③ 窗宽 0 时调相位没用
```

## 17.4 放行之后真的能跑（板上验证，2026-10-27）

用 `xdom_loop_multirate_ok.contract.json`（**契约**声明 root 2 ms / nuttx 1 ms、预算 2 拍、
drift 15 ppm）生成，全程**不用** `--experiment-*` 开关——第一次走通
"契约声明 → 生成 → 板跑"的完整闭环（判据放行的部署实例）。

```
root   xdom init   t0_us=3535951819  period_us=2000
root   xdom anchor now_us=3535952695  period_us=2000      ← init→首拍 876 µs
nuttx  xdom anchor now_us=3535959492  period_us=1000
```

`ρ = (3535959492 − 3535952695) mod 1000 = 797 µs`

| | 数值 |
|---|---|
| 模型预测年龄集合 | `{797, 1797}` µs |
| 实测每窗口 `min_us` | 792 … 734 |
| 实测每窗口 `max_us` | 1865 … 1814 |
| 中点（预测 1297 / 实测 1328） | 差 32 µs |
| 预算 2 拍 = 2000 µs | 未越界，`stale=0` |
| 回路 | 有界（`g_plant=999`、`g_act=1616`），root `periods=10008`、`missed=0` |
| ρ 漂移 | min 792→734（3 s 掉 58 µs）⇒ **≈19 ppm** |

三件事被这次闭环确认：

1. **判据没有误杀**：窗 ≈100% 的部署能生成、能加载、能跑，且 model 的数值预测再次命中
   （中点差 32 µs，与 §16.3 的残差同量级）。
2. **契约声明即实现**：`domain_period_us{root:2000}` 真的变成 `ECOS_XDOM_PERIOD_US 2000` 与
   宿主 `period_us = 2000`，不再需要 `--experiment-*`。
3. **预算 2 拍在运行时确实没触发拒收**（`stale=0`），说明"声明—强制—证据"三者一致。

⚠ **必须说清的边界（否则会被读成"age 1.9 拍也没事，所以 §13.12 错了"）**：
这里 age 到 1865 µs（≈1.9 拍）而回路有界，与 §13.12"age 1–2 拍发散"**不矛盾**——
两者的 age 来源不同：

- §13.12 是**人为注入**：本来 1:1 的回路里把数据额外退 N 拍，控制律仍按 1 ms 设计 ⇒ 相位裕度被吃掉 ⇒ 发散。
- 这里是**结构性慢生产**：plant 本来就每 2 ms 才更新一次，控制律面对的就是一个 2 ms 的回路，
  "数据 1.9 ms 旧"是它自己的节拍，不是额外延迟。

⇒ 结论只能写：**"age ≤ 预算"是必要条件，不是稳定性的充分条件；而且同样的 age 数值，
来源不同（注入 vs 结构）对回路的影响不同**。判据拦的是"这个部署排不出满足声明的 age"，
不是"这个回路一定稳定"。

## 17.5 边界

- 判据只覆盖**单条跨域边**的年龄；~~整数倍速率比~~ **已由 §22 解除**（非整数比走同一条模拟）。
- 抖动不在模型里：判"窗为空/窗宽 0"够用（差别是数量级），判"窗只剩 30 µs"不够。
- `--allow-infeasible-deployment` 仍可强行生成（复现已证明不可行的装置是正当需求），
  但产物写 `EXPERIMENT.txt` 明确标注"不得用于论文主张"。
- 判据**不**判断控制稳定（同 §12.6）：满足年龄预算 ≠ 闭环性能好。

# 18. 口径对齐 + 判据的"必要性"实证（2026-10-27）

## 18.1 先修一个我自己留下的缺陷：两边对"1 拍"理解不同

§14 的运行时拒收写成 `age_us / PERIOD_US > MAX_AGE`（**向下取整**），而 §17 的编译期判据是
`max age_us ≤ 预算 × P_c`（**严格 µs**）。于是对同一份契约：

| 量 | 1797 µs 的 age |
|---|---|
| 运行时（floor） | `1797/1000 = 1 拍` ⇒ 预算 1 拍时**放行** |
| 编译期（µs） | `1797 > 1000` ⇒ **不可行** |

两边结论相反。后果有两个：判据拒绝的部署在板上"演示不出来"（运行时不拒），
而且运行时的拒收其实**没在执行声明**（声明 1 拍，实际放行了接近 2 拍的数据）。

修法：**统一到 µs**，声明与强制同源。

```c
#define ECOS_XDOM_MAX_AGE_US  ((uint32_t)ECOS_XDOM_MAX_AGE * (uint32_t)ECOS_XDOM_PERIOD_US)
if (ECOS_XDOM_MAX_AGE != 0 && age > ECOS_XDOM_MAX_AGE_US) { e->n_stale++; return; }
```

顺带把日志里的拍数改成**向上取整**（`(age + P - 1) / P`）：1797 µs 记 **2 拍**，
不再说成 1 拍。判据用 µs，拍数只用于人读的日志——两者不再互相冒充。

## 18.2 双臂对照（同一批代码，只换部署）

| 臂 | 部署 | 预算 | age_us（min…max） | 拍数 | `stale` | 回路 |
|----|------|------|------------------|------|---------|------|
| A | 1 ms / 1 ms（契约通过） | 1 拍 = 1000 µs | 621 … 777 | 1 | **0** | 有界 |
| B | 2 ms 执行器 / 1 ms 控制（契约**拒绝**，用 `--allow-infeasible-deployment` 强行生成） | 1 拍 = 1000 µs | min 766…846 / max 1864…1927 | **2** | **恰好 50.0%**（499/998、999/1998、…） | **也有界** |

B 臂的 `stale` 比例每一窗口都精确落在 50.0%——正好是模型说的"年龄在 `{a, a+1000}` 两个值上
交替，其中每隔一个就越过 1000 µs"。

## 18.3 三个结论

**① 判据的"必要性"得到实证。** 它拒绝的部署**确实无法满足声明**：一半样本的年龄越界
（1800 µs vs 声明 1000 µs）。这不是保守误判——如果放它过，运行时会拒掉一半数据，
等于这份契约根本没被执行。

**② 但"违反声明"≠"发散"。** B 臂回路仍是**有界**的。原因与 §17.4 同源：这里的 age 大是
**结构性慢生产**造成的，而且拒收一半样本的效果是"消费者改用旧值"——等于把回路进一步降速，
反而更稳。所以判据拦的是**契约违背**，不是稳定性。

**③ 判据 + 运行时是两层，不是一层。** 编译期判"这个部署排不排得出满足声明的 age"，
运行时保"真跑起来时越界的数据不进控制律"。缺任何一层都有洞：

- 只有运行时：违约的部署照样上板，靠拒收兜底——§14 已证拒收救不回（拒收=保持旧值=又一种延迟）。
- 只有编译期：模型之外的抖动/异常仍可能在板上越界（本节的 A 臂 age 已经到 777 µs，
  离 1000 µs 只剩 22%）。

## 18.4 边界

- 串口只有 nuttx 侧的 `ch1` 证据；root 侧 `ch0` 没人调 `ecos_xdom_report_evidence`，
  所以"root 消费慢生产数据"这一侧本次没有证据（它的预算按 2 ms 折算，理论更宽松）。
- 速率比是 2:1（整数倍）。**非整数比见 §22**：模型天然支持，差别在死区公式不能再用 ceil。
- 抖动仍未建模：A 臂 age 上界 777 µs 与预算 1000 µs 之间的余量，就是抖动要吃掉的。

# 19. 抖动进判据 + root 侧证据补齐（2026-10-27）

## 19.1 抖动怎么量：不需要外部参考

每个上报窗口已经同时给了 `min_us` / `max_us`——**同一窗口内的峰峰值就是抖动**。
这是本次补的两件事之一，另一件（root 侧证据）刚好让抖动第一次能在两个方向上量到：

| 通道 | 方向 | 每窗口跨度（峰峰） |
|------|------|------------------|
| ch1 | root 生产 → nuttx 消费 | 72 … 106 µs（20 窗口，均值 **94**） |
| ch0 | nuttx 生产 → root 消费 | 91 / 93 / 100 / 91 µs |

（ch0 以前一条证据都没有：`ecos_xdom_report_evidence` 只被 nuttx 宿主调用。现在
Linux 宿主也按秒调用一次，走 `pr_info` → dmesg。）

一条真实的 dmesg 样例：

```
xdom ch0 prod=1370954421 cons=1370954782 age_us=361 min_us=275 max_us=366 age=1 n=17000 stale=0 max=1
xdom ref t0_us=1353954650 now_us=1370954808 period_us=1000
```

⇒ §18.4 那条"root 侧没有证据"的边界补上了，双向判据现在**两个方向都能在板上量**。

## 19.2 抖动只进编译期判据，不进运行时

```python
budget_eff = budget_ticks × P_c − xdom_jitter_us      # 判据用这个
if age > MAX_AGE × PERIOD_US: 拒收                     # 运行时用声明的原值
```

为什么不对称：抖动是**模型的不确定性**（模型把每个事件当确定时刻），
不是数据的问题。所以它该在"预测还准不准"这一步扣掉，而不是让运行时去背。

判据新增一档：**预算 ≤ 抖动** ⇒ 直接判"这份契约本身就不成立"
（预算比不确定性还小，谈安全相位没有意义）。

声明值从初版的 100 µs 提到 **150 µs**：实测峰峰最大 106 µs，声明 100 等于零余量。
⚠ **§23 四档负载复测后已改成 200 µs**：同镜像下峰峰最大 173 µs（三核 100%），150 只剩 5% 余量。

## 19.3 加抖动后各部署的窗

| 部署 | 预算 | 有效（−150 µs） | 安全相位窗 | 结果 |
|------|------|-----------------|-----------|------|
| 1 ms / 1 ms | 1000 µs | 850 µs | ≈85% | 通过 |
| 2 ms / 1 ms | 2000 µs | 1850 µs | ≈92.5% | 通过 |
| 2 ms / 1 ms | 1000 µs | 850 µs | — | **拒绝**（仍无安全相位） |
| 预算 ≤ 抖动（如 1000 µs 预算配 1200 µs 抖动） | — | ≤0 | — | **拒绝**（契约不成立） |

1:1 从 §16 的 100% 掉到 85%，2:1+2 拍从 100% 掉到 92.5%——这正是抖动该吃掉的部分，
之前的"100%"是把模型当真理时的假象。

## 19.4 边界

- 峰峰值是**上界风格**的观测（每窗口的极差），不是分位数；没有做多负载/多温度重复。
- 抖动还会随负载变化，150 µs 只是本装置稳态下的上界——**§23 已按四档负载改成 200 µs**，
  并把"相位穿过 0 边界"那类整拍跳变从抖动里分出去（它不属于 jitter）。
- root 侧证据是按秒打印，`n` 的粒度仍是 1000 拍；`min/max` 是**该窗口内**的极差。
- ~~判据仍然只覆盖整数倍速率比~~ —— **已由 §22 扩展到 1.5:1 / 1.2:1**。

# 20. PR11-D：把"各域周期"喂进验证器 —— 多速率终于被**算**，而不只是被"生成"

§13–§19 里所有"合法/不合法"的判断，用的都是**一个** `period`。多速率部署
（执行器 2 ms / 控制 1 ms）虽然能生成、能上板，但**方案合法性从没被正确验证过**：
`grep domain_period_us` 在 `temporal_model.py` / `plan_verify.py` / `fusion_plan` 里全为空。
这一节补三件事：时间语义按域、参考模型跟到 v3、跨域收进严格入口。

## 20.1 单周期在多速率下不是"保守"，是**数值错**

三处受影响，逐一改：

| 位置 | 原来 | 现在 |
|------|------|------|
| `schedule()` | 所有组塞进一条串行线 | **按域各走一条**：同域串行、跨域并行（各有内核）。单域时逐位等价于旧实现 |
| 反馈死区 | `(1 + xd)·P`，P 是全局 period | `(k + xd)·P_c`，`P_c` = **消费者**的域周期，`k = ceil(P_p/P_c)` |
| 组容量 | `tot > period` | `tot > 该组所在域的周期`（2 ms 域里 1.5 ms 的段不再被"永远跑不完"误杀） |

死区为什么按消费者、为什么有 `k`：

- 消费者只能在**自己的**周期边界上读，所以"一拍"是 `P_c`；
- 生产比消费慢（`P_p > P_c`）时，消费者有几拍拿到的是**同一个旧值**——
  板上实测 2 ms/1 ms 的 age 在 `{a, a+1000}` 两个值间交替（§16），最坏要到 `k` 拍。

`k = 1` 时退化成 PR10-B 的 `(1+xd)·P`，所以 1:1 夹具**逐位不变**（自测里钉住了 400 µs）。

## 20.2 一改就翻出一个真问题：2 ms 执行器 + 2500 µs 期限**本来就不自洽**

把域周期喂进去之后，同一份 `xdom_loop` DAG：

| 契约 | 端到端 | 结果 |
|------|--------|------|
| `xdom_loop`（1:1，期限 2500） | 621.8 µs | 通过 |
| `xdom_loop_multirate`（root 2 ms，期限 2500） | 621.8 ＋ 跨域 1 拍 × 2000 = **2621.8 µs** | **拒绝**（XDOM_DEADLINE） |
| `xdom_loop_multirate_feasible`（同上一份，**只把期限放到 5000**） | 2621.8 µs | 通过 |

⚠ 这意味着 §17.4 那次板上"合法部署"实验的结论要**降级**：它满足**年龄预算**
（预算 2 拍、stale=0），但**不满足期限**——2.5 ms 的期限配 2 ms 的执行器不可能。
那次跑通的是"年龄维度上的合法"，不是"整方案合法"。判据链以前没有能力区分这两件事，
现在有了。

新夹具 `xdom_loop_multirate_feasible.contract.json` 与 `_ok` **只差 `deadline_us`
（2500 → 5000）**，它同时满足三道：年龄预算 2 拍（窗 ≈92.5%）、期限
（2621.8 ≤ 5000）、反馈死区（2400 ≤ 2500）。

## 20.3 参考模型跟到协议 v3（"规格 = 实现"这句才成立）

`kfusion/scripts/test/xipc_versioned_model.py` 之前还停在 v2：槽里叫 `tick`、
按整数拍判过期、没有 LAG / PICK。它自称"桥的可执行规格"，而那句话只对
"挑哪条消息"成立。现在逐条对齐 v3：

| 模型里必须有的 | 为什么 |
|----------------|--------|
| 槽字段 `ts_us`、`pub` 用发布时刻 | v2 的周期索引在多速率下不可比，已废弃 |
| `age_us = now − ts`（32 位回绕） | 与速率无关的真实年龄 |
| `age(拍) = ceil(age_us / P)` | 1797 µs 记 2 拍，不说成 1 拍 |
| 拒收判据 `age_us > MAX_AGE×P` | 与编译期 `预算×P` 同口径（§18 的缺陷就是这两边不一致） |
| `PICK` 三臂（latest/oldest/one） | 对应 §14 的三条取数语义臂；`one` 必须能积压 |
| `LAG` 移位寄存器 | 对应 §13.11/§13.12 的剂量-反应旋钮 |

自测覆盖 7 组断言，其中"1797 µs 记为 2 拍 / 预算 1 拍拒收 / 预算 2 拍放行"
正是板上那两跑的判据；`one` 臂的"环里还剩 4 条"对应"每拍只消化一条会积压"。

## 20.4 跨域收进严格入口：`ecos_build.sh --split-by-domain`

以前跨域只有一条路：手写 `xdom_build.sh` + 两条手工 `emit` 命令。于是
**"论文用的产物"和"严格入口产出的产物"是两条链**，绕过严格入口反而成了默认做法。
现在一次调用走完：

```
契约门 → 规划 → 对落盘 plan.json 独立复检 → split（每域一份子方案 + interface.json）
      → 两端各自 emit（root→linux-kernel，nuttx→nuttx）→ 溯源清单 manifest.txt
```

落盘形态与手写链一致（`root/` 与 `nuttx/` 各含 `ecos_fused_*`、`ecos_xdom.*`、
`stage_impl.c`、`ecos_xipc.h`），所以目标板上的 `xdom_build.sh` 可以直接吃。
两条硬约束在入口里守住了：

- `--split-by-domain` 与 `--target` **互斥**（rc=2）：拆分后两端目标由域决定，
  静默忽略一个用户以为生效的开关比报错更糟。
- 两端 `stage_impl.c` 与 `ecos_xipc.h` **逐字节相同**（自测断言）；只编一端会 ABI 不一致，
  表现是数据错乱而不是报错。

## 20.5 边界（这一节没有证明什么）

- **规划器的 DP 仍是串行的**（`solve_dp` 按线性顺序递推 `max(头相位, 上一组完成)`）。
  所以它挑分组时对多速率是**偏保守**的（可能低估并行、挑到更碎的方案）；
  报告与验证的数字走 `schedule()`/`_finish_time()` 的按域版本，两者已经一致，
  但"搜索"这一步没有按域重写。
- ~~只覆盖整数倍速率比~~ —— **§22 把死区改成 `P_c + xd·P_p` 后，非整数比也精确了**
  （`k = ceil(P_p/P_c)` 从此只用于人类可读的"几拍"）。
- 跨域一拍的定价取"各跨域边消费者周期的最大值"（`hop_period_us`），
  不知道关键路径具体走哪几条边时这是上界，不是精确值。
- `xdom_loop_multirate_feasible` 只证明"模型认为它自洽"，**没有上板重跑**；
  板上已验证的是 `_ok`（年龄预算维度）。

# 21. 部署可行性进验证器：判据只此一份，两个消费者各取所需

## 21.1 缺口：判据在"门"上，不在"验证"里

§17 把安全相位窗接进了 `contract_validate`（契约层）与 `emit`（生成层），
但**没接进 `plan_verify`**。而项目铁律是：

> 整份方案的合法性**只认** `ecos/plan_verify.py`。

于是留下一个真实的漏洞：一份方案可以在 `plan_verify` 里"验证通过"，却在该速率组合下
根本排不出预算内的数据年龄。那样"通过"是假的——它通过的是**另一套**判据。

## 21.2 做法：判据加诊断码，两处共用同一份

`plan_verify` 的错误是 `{code, msg}`（报告、CI、失败归因都按 code 归属），
而 `contract_validate` 只需要打印文本。所以：

```
xdom_timeline.check_contract_coded(dag, contract) -> ([(code,msg)], [(code,msg)])
xdom_timeline.check_contract(dag, contract)       -> ([msg], [msg])      # 仅降维
```

`check_contract` 只做 `(code,msg) → msg` 的降维，**不另写一套判据**。
把同一份逻辑复制两遍，正是 P0-1 那类"算得出的与验得出的分叉"的来源。

诊断码：

| code | 含义 |
|------|------|
| `XDOM_INFEASIBLE` | 安全相位窗为空或总宽 0 ⇒ 该速率组合在预算内排不出 |
| `XDOM_BUDGET_MISSING` | 有跨域边但契约没给 `xdom_max_age_ticks`（fail-closed） |
| `XDOM_BUDGET_INVALID` / `XDOM_DRIFT_INVALID` / `XDOM_JITTER_INVALID` | 字段不是数字 / 负数 |
| `XDOM_PERIOD_UNKNOWN` | 跨域边的域周期既没 `domain_period_us` 也没 `period_us` |
| `XDOM_DRIFT_UNDECLARED` / `XDOM_JITTER_UNDECLARED` | 告警：按 0 处理会让窗偏乐观 |
| `XDOM_NARROW_WINDOW` | 告警：窗宽 < 10% |
| `XDOM_CHECK_FAILED` | 判据本身跑不起来（fail-closed，绝不放行） |

## 21.3 三条它现在能拦住的（自测固化）

| 情形 | 结果 |
|------|------|
| 自洽多速率（预算 2 拍 / 期限 5000） | 规划 + 独立验证都通过 |
| 同一份方案，契约只把预算改成 1 拍（期限仍 5000，跨域期限**不**红） | **规划阶段即拒**：`[XDOM_INFEASIBLE]` |
| 把**已经通过验证**的方案拿更严预算复检 | **复检也拒**：`[XDOM_INFEASIBLE]` |
| 有跨域边但契约没给预算 | **fail-closed**：`[XDOM_BUDGET_MISSING]` |
| 1:1 跨域环（窗 ≈85%） | 通过（不误杀） |

第三行是关键：它证明判据在**验证器**里，而不是只挡在生成那条路上。

## 21.4 副作用（要记住）

严格入口现在**拒绝**生成"预算内不可行"的部署——这是对的，但它改变了复现流程：

- 以前可以 `fusion_plan --contract xdom_loop_multirate`（预算 1）规划出方案，
  再让 `emit --allow-infeasible-deployment` 强行生成，用来复现已证明不可行的装置。
- 现在规划这一步就 `rc=3`。**复现路径改为**：用 1:1 契约 + `--experiment-period-us`
  生成，或在 `emit` 层直接给定 plan（`--allow-infeasible-deployment` 仍然有效，
  它管的是"生成层的最终节拍"，与这里的"契约层判据"不是同一层）。

两层判据都没有删：`emit` 的检查用**最终**节拍（含 `--experiment-*` 覆盖），
`plan_verify` 的检查用**契约**；两者调用同一个 `check_edge`，不构成第二套语义。

## 21.5 边界

- 仓库里**只有一张**跨域 DAG 夹具（`xdom_loop.dag.json`），所以这次改动的影响面很小；
  但也意味着"多域但非环形"的图没有被覆盖。
- ~~仍只覆盖整数倍速率比~~ —— **已由 §22 处理**。
- 判据判的是"这个部署排不排得出满足声明的 age"，**不是**控制稳定（同 §12.6）。

# 22. 非整数倍速率比：死区公式从"数拍"改成"算时间"

## 22.1 先量清楚：最大年龄的上界是 `P_p`，不是 `k·P_c`

用 `xdom_timeline` 扫 ρ（步长 `P_c/4`，`n_cons=600`）：

| 生产/消费 | 实测最大年龄 | `P_p` | `k = ceil(P_p/P_c)` | `k·P_c` |
|-----------|-------------|-------|--------------------|---------|
| 1000 / 1000 | 750 | 1000 | 1 | 1000 |
| 2000 / 1000 | 1750 | 2000 | 2 | 2000 |
| **1500 / 1000** | **1250** | **1500** | **2** | **2000** |
| **1200 / 1000** | **1150** | **1200** | **2** | **2000** |
| 2500 / 1000 | 2250 | 2500 | 3 | 3000 |
| 3000 / 2000 | 2500 | 3000 | 2 | 4000 |

读法：`max age < P_p` 一直成立（生产者每 `P_p` 才更新一次，消费者读到的不会更旧）。
而 `k·P_c` 只在**整数倍**比下才接近 `P_p`；非整数比会明显虚高——
1200/1000 时虚高 **67%**。

## 22.2 所以死区公式改成 `P_c + xd·P_p`

```
dead_us = P_c + xd * P_p + (t_cons - t_prod)
```

- `P_c`：消费者只能在**自己的**周期边界上读 ⇒ z⁻¹ 那一拍是消费者的一拍。
- `xd·P_p`：跨域时这条数据最多已经旧了一个**生产**周期 ⇒ 跨域那一项是生产者的一拍。
- `P_p = P_c`（同域）或 1:1 跨域时，退化成 PR10-B 的 `(1+xd)·P`：**逐位不变**。

替换的旧式子是 `(k + xd)·P_c`。它在整数倍下与上式**完全等价**（`P_p = k·P_c`），
在非整数比下才会分叉——所以这是一次**只收紧、不放宽**的修正：

| 速率比 | 旧 `(k+xd)P_c` | 新 `P_c + P_p` | 实测最大年龄 |
|--------|---------------|----------------|-------------|
| 1:1（跨域） | 2000 | 2000 | ≤1000 |
| 2:1 | 3000 | 3000 | ≤2000 |
| 1.5:1 | **3000** | **2500** | ≤1500 |
| 1.2:1 | **3000** | **2200** | ≤1200 |

旧式子在 1.5:1 上比新式子多算 500 µs，在 1.2:1 上多算 800 µs——足够把一份本来合法的方案
顶出 `feedback_delay_max_us`，这就是"非整数比下会误拒"的具体机制。

## 22.3 可行性判据本来就支持非整数比（它一直是模拟，不是公式）

`safe_phase_window` 扫 `ρ ∈ [0, lcm(P_p,P_c))`、逐拍模拟环——**没有一个地方假设整数倍**。
非整数比只是 `lcm` 变大（1200/1000 ⇒ 6000 µs），步长更细而已。实测：

| 部署 | 预算 | 窗 | 判定 |
|------|------|-----|------|
| 1500/1000 | 1000 µs（1 拍） | — | **不可行**（真实最大年龄 1500 > 850 有效预算） |
| 1500/1000 | 2000 µs（2 拍） | 2992/3000（100%） | 可行 |
| 1200/1000 | 1200 µs | 933/6000（**16%**） | 可行但窗很窄 ⇒ 告警 |

最后一档是"告警而不是拒绝"的正当例子：窗存在（16%），但对漂移几乎没有余量。

## 22.4 自测固化的（§36，七组 + 契约层三条）

- 上界性：1.5:1 / 1.2:1 / 2.5:1 / 1:1.5 四组，实测最大年龄都 ≤ `P_p`；
- 死区：1.5:1 得 1900 µs（1000 + 1500 − 600），且**严格小于**旧式子的 2400；
- 死区减去相位差 ≥ 实测最大年龄（"上界"不是标签，是算出来的）；
- 契约层：1.5:1 + 预算 1 拍 ⇒ `rc=3`；预算 2 拍 ⇒ `rc=0`；规划+验证随之通过。

## 22.5 边界

- `k = ceil(P_p/P_c)` 仍留在报告里（"几拍"给人读），但**不再参与死区计算**；
  如果以后有人把它当判据用，就会退回本节修正前的错误。
- 模拟仍假设**带宽无限、无丢包**（环容量 224）；消费者跟不上时的 `drops` 只在模型里计数，
  没有反馈到年龄上界里。
- 只测了整数毫秒级周期（1000/1200/1500/2000/2500/3000）。带小数的周期（如 1000/3 µs）
  在 `safe_phase_window` 里会被 `int()` 截断做 gcd，那条路没验过。

# 23. 抖动到底多大：四档负载复测（并纠一个口径错误）

§19 把 `xdom_jitter_us` 定成 150，依据是**一次开机、单负载**下每窗口峰峰 72…106 µs。
这一节用**同一份镜像**跑四档负载，看看这个数是不是上界——顺带发现 §19 把两件事混成了一个量。

## 23.1 装置（顺带验证 §21 的严格入口产物能上板）

产物由 `ecos_build.sh --split-by-domain` 生成（契约 `xdom_loop.contract.json`：1:1、
预算 1 拍、drift 15 ppm；建镜像时的 jitter 还是 150，之后按本节数据改成 200——
jitter 只进编译期判据、不进生成代码，所以镜像与这个数无关），板端 `xdom_build.sh` 编 root `.ko` + NuttX 镜像，
`deploy_nuttx_cell.sh` + `insmod`，串口（COM11）读 `xdom ch1` 每 1 s 的窗口统计。

``` 
nuttx/root 各 1 ms；root periods≈22000/22 s；missed=0（原子释放无积压）
```

## 23.2 结果：抖动对负载**不敏感**

| 臂 | 负载（已确认） | p2p p50 | p2p p90 | p2p max | 窗口 max_us | stale |
|----|---------------|---------|---------|---------|-------------|-------|
| L0 | 空载 | 105 | 963* | 1009* | 1009* | 49 / 21990（0.22%） |
| L1 | 1 核 100% | 98 | 106 | 143 | 629 | 0 |
| L2 | 三核忙（未确认生效） | 91 | 99 | 117 | 403 | 0 |
| L3 | 3 核各 100%（`top` 确认） | 96 | 131 | 173 | 882 | 0 |

\* L0 的 p90/max 不是抖动，见 §23.3。

读数：

- **中位峰峰 91…105 µs，四档几乎一样**（差 <15%）。负载把 p90 从 106 抬到 131、
  最大值抬到 **173 µs**，但量级没变。
- 所以 §19 的 150 µs **只剩 5% 余量**，不配叫上界；夹具已改成 **200 µs**
  （1:1 的安全窗随之 85% → 80%，2:1 + 2 拍 84% → 79%，都仍通过）。
- `age(拍)` 全程 ≤ 1，L1/L2/L3 的 `stale` 都是 0——**负载没有把 1 拍预算顶穿**。

## 23.3 纠错：~1000 µs 的尖峰不是抖动，是"相位穿过 0 边界"

L0 的逐窗口序列（节选）：

```
序   age_us  min   max   p2p   stale
17      22     8   112   104     0
18       6     1    97    96     0
19     991     0  1009  1009    48     ← 这一秒里 ρ 跨过 0
20     975     3  1003  1000    49
21     959    24   987   963    49
```

前 19 个窗口 `age_us` **单调下降** 291 → 6（≈14.9 µs/s ⇒ **14.9 ppm**，与 §16.3 的
13.7 ppm、§15 的 15 ppm 同源）。到第 19 秒 ρ 穿过 0，年龄**整体跳一个周期**
（6 → 991），那一秒里 48 个样本因 `age > 1000` 被拒收。

三次独立 `insmod` 的漂移都是 **14.3 / 15.0 / 15.8 µs/s**，所以：

> 双域相位每 `P_c / drift ≈ 1000 / 15 ≈ **67 s**` 穿过一次边界；
> 每次穿越的瞬间，抖动会把年龄顶出预算，产生**约 50 个样本**的拒收（0.2% 量级）。

两件事必须分开：

| 量 | 数值 | 性质 | 该进哪里 |
|----|------|------|----------|
| 抖动（p2p 内噪声） | 90…173 µs | 随机、负载弱相关 | `xdom_jitter_us`（判据扣预算） |
| 穿越跳变 | ≈ 一整拍（1000 µs） | **确定性**，由 drift 决定 | 相位问题，不是 jitter |

把穿越算进 jitter 会得出"抖动 ≈1 ms"的荒谬结论；不算它，又会漏掉"每次穿越必然有一小段拒收"。
正确写法是 §16 的安全相位窗 + 这里的漂移速度：**相位空间里 15% 不安全 ⇒ ρ 每 67 s
把整个相空间走一遍 ⇒ 每 67 s 有一小段拒收**。

## 23.4 工程结论

1. **`xdom_jitter_us` 取 200**（覆盖实测最大 173，留 ~15% 余量）。
2. **1:1 + 1 拍预算是"相位空间 80% 安全"，不是"永远合法"**：ρ 会漂到不安全的那 20% 里。
   想长期不掉样本，只有两条路：
   - 预算放到 **2 拍**（覆盖一次穿越），或
   - **周期性重同步**（把 ρ 拉回安全区）——这正是 PR11-A 原义里"相位协调"真正的位置。
3. 这条给出了一个可写进论文的定量表述：
   *"在 15 ppm 漂移下，编译期钉死的安全相位每 67 s 就被走穿一次；单拍预算的部署
   因此每秒级地承受 0.2% 的样本拒收，而不是'一次配置永久成立'。"*

## 23.5 边界

- 单板、单机、22 s/臂（只覆盖一次穿越）；没有多温度、没有长时间（>1 h）跑。
- 负载用 3 个 100% 自旋，只代表"CPU 被占满"这一种压力，不代表真实应用的缓存/IO 压力。
- 只解析了 nuttx 侧 `ch1`；root 侧 `ch0` 这次没从串口抓（它在 dmesg，本臂没取）。
- L2 的负载未确认生效（`uptime` 只到 1.08，`top` 没在跑中取样），所以只当"轻载"参考。

# 24. 长跑 A/B：预算 1 拍 vs 2 拍（穿越的代价能不能用预算买掉）

§23 的结论是"每 ~67 s 漂移会把相位拖过边界、每次约 50 个样本被拒，要长期不掉样本只能
预算 2 拍或周期性重同步"。这一节把它做成**受控 A/B**：同一份 DAG、同一装置、同一耗时，
**只改 `xdom_max_age_ticks`（1 → 2）**，各跑 180 s（≈3 个穿越周期）。

## 24.1 装置

- 产物由严格入口生成（`ecos_build.sh --split-by-domain`），契约分别是
  `xdom_loop.contract.json`（预算 1）与 `xdom_loop_budget2.contract.json`（预算 2，
  **只差这一个字段**）；两端 `ECOS_XDOM_PERIOD_US=1000`，1:1。
- 板端 `xdom_build.sh` → `deploy_nuttx_cell.sh` → `insmod`；空载（loadavg ≈ 0）；
  串口每次窗口（1 s）打 `xdom ch1 prod cons age_us min/max age n stale max`。
- 两臂 `periods≈182000/182 s`（**1.000 kHz**）、`missed=0`（释放无积压）。

## 24.2 结果

| 臂 | 预算 | 穿越次数（时刻） | 实测间隔 | 每次新增 stale | 总 stale | age_us 范围 | 窗口 max_us |
|----|------|-----------------|---------|---------------|---------|-------------|-------------|
| A | **1 拍**（1000 µs） | 3 次（23 / 86 / 149 s） | **63 s** | 35 / 48 / 45 | **141 / 181995（0.077%）** | 3…996 | **1060** |
| B | **2 拍**（2000 µs） | 3 次（17 / 80 / 143 s） | **63 s** | 0 / 0 / 0 | **0 / 181989（0%）** | 2…992 | 1013 |

两臂的漂移中位都是 **16 µs/s（16 ppm）**，穿越间隔都是 **63 s**——装置完全可比，
唯一差别就是预算。

## 24.3 穿越时刻是**可预测**的（两次独立命中）

穿越发生在 ρ 穿过 0 的时刻，所以首个穿越时刻 ≈ `age₀ / drift`：

| 臂 | 开局 age_us（前三个窗口） | 用 `age₀/(age₀−age₁)` 预测 | 实测首个穿越 |
|----|--------------------------|---------------------------|-------------|
| A | 350 / 335 / 319 | **23 s** | **第 23 秒** |
| B | 255 / 239 / 226 | **16 s** | **第 17 秒** |

穿越周期：`1000 µs ÷ 16 µs/s = 62.5 s`，实测 **63 s**（误差 0.8%）。
⇒ 这不是"随机抖动"，是**确定性的相位行走**：给它起点的 age 和漂移速率，就能算出下一次
什么时候掉样本。这条比"抖动 200 µs"更能解释长期行为。

## 24.4 预算 2 拍确实买掉了穿越，价格是"一拍"

- 预算 1：每次穿越有 **35–48 个样本**因 `age > 1000` 被拒（那一秒的 `stale` 增量），
  180 s 累计 0.077%。拒收**不是**因为调度积压（`missed=0` 全程为零），纯粹是年龄越界。
- 预算 2：同样 3 次穿越、`stale = 0` 全程，窗口 `max_us` 最大 **1013**，
  离 2000 µs 还有近一半余量。

所以工程上的选择很清楚：

> 若"掉 0.08% 的样本"可接受 → 预算 1 拍就够；
> 若要"一次都不掉" → 预算给到 2 拍（覆盖一次整拍跳变），代价是允许的数据年龄翻倍。
> 想两者兼得，只能做**周期性重同步**（把 ρ 拉回安全区）——那是 PR11-A 原义要做的事。

## 24.5 顺带：root 侧 ch0 第一次进长跑

B 臂在 root 侧（`pr_info` → dmesg）也取了 182 s 的窗口：

```
xdom ch0 prod=460609617 cons=460610205 age_us=588 min_us=517 max_us=590 age=1 n=181000 stale=0 max=2
xdom ch0 prod=461609617 cons=461610220 age_us=603 min_us=532 max_us=615 age=1 n=182000 stale=0 max=2
```

`n=182000`、`stale=0`、`age_us≈600`、`age=1 拍`（`max=2` 是取整后的历史最大值）。
⇒ **双向**（nuttx→root 与 root→nuttx）在长跑下都保持有界且零拒收，不是只有一侧好看。

## 24.6 边界

- 单板、空载、180 s（约 3 个穿越周期）。没有测 >1 h（漂移周期约 63 s，长跑会很多次穿越，
  但预算 2 臂的"零拒收"是否会因偶发大抖动破掉，需要更长时间）。
- 预算 2 的"足够"是**本装置的经验结论**（`max_us` 最大 1013 < 2000）。理论上界仍是
  `P_c + jitter`；换到抖动更大的平台，2 拍可能不够。
- 两臂的穿越时刻不同（23/17 s 起），所以"每次 stale 数量"不是逐次配对的，
  只能比"量级"与"是否为零"。
- `stale` 只统计**越界被拒**，不区分"差 1 µs"和"差 60 µs"；本节的 `max_us` 说明
  最大越界幅度只有 ~60 µs。

# 25. 周期性重同步：用"一次超周期"换掉"一次穿越"（预算 1 拍也能零拒收）

§24 的结论是二选一：要么接受每次穿越掉 ~40 个样本（预算 1 拍），要么把预算翻到 2 拍。
第三条路是**把相位拉回来**——这正是 PR11-A 原义里"相位协调"要干的事。这一节把它做成
最小可运行版本，并在板上验证。

## 25.1 机制（很小，只动两处）

```
桥（ecos_xdom.c）：
    每个样本算出 age_us 后，若 age_us < xdom_resync_at_us（快到边界了）
    且距上次超过冷却时间 ⇒ 置一个待应用的平移量 xdom_resync_us，计数 +1
宿主（消费者那一侧，生成在 ecos_nuttx_main.c）：
    每拍开头 d = ecos_xdom_resync_take(); 若 d != 0 ⇒ base += d
```

- 判据只看"年龄已经很小"，**不看"已经越界"**——等越界那一拍再补，那一拍已经掉了。
- 平移是**一次性**的：只把"这一个"周期的释放时刻推后 `resync_us`，之后继续按原周期跑。
- 代价必须记账：**被平移的那一个周期会变长** `resync_us`（周期不再严格等长）。
- 三个字段全部写在契约 `timing_constraints` 下（`xdom_resync_us` / `xdom_resync_at_us` /
  `xdom_resync_cooldown_us`），emit 只从契约读；写错位置、或只给平移不给触发阈值，都判错
  （后者意味着"配了永远不会生效"）。
- 默认全 0 ⇒ 整套逻辑被编译掉，既有产物一个字节都不变（自测里钉住了）。

实验配置：`xdom_loop_resync.contract.json` —— 与 `xdom_loop` **只差这三个字段**
（500 µs / 200 µs / 15 s），**预算仍是 1 拍**。

## 25.2 三臂对比（同一 DAG、同一装置、各 180 s、空载）

| 臂 | 预算 | 重同步 | 穿越次数 | `stale` | `age_us` 范围 | 窗口 `max_us` | `missed` |
|----|------|--------|---------|---------|---------------|----------------|----------|
| A | 1 拍 | 无 | **3**（23/86/149 s） | **141**（0.077%） | 3…996（含跳变到 1060） | 1060 | 0 |
| B | 2 拍 | 无 | 3（17/80/143 s） | 0 | 2…992 | 1013 | 0 |
| **C** | **1 拍** | **500 µs @ age<200** | **0** | **0 / 181995** | **205…716** | **788** | **0** |

C 臂的重同步事件：**6 次**（n=1…6），每次都打印 `xdom resync shift_us=500`，
且**全程没有一次 age 跳升超 500**——穿越被完全挡住，不是"越界后补救"。

## 25.3 三个结论

**① 预算不翻倍也能零拒收。** C 臂预算与 A 相同（1 拍），`stale=0`；
A 臂在同样 180 s 里掉了 141 个样本。

**② 它比"加预算"更紧。** 同为 0 拒收，B 臂（2 拍）的窗口最大值到 1013 µs，
C 臂只到 **788**，日常年龄被压在 **205…716** 的窄带里。原因是重同步**主动**把相位
推回安全区，而加预算是**被动**允许更大的年龄。

**③ 代价是 6 个"超周期"。** 每次平移让那一个周期多 500 µs，180 s 里共 6 次 ⇒
累计 3 ms（占比 0.0017%）。`periods=182008 / 182 s` 仍是 1000.0/s，`missed=0`
（原子释放计数没有积压）——也就是说这点超周期没有把调度推歪。

> 一句话：**"一次 500 µs 的超周期" 换掉了 "一次整拍跳变 + ~40 个样本拒收"**。
> 这就是 PR11-A 想要的相位协调，最小形态。

## 25.4 边界（这条最容易被误读成"问题解决了"）

- **不是 LET**。LET 要给执行窗、要证明"输出在窗口内生效"；这里只是把消费者的一次释放
  推后一点。它调的是**相位**，不保证控制律的时序语义。
- **方向是写死的 +500 µs**。本装置的漂移是"age 单调下降"，所以"往后推"总是对的。
  若漂移反向（age 增长），触发会发生在刚跨过边界之后，那一次仍可能掉几个样本
  （然后才被推回）。**方向自适应没有实现**。
- **门限/步长是手工定的**（200/500），没有闭环控制律；步长太大会把 age 推到接近
  预算上限（本配置 200+500=700，离 1000 只剩 300）。
- **只改消费者一侧**。生产者的释放时刻没动；如果两边都想调，需要额外的协调协议。
- **超周期是对"严格周期"契约的违反**，只是幅度小（500 µs / 1000 µs = 半个周期，
  一次）。论文里必须写成"以一次非等周期为代价"，不能写成"没有代价"。
- 180 s、单板、空载；没有测漂移方向反转、没有测更长的多天稳定性。
