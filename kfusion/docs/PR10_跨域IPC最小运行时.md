# PR10 —— 跨域 IPC 最小运行时（IVSHMEM 发布-订阅）

> 状态：**两端实现 + 板上实测完成**（2026-10-25）。
> 目标：给 ECoS 的跨域边一个**可测的代价**，而不是拿单域融合的 `c`（唤醒税）去糊。
> 结论先说：**通路本身是亚微秒级，但控制回路里跨域依赖的代价是"一个周期"**。
> 这两件事差三个数量级，混用会把跨域优化的收益算到天上去。

---

## 1. 为什么不是"把旧 PoC 扩大一下"

仓库里原有 `xshm` + `ivshmem_probe`：直接拿 rw_section 起始 16 字节当 mailbox，
四个 32 位字，单向写、对端轮询。它能证明"通路通了"，但做不了三件事：

| 缺口 | 后果 |
|---|---|
| 只用一个方向的一段内存 | 两个方向要同时跑就得各写一套偏移，两端一旦不一致就是"都跑得动、数据不对" |
| 无提交语义（读者可能读到半个槽） | 跨域场景下这个窗口比单核大得多 |
| 无"这一轮"概念 | cell 重建**不清零** IVSHMEM，上一次的残留会被当成有效状态 |

PR10 的运行时有四条硬设计：

1. **一份头，两个宿主**：`kfusion/runtime/xshm/ecos_xipc.h` 被 root 侧（Linux 用户态）
   与 inmate 侧（NuttX）同时 `#include`，布局与环操作**只有一处定义**。
   仓库里不允许有第二份（自测里查）。
2. **按 peer 分片**：rw_section 是 3 peer × 12 KiB（0x9000）。peer0 片放 root→inmate 环，
   peer1 片放 inmate→root 环，peer2 片放统计。补上了旧 PoC 明确留下的 TODO。
3. **SPSC 无锁环**，每个环唯一写者、唯一读者，`head`/`tail` 各占一条 cache line；
   提交靠 `slot.seq`：先写负载 → 再写 seq → 最后推进 head，读者只认 `seq == tail+1`。
4. **session 号**：owner 每轮用 `CNTVCT` 生成一个新 session 写进环头，对端必须看到
   session **变化**才认为"新一轮开始了"。这一条是实测踩出来的，见 §5 的坑 3。

```
rw_section @ 0x1faf1000（root: /dev/uio0 map2；inmate: 同一物理地址同虚拟地址）
  0x0000  peer0 片  ┌─ struct xipc_ring  root → inmate  （224 槽 × 16 B）
  0x3000  peer1 片  ├─ struct xipc_ring  inmate → root
  0x6000  peer2 片  └─ struct xipc_stats（各字段归属固定，避免伪共享）
```

环头：`magic 0x00 | version 0x04 | cap 0x08 | slot_bytes 0x0C | session 0x10 |
head 0x40 | tail 0x80 | drops 0xC0 | slot[224] 0x100`，总共 3840 B，装进一页。
这些偏移在头文件里由 `XIPC_ASSERT_EQ` 编译期断言，另有
`kfusion/scripts/ecos/xipc_layout_check.py` 在本机（无编译器）做同一套算术校验。

### 消息与控制面

| kind | 方向 | 语义 |
|---|---|---|
| `HELLO` | inmate→root | 上线，a=版本，b=CNTFRQ |
| `PING` | root→inmate | a=序号，b=发送时刻（counter 低 32 位） |
| `ECHO` | inmate→root | a=序号，b=**读到 PING 那一刻**的 counter |
| `TICK` | inmate→root | 周期数据，b=产生时刻 |
| `MODE` | root→inmate | a=tick_every，b=period_us（运行时切模式） |
| `STOP` | root→inmate | 收工 |

`MODE` 不只是省一次交互：那块板子的串口**只能看不能敲**（只接了 Pi TX → 适配器 RX），
没法在 NSH 里输参数。让 root 侧用一条消息切换实时侧的工作模式，等于把"控制面"
也架在同一条环上——正好是要证明的东西：一条 SPSC 环 + 两类消息就能跑一个跨域控制回路。

## 2. 为什么两端都是轮询（门铃的硬约束）

IVSHMEM 门铃 = 往寄存器区 offset `0x0C` 写 `(target<<16 | vector)`，由 hypervisor
陷获后向目标 cell 注入中断。它成立的前提是**寄存器区被注册成可陷获的 MMIO**，而这
要求本 cell 的 PCI 命令寄存器置了 `MEM` 位：

- root 侧：`uio_ivshmem` 驱动置了 → 门铃路径存在（`/proc/interrupts` 里能看到
  `uio_ivshmem[0001:00:00.0]`，GICv2 182）。
- NuttX 侧：**没有 PCI 枚举**，这个位不会置。此时 cell 配置里 0x1faf0000 只给了
  `JAILHOUSE_MEM_READ`，对该地址的写不是"没效果"，而是**故障**。

所以本轮两端都是轮询。对周期性控制任务这不是妥协：实时侧本来就要在周期边界采样，
边界上的轮询是零额外代价的。门铃要等 NuttX 侧补一个最小 PCI 配置访问（置 `CMD_MEM`
+ 启 INTx）才谈得上，记在 §6。

## 3. 实测（Pi4，root cell ↔ NuttX inmate，1 kHz 参考周期）

条件：Pi4B / jailhouse v0.12-342 / 内核 5.15.86 / NuttX cell 独占 CPU1 /
root cell 0,2-3 / 未绑核 / `CNTFRQ = 54 MHz`。
分位数为原始样本排序后的精确值（不用直方图近似，原因见 §5 坑 6）。

### 3.1 通路下限（inmate 忙等，3000 次一问一答）

| 量 | p50 | p90 | p99 | p99.9 | min | max |
|---|---|---|---|---|---|---|
| 单程 root→inmate | **0.65 µs** | 0.65 | 0.70 | 71.61 | 0.59 | 71.85 |
| RTT | **1.24 µs** | 1.26 | 1.31 | 72.28 | 1.19 | 76.85 |

- 单程/RTT ≈ 1.9 —— 这是**时间基准自洽的经验证据**：两侧都读 `CNTVCT_EL0`，
  Jailhouse 不设 `CNTVOFF`，所以是同一个计数器。异常样本 0 / 3000。
- 尾部 72 µs 不是通路本身，是偶发的调度/中断介入（未绑核，未做归因）。

### 3.2 控制回路里的真实代价（inmate 按 1 ms 周期采样，500 次）

| 量 | p50 | p90 | p99 | min | max |
|---|---|---|---|---|---|
| 单程 | **1005.26 µs** | 1005.33 | 1005.37 | 285.70 | 1006.18 |
| RTT | **1005.87 µs** | 1005.94 | 1006.00 | 286.30 | 1017.44 |

**p50 ≈ 1.005 个周期**，不是半个周期。原因不是"运气差"，而是调用方被相位锁死：
root 收到 ECHO 后立刻发下一个 PING，而此刻 inmate 刚好做完本轮 drain 去睡，
于是下一个请求必然等满一整拍。min 285.7 µs 对应"恰好在 drain 前到达"的少数样本。

对 ECoS 的含义很直接：**跨域边是一条 ≥1 个周期的延迟边**。评估"该不该把这段搬到
另一个域"时，必须用 `≈ period` 而不是 §3.1 的微秒数。

### 3.3 消费侧轮询粒度（inmate 每 1 ms 推一个 TICK）

| root 的 drain-sleep | p50 | p90 | p99 | max |
|---|---|---|---|---|
| 0（忙等） | **0.74 µs** | 0.78 | 0.80 | 15.78 |
| 250 µs | 166.56 µs | 296.04 | 323.07 | 363.22 |
| 500 µs | 286.20 µs | 509.83 | 563.33 | 698.91 |

p50 ≈ `sleep/2 + 40 µs`。那 40 µs 是 `usleep()` 的固有超调（Linux 的 sleep 粒度），
不是通路开销——把它算进"IPC 延迟"会高估一个数量级以上。

## 4. 三个必须分开说的判断

1. **通路延迟 ≠ 依赖代价。** 0.65 µs 是"两个 cell 都空转时"的下限；1.005 ms 才是
   "实时侧按周期采样"时的真实值。论文里只能引用后者作为跨域边的代价。
2. **门铃不是"还没做"，是"这侧没有 MMIO 陷获"。** 写门铃会撞只读映射。不写清楚
   这一点，后来的人会以为加个 `write()` 就行。
3. **时间可比是有前提的。** 两侧共基准靠"Jailhouse 不设 CNTVOFF"这个事实，
   不是协议保证的。所以运行时自带经验校验（单程 > RTT 就单列计数），
   一旦换 hypervisor / 换核，异常计数会立刻暴露。

## 5. 踩到的坑（每条都花了不止一轮）

| # | 症状 | 根因 | 处理 |
|---|---|---|---|
| 1 | root 侧 `SIGILL`，且**一行输出都没有** | `mrs cntpct_el0` 在 EL0 是未定义指令（内核没置 `CNTKCTL_EL1.EL0PCTEN`）；stdout 走管道是块缓冲，崩了什么都不留 | 改用 `CNTVCT_EL0`（VDSO 用的就是它）；root 侧 `setvbuf(_IOLBF)` |
| 2 | 单程**恒为负**、可见值溢出到量程顶 | 环槽只有 32 位，我把截断值和 64 位值直接比较 | 两端统一用"32 位回绕差"：`(uint32_t)(b - a)`，@54 MHz 可表示 79 s |
| 3 | root 等 30 s 收不到 HELLO，inmate 日志说"已发过" | **IVSHMEM 内存不随 cell 重建清零**，inmate 看到上一轮的 magic 就上线，HELLO 被 root 随后的 init 抹掉 | 加 session：owner 每轮写新的 `CNTVCT` 值，对端必须看到 session **变化** |
| 4 | 改了代码、构建报成功、跑起来还是老行为 | `cp -a` 保留 PC 侧 mtime（还差 8 小时时区），make 认为源码没变；而"镜像里有 xipc"的校验串从第一版就存在 | 构建脚本强制 `touch` + 删 `*.o`；校验串换成**本版专有**标记 `xipc: session 0x` |
| 5 | 开机只打一行 `usage: xipc ...` 就结束 | `task_spawn` 会把 `CONFIG_INIT_ARGS` 塞成 `argv[1]`（argc=2），参数解析遇到不认识的直接 `return 1` | 未知参数只告警并继续；所有参数有缺省值 |
| 6 | "周期"档 p50 报出 `819.10 µs` | 100 ns × 8192 = 819 µs 的直方图，样本全撞桶顶，报出来的是**桶顶假值** | 改存原始样本再排序求分位数（几千个样本，不值得用近似） |
| 7 | 忙等档"2000 万次迭代"0.4 秒就跑完，实验还没开始就退出 | 退出条件写成迭代数，而忙等一圈只有几十纳秒 | 退出条件改成**时间**（deadline），迭代数只作上限 |

另外两条不是坑但值得记：
- inmate 侧日志必须**纯 ASCII**（中文经 mini-UART 出去是乱码）；
- 开机入口从 `fiveloop_main` 换到 `xipc_main` 而不是"关掉 CONFIG_BENCHMARK_FIVELOOP"
  ——关配置项后旧 `.o` 还会赖在 `libapps.a` 里（上一轮踩过）。

## 6. 没做 / 下一步

- **门铃（中断）**：需要 NuttX 侧最小 PCI 配置访问（置 `CMD_MEM`、启 INTx、
  接 IRQ 184）。届时可对比"门铃唤醒"与"轮询"在**空闲**场景下的差。
- **按 peer 分片的形式化**：现在用了 peer0/1/2 三片，但没有实现 Jailhouse 内置
  协议的 peer 状态表语义（`State Register` / `State Table`）。
- **未绑核**：尾部 72 µs 未归因；把 inmate 任务与 root 线程钉到固定核后应能压低。
- **接进 ECoS 规划器**（下一轮 PR10-B）：跨域边进入 DAG 后，规划器应
  ① 禁止跨域融合（除非显式允许），② 用 `≈period` 而不是 `c` 计代价，
  ③ 由验证器独立复核该代价。

# 8. PR10-B：跨域边进入 ECoS（规划 / 验证 / 生成三处都按"拍"计）

上一节量出来的数如果不能改变决策，就只是博客。这一节把它接进工具链。

## 8.1 语义：跨域边 = 只能跨拍满足

跨域边和 z⁻¹ 闭合边是**同一类东西**：生产者在一个 cell 跑完，消费者在另一个 cell，
两者没有共享的"这一拍"，消费者只能在下一个周期边界看到它。因此：

| 结论 | 依据 |
|---|---|
| 不约束同一拍内的先后 | 消费者本来就读的是上一拍的值，同拍顺序对它无意义 |
| 每条给端到端加**一整拍** | 实测 1 kHz 下跨域 RTT p50 = 1005.26 µs（≈1.005 拍） |
| 环上 C 条跨域边 ⇒ 死区至少 C 拍 | 同上，每跨一次域就得多等一个边界 |
| **跨域融合不存在** | 融合 = "一次释放里连续跑几个阶段"；两个 cell 各有内核与调度器 |

最后一条写成**硬约束，不给开关**。设一个 `--allow-cross-domain-fusion` 只会让人以为
"调一下就能跨域融合"，而那是物理上做不到的事。规划器拒绝、验证器独立复核、代码生成器
也拒绝（`emit` rc=6，因为一个宿主不可能同时属于两个 cell）。

## 8.2 实现

```
kfusion/scripts/ecos/domain_model.py   ← 域语义唯一实现（规划器与验证器共用）
kfusion/scripts/ecos/plan_verify.py    ← 独立复核 DOMAIN_MIXED / XDOM_DEADLINE
kfusion/scripts/fusion_plan__融合规划.py ← 组内域纯度 + 端到端按拍计 + 死区按拍计
kfusion/backend/synthesis/emit.py      ← 跨域方案拒绝合成（rc=6）
```

DAG 里节点级 `domain` 字段即可声明（`"domain": "nuttx"` / `"root"`）；不写就是单域，
**现有所有夹具行为不变**。域信息出现在三处：`plan.meta.cross_domain`（统计）、
每个组的 `domain`、`cost.cross_domain_periods / cross_domain_extra_us`。

## 8.3 实测（夹具 `xdom_loop`：同一条闭环，前三段 NuttX，后两段 root）

```
方案：2 组
  g0   stage_sample + stage_fir + stage_pid        （nuttx）
  g1   stage_clamp + stage_plant                   （root）
代价
  释放税 2×21 = 42 µs ｜ 段内 R̂ ≈ 621.8 µs
  跨域：2 条跨域边 stage_pid→stage_clamp, stage_plant→stage_sample
        ｜ 端到端多 1 拍 × 1000 µs = 1000 µs ⇒ **含跨域 1621.8 µs**
反馈环
  闭合边 stage_plant→stage_sample 间隔 200 µs → **1400 µs**（×7.00）
```

三个值得看的点：

1. **段内只有 621.8 µs，看着很健康；加上跨域那一拍就是 1621.8 µs。**
   期限如果按 1000 µs 给，规划器报 `跨域期限` 并拒绝——而"段内"检查会一路放行。
   这就是必须按拍计的原因：差三个数量级。
2. **死区从 200 µs 变成 1400 µs**：1 拍来自 z⁻¹，另 1 拍来自跨域。两笔都要算。
3. **不能全融合了**：`不可合并：…（跨域：段内成员分属 nuttx / root，融合要求同一次
   释放…）`。同样一条闭环，单域时 1 组、跨域时 2 组——省下的唤醒税也不同。

## 8.4 顺带修掉一个真的 bug（域切开后才暴露）

规划器的"不可分性"检查原来用**全边**传递闭包（含 z⁻¹）。有环的图里这会造成假阳性：
`stage_clamp` 经由 `plant→sample` 的 z⁻¹ 边能绕回 `stage_sample`，于是
`stage_sample + stage_fir` 被判成"clamp 必须夹在中间"——跨域切开后**每一对**相邻阶段
都被误拒。

修法：不可分性只用**同拍**可达（摘掉闭合边与跨域边后再算闭包）。验证器一直是这么算的
（它只喂 `same_cycle` 边），规划器不是——两边不一致本来就会产出"规划说不可行、
验证说合法"的鬼故事。修完规划器给出正确的 2 组。

## 8.5 回归

- 融合自测 79 → **88**（§27 域纯度 / §28 代价按拍 + 死区 2 拍 / §29 验证器独立复核）
- 后端自测 50 → **55**（§11：跨域方案 emit 拒绝 rc=6、拒绝即停、不误伤单域）

## 8.6 没做

- **两个域各自合成一份产物**：现在 `emit` 直接拒绝跨域方案。正解是把 plan 按域拆开、
  各配自己的阶段源码分别 emit，再用 PR10 的环把两端连起来——需要 `ecos_build` 支持
  `--split-by-domain`。这是 PR10-C。
- 跨域边的**相位对齐**没有建模（现在只算拍数，不算"哪个边界"）。
- 多域（>2）只在 unit 层面支持，没有夹具。

# 9. 一个被 bug 掩盖的旧结论：环**可以**部分融合

修掉不可分性的假阳性之后，两个既有夹具（`loop_phasepin`、`loop_fb_limit`）的结论变了，
这个变化比 bug 本身更值得记。

## 9.1 旧结论错在哪

项目里长期记着一条判据：**"SCC 上不可分性自动成立 ⇒ 环只能整体成组"**。它来自同一个
全边闭包：环里任意两个成员之间总能找到第三个成员（绕 z⁻¹ 边绕回来），于是任何切分都被
判"不可分"。但这恰恰是假阳性——**z⁻¹ 边跨的是两拍**，"中间夹着"在拍内不成立。

摘掉延迟边后，周期性环是一条**链**：

```
sample(0) → fir(200) → pid(400) → clamp(600) → plant(800) →[z⁻¹]→ sample(下一拍 0)
└────────────── 同一拍，顺序固定 ──────────────┘   └── 跨拍 ──┘
```

所以部分融合是合法的，条件是两条：**同拍边顺序不变**、**死区上限不被突破**。

## 9.2 实际变化

| 夹具 | 旧（假阳性） | 新 | 死区 |
|---|---|---|---|
| `loop_phasepin` | 5 组（被"环"强行全拆） | **2 组**：`sample+fir+pid+clamp` ｜ `plant` | 200 → 200 µs |
| `loop_fb_limit` | 5 组（同上） | **2 组**：`sample+fir+pid` ｜ `clamp+plant` | 200 → **400 µs**（上限 500，合法） |
| `five_stage_loop`（无上限） | 1 组 | 1 组（不变） | — |

`loop_phasepin` 里挡住全融合的其实是**相位钉住**（`plant` 读外部输入，前拉 800 µs 等于
提前采样），跟环是不是 SCC 无关。`loop_fb_limit` 里死区上限 500 µs 是**硬约束**、
不是优化目标：拉到 400 µs 没越限就合法，而 2 组的 R̂（621.8 µs）比 5 组（821.5 µs）更好。

两个夹具的新方案都过了独立验证器——规划器与验证器给出同一个结论，这正是修好一致性后
该有的样子（以前是两边都错得一样）。

## 9.3 因此改判的判据

> ~~SCC 上不可分性自动成立 ⇒ 环只能整体成组~~
>
> 正确判据：**不可分性只由同拍边决定**（摘掉 z⁻¹ 闭合边与跨域边）。
> 周期性环摘掉延迟边后是链，可以部分融合；真正拦住它的是相位钉住、
> 死区上限、控制窗这些**独立**约束。

# 10. PR10-C：按域拆成两份产物，跨域数据过环

PR10-B 定了"跨域融合不存在"，PR10-C 把这条约束**落到产物上**：一份跨域 plan 拆成
每域一份，各自生成各自的宿主，中间的共享全局改成过环的消息。

## 10.1 为什么必须改成交信，不能继续共享全局

单域部署里 `g_act` 是一次 store + 一次 load。跨域部署里如果两端仍然各自读写自己的
`g_act`，**跑起来不报错、结果全错**——两个 cell 的 `g_act` 是两份独立内存。

所以拆分器要把"哪些全局要过环"从 DAG 边的 `evidence`（`@g_act`）里读出来，写进
接口描述；生成器据此在阶段调用前后插发布/订阅。没有证据的跨域边**直接报错退出**，
不生成"两端互不相干"的产物——那不是降级，是错的。

## 10.2 产物形态

```
plan.json（跨域，已验证）
   └─ split_plan ─► OUT/interface.json        （哪条边、哪个全局、哪个方向）
                 ├─ OUT/nuttx/{plan,meta}.json
                 └─ OUT/root/{plan,meta}.json
                        │
        emit --xdom meta.json（每域各跑一次）
                        │
        ├─ nuttx/  ecos_nuttx_main.c + ecos_fused_body.c + ecos_xdom.c + Makefile
        └─ root/   ecos_fused_linux.c  + ecos_fused_body.c + ecos_xdom.c + Kbuild
```

生成的周期体（nuttx 侧，注意插点位置）：

```c
void ecos_body_g0(void)
{
	ecos_xdom_sub(1, &g_plant);	/* 跨域输入：通道 1，来自 root 域 —— 在 sample 之前 */
	stage_sample();
	stage_fir();
	stage_pid(1000);
	ecos_xdom_pub(0, g_act);	/* 跨域输出：通道 0，发往 root 域 —— 在 pid 之后 */
}
```

两个插点位置都是**语义要求**，不是排版偏好：
- 订阅必须在消费阶段**之前**：晚一个周期，可用时刻就晚一个周期。
- 发布必须在产生阶段**之后**：同理。

## 10.3 桥本身（`ecos_xdom.c`）

只做三件事：init 时按本域角色把两个环的地址定下来、pub 把 int32 塞进槽、
sub 把本通道**最近一条**取回。没有线程、没有锁、没有定时器——调度归宿主，桥只搬字。

环的选择写在生成物里，不靠运行时猜：root 域 out=`0x0000`/in=`0x3000`，
nuttx 域相反（与 PR10 的 peer 分片一致）。

订阅只取最近一条、丢弃积压——跨域读的本来就是上一拍的值，攒着只会读到更旧的数据。

## 10.4 门（三条，都有负向用例）

| 情况 | 行为 |
|---|---|
| 父方案没有验证凭据 | 拆分拒绝（rc=3）。拆分不产生合法性 |
| 方案里有组跨域 | 拆分拒绝（rc=3），理由写"融合要求同一次释放" |
| 跨域边没有 `evidence` | 拆分拒绝（rc=3）。否则会生成两端互不相干的产物 |
| 拿**未拆分**的跨域 plan 直接 emit | rc=6（PR10-B 的门 0，仍然有效） |

## 10.5 回归

后端自测 55 → **79**（§12：拆分组网/接口内容/方向、三条拒绝门、桥的生成与接线、
Kbuild/Makefile 把桥编进去、桥里没有调度原语）。

## 10.6 还没做（下一站）

- **两端一起上板**：现在是"生成完毕"，还没有在 Pi4 上一次跑通 nuttx 端 + root 端，
  用 `--digest-var g_act` 对两侧的值。这是 PR10-D。
- 桥目前只传 **int32**。控制量够用，但结构体/数组要另定帧格式。
- 订阅没有超时/陈旧检测：对端没起来时读到的是初始值，不会报错。

# 11. PR10-D：两端一起上板 —— 跨域闭环跑通，以及一个被算出来但没人看的数

§8.3 的规划器早就算出一个数：跨域闭环的**死区从 200 µs 变成 1400 µs（×7）**。
那一节把它当作"代价变大"的记录，没人问下一个问题：**这个延迟下，回路还稳不稳？**

这一节上板回答了这个问题。

## 11.1 装置

```
Pi4B ｜ jailhouse v0.12-342 ｜ 内核 5.15.86
  cell 0（root）  = CPU 0,2,3    ← root 端：stage_clamp + stage_plant
  cell 1（inmate）= CPU 1        ← NuttX 端：stage_sample + stage_fir + stage_pid
两域之间：PR10 的 IVSHMEM 环（r2i / i2r 各 224 槽）
参考周期 1 kHz（1000 µs）
```

同一份 `five_stage_loop__闭环五阶段示例.c` 拆成两份 `stage_impl.c`（各自编译），
周期体 `ecos_fused_body.c` 两端**逐字节相同**。

## 11.2 跑通了：数据真的过环

NuttX 侧（inmate，只有物理 mini-UART，看得到输出）每 1000 拍报一次：

```
ecos: periods=4000  g_act=1253 g_plant=1066
ecos: periods=5000  g_act=1189 g_plant=1076
ecos: periods=6000  g_act=1014 g_plant=1285
```

root 侧（`/sys/module/five_stage_loop/parameters/`）：

```
periods=5009 g_act=1088 g_plant=821
periods=8025 g_act=687  g_plant=703
```

三条独立证据，说明"环通了"不是错觉：

1. **通向前 `g_plant` 恒为 0**：root 模块还没加载时，NuttX 侧订阅不到任何东西，
   `g_plant=0`（发了 4,024,000 拍都是 0）。root 模块 `insmod` 之后，
   `g_plant` 立刻变成 1066/1076/1285/821/1335… 并且持续在变。
2. **反向也通**：root 侧的 `g_act` 同样在变（1088 → 687），说明 NuttX 发的
   `g_act` 被 root 收到了。
3. **同一个值出现在两侧**：root 侧读到 `g_plant=821` 的那一拍，NuttX 侧
   `periods=7000` 报出的也是 `g_plant=821`。跨域传输的是**同一个数**，
   不是两个各自算出来的相似数。

环本身的可靠性也量了：整个实验期间 **386738 条消息，drops = 0**。

## 11.3 但值在发散 —— 而单域不发散

跑起来之后 `g_act` 不在 1000 附近，而是长到 ±90000：

```
root   14:17:36 g_plant=6332   g_act=-66712
       14:17:39 g_plant=19616  g_act=-73962
nuttx  periods=157000 g_act=-87880 g_plant=-3236
```

先排除"是不是这个回路本来就不稳"。用 §3 的参考模型（与 C 侧逐位相同的整数语义）
跑单域轨迹：

| 拍数 | 单域 g_out | 单域 g_plant |
|---|---|---|
| 100 | 1776 | 1435 |
| 1000 | 1240 | 1147 |
| 10000 | 907 | 1072 |
| 50000 | 1386 | 1062 |

**单域稳定收敛在 1000 附近**（积分项始终在 ±100000 限幅内、没打满）。所以发散
不是 plant 的动力学，是**跨域引入的**。

## 11.4 根因：跨域边让反馈延迟从 1 拍变成 2 拍

把参考模型里"sample 读到的 plant"改成读 k 拍前的值：

| 反馈延迟 | n=100 | n=1000 | n=20000 | 形态 |
|---|---|---|---|---|
| **1 拍**（单域） | g_out=1103 | 446 | 1783 | 稳定在 ~1000 |
| **2 拍**（跨域） | g_out=-1452 | **-42632** | **-39796** | ±60000 振荡、积分打满 |
| 3 拍 | 6479 | 60000 | -17236 | 同样发散 |

**2 拍延迟的形态与板上实测完全同构**（±60000 量级振荡、积分项打到 ±100000 限幅）。

时序上也能对上：

```
单域（一拍一次释放，五个阶段都在同一拍）
  t=0    sample 读 g_plant   ← 上一拍 800µs 写的值，延迟 1 拍
  t=200  fir
  t=400  pid   → g_act
  t=600  clamp → g_out
  t=800  plant → g_plant     ← 下一个 t=0 才被读

跨域（两个 cell 各有内核与调度器，没有共享的"这一拍"）
  NuttX 拍起点(0µs)  sample / fir / pid → 发 g_act
                                      ↓ 过环（≈1 拍，PR10 §3.2 实测 1005 µs）
  root  拍中(600µs)  clamp / plant     → 发 g_plant
                                      ↓ 过环（≈1 拍）
  NuttX 拍起点(0µs)  sample 读到的，是**两拍前**的 g_plant
```

反馈边的延迟 = 原有 1 拍（z⁻¹） + 跨域那 1 拍 = **2 拍**。§8.3 的规划器算的
"死区 200 → 1400 µs"就是这件事（200 + 1000 + 200）。

**这不是 bug，是设计使然**：PR10-B §8.1 已经把"每条跨域边加一整拍"写成了硬约束，
死区按拍计也是这么算的。**缺的从来不是算，是没人拿这个数去问闭环还稳不稳。**

## 11.5 工具链缺的那一扇门

先说清楚**已有的**是什么：`plan_verify.py` 里有一条反馈死区检查（`FEEDBACK_FUSED`），
它判的是"反馈边若并入同一组（= 融合），死区≈一整拍，超过契约上限就报错"。
这条检查本身是对的，但它只覆盖**融合**那一种让死区变大的成因。

而**跨域是另一种成因，它完全没被判**：反馈边跨了组时（`gid_of[a] != gid_of[b]`），
上面那条检查直接跳过——于是"死区因为跨域而翻倍"这件事，在验证器里是**静默**的。

于是链路上出现了一个具体的洞：

- 规划器算出了死区拍数（§8.3 的"死区 200 → 1400 µs"），并写进方案；
- 验证器独立复核了死区拍数（跨域边按拍计那部分），也通过了；
- 但**没有任何一处**拿"死区 = 2 拍"这个数去问"这个延迟下闭环还稳不稳"。

后果是具体的：一条 `xdom_loop` 夹具在单域下是稳定的闭环，
拆到两个 cell 之后就发散，而工具链一路绿灯放行、两个后端都构建成功、
板上也确实在跑——**所有环节都"成功"了，只有一个数不对**。

要补的检验（下一站）：把被控对象 + 控制器 + 反馈延迟做成可分析的形式，
在规划阶段就判"这个跨域拆分会不会让闭环失稳"，失稳就**拒绝拆分**并说清
"延迟从 1 拍变 2 拍，这个夹具在 2 拍下发散"。

判据可以挂在现成的契约字段上（`feedback_delay_max_us`）：反馈边的**总**延迟
（原有拍数 + 跨域带来的拍数）与上限比，超了就报错。

两个实现上的坑（查的时候踩到的）：

1. **反馈延迟的拍数不能把闭合边自己算两遍**。跨域闭合边既带原有的 1 拍，
   又带跨域那 1 拍；环上**别的**跨域边才额外加拍。算重了会得到 3 拍。
2. **`xdom_loop.contract.json` 的字段位置和其他契约不一样**：它把
   `feedback_delay_max_us` 放在**顶层 `control`** 下，而 `plan_verify.py` 与
   `contract_validate.py` 读的都是 `timing_constraints`。所以这个夹具的上限
   **从未被读到过**（其余 7 个契约都在 `timing_constraints` 下）。
   校验器也不报错——它压根没看那个字段。跨域夹具的契约要么挪位置、
   要么校验器认两种位置，这笔账得在实现稳定性门的时候一起结。

注意这不能靠"跑几拍看看"来判——那就退回到实测了。可行的方向是：
对线性化的闭环算离散特征根，或者退一步做"延迟预算 vs 对象时间常数"的
必要条件筛查（这个夹具的对象是一阶 `(3y+u)/4`，时间常数 4 拍，1 拍延迟能稳、
2 拍就压不住）。

## 11.6 踩到的坑（这一版修的）

### 坑 1：NuttX 入口名与 PROGNAME 必须一致（链接期才炸）

NuttX 的 builtin 注册表由 `apps/Make.defs` 的 `REGISTER` 宏**按 app 的 `PROGNAME`
自动生成**，注册项引用的符号固定是 `<PROGNAME 去横线>_main`；同时 `Application.mk`
给 MAINSRC 传 `-Dmain=<PROGNAME 去横线>_main`，把源码里的 `main` 改名成它。

跨域那版把 `PROGNAME` 设成 `fiveloop`（复用板上已打开的
`CONFIG_BENCHMARK_FIVELOOP`）、入口函数却叫 `xdom_main` → 注册表引用
`fiveloop_main`、源码只给 `xdom_main` → 链接期 `undefined reference`。

**第一次构建能过纯属侥幸**：NuttX 的 `libapps.a` 会保留历史成员，上一轮构建的
`fiveloop_main.c.o` 还在归档里顶着这个符号。等到注册表被重新生成、归档被重建，
这个符号消失，缺陷才暴露。

修法：入口名**由 `PROGNAME` 派生**（`--nuttx-progname`），显式给不一致的
`--nuttx-main` 就在**生成期**报 rc=2，不留半成品目录。板上构建脚本也改成
从 Makefile 读回 `PROGNAME`、派生符号、核对源码里的入口名，不一致直接退出。

### 坑 2：改了 `.config` 之后不要并行重建 NuttX

NuttX 的 `.depend` 依赖 `$(TOPDIR)/.config`。改了 `.config`（本例是开机入口）
→ 全树 `.depend` 失效 → `make` 要重跑 `pass1dep`/`pass2dep` 重新生成 `.ddc`。
`-j` 下两个 make 可能在同一目录里互删 `.ddc`，报：

```
cat: mm_initialize.ddc: No such file or directory
make[2]: *** [Makefile:103: makedepfile] Error 1
```

改用 `-j1` 重建依赖、只在链接阶段并行。

### 坑 3：跨域共享内存的映射类型（NuttX 侧读不到 root 写的值）

root 侧原来用 `ioremap()` 映射 IVSHMEM 块 → 那是 device/nGnRE 映射，**内核绕过
cache 直读内存**。而 NuttX 侧的 `up_clean_dcache` 只清到 PoU（L2），数据不一定落到
DRAM。于是现象是：**用户态看得见、内核看不见**（模块里 `xr_in->head` 恒为 0，
而对端明明在发）。

改用 `ioremap_cache()`（与对端 MT_NORMAL 的内存类型一致）后立刻通。

反向也有一条对称的要求：NuttX 侧等待环就绪的循环**必须先失效再读**。
那一侧的映射是 cacheable 的，而 owner 是**另一个 cell**；第一次读若发生在 owner
初始化之前，那一行就带着旧值常驻缓存，之后永远看到"未就绪"（实测等满 30 s 放弃）。

### 坑 4：不要用"periods 在涨"当正确性证据

`periods` 在涨只证明调度在跑。真正证明"算得对"的是：单域用参考模型逐位比对
（`ref_model_five_stage.py --compare`），跨域用**同一个值在两侧都出现**来比对。
§11.2 的第 3 条证据就是后者。

# 12. PR10-E：把"反馈死区"变成一条真的会拒绝的门

§11.5 把洞说清楚了：规划器算出了死区（200 → 1400 µs），验证器也复核了跨域拍数，
但**没有任何一处**拿"死区 = 2 拍"去问"这个延迟还合不合约束"。这一节把它补上。

## 12.1 三个具体的漏判

动手前先把洞拆成三条可验证的，而不是笼统的"缺少稳定性检查"：

1. **上限根本没被读到。** `xdom_loop.contract.json` 把
   `feedback_delay_max_us` 写在**顶层 `control`** 下，而 `TemporalModel` /
   `contract_validate` 读的是 `timing_constraints`。于是这份夹具的反馈上限
   **从未生效**，校验器也不报错——它压根没看那个字段。
2. **验证器只判"融合"，不判"跨域"。** `plan_verify.py` 的反馈死区检查条件是
   `gid_of[a] == gid_of[b]`（反馈边并入同一组）。反馈边跨组时——**跨域恰恰
   就是跨组**——检查直接跳过，死区翻倍这件事在验证器里是静默的。
3. **两套实现。** 死区公式 `(1+xd)*period + t_cons - t_prod` 只存在于
   `fusion_plan__融合规划.py::recurrence_report` 里。验证器没有这份公式，
   自然也就没有判据。上一轮（P0-2）已经吃过一次"算得出的和验得出的不是一个
   定义"的亏，这里是同一类病。

## 12.2 改法：公式只留一份，判据也只留一份

死区计算搬进 `temporal_model.py`（这个项目里"时间语义唯一实现"的地方）：

```python
dead_us = (1 + xd) * period + t_cons - t_prod      # xd = 1 表示跨域
```

- `1` 是闭合边自身的 z⁻¹：生产者相位晚于消费者，一拍之内不可能满足，
  只能等到下一个周期边界；
- `xd` 是跨域附加的那一拍（PR10 实测 1005.26 µs ≈ 1.005 拍）；
- `t_cons - t_prod` 是两者在各自组内偏移之差（含释放代价与执行时间）。

⚠ **两笔不能分开各加一次**。跨域闭合边"既是 z⁻¹ 又是跨域"，但它们在描述
同一个"等到下一个边界"，所以合并成 `(1+xd)`。分开累加会把 2 拍算成 3 拍——
PR10-E 实现时确实先写成了 3 拍，靠"代入夹具应有 1399 µs"才发现。

新增两个接口，规划器与验证器**都调它**：

| 接口 | 作用 |
|---|---|
| `TemporalModel.feedback_delays(groups, dom, sched)` | 给出每条闭合边的总死区 + 来源分解（z⁻¹ 几拍、跨域几拍、生产/消费偏移） |
| `TemporalModel.feedback_violations(...)` | 按契约上限判，返回 `(errors, warnings)` |

`sched` 用统一时间线的**实际开始时刻**（含组间积压），不是名义相位——
被积压推后的组只会让死区更长，用名义相位会低估。

## 12.3 三条新判据

| 诊断码 | 触发条件 | 为什么是**错误**而不是提示 |
|---|---|---|
| `FEEDBACK_DEADZONE` | 反馈边**跨组**且死区 > 契约上限 | 跨域会把死区多加一整拍；超限就没有任何证据说这一步保住了时序语义 |
| `FEEDBACK_CONTRACT_MISSING` | **这条反馈边自己跨域**，但契约没给上限 | 没有上限就无法证明；按 fail-closed 拒。反馈边不跨域（只是方案别处跨 domain）不强行要求——那种情形死区仍是一拍，与单域同构 |
| `FEEDBACK_MODEL_UNPROVEN` | 契约声称 `evidence.exec=bounded` 却没有 `wcet_us` | 只有实测均值却标"已证明"，等于拿经验预测冒充硬实时证明 |

原有的 `FEEDBACK_FUSED`（反馈边并入同组 ⇒ 死区≈一整拍）保留，只是现在
和跨域那一条共用同一个死区公式。

另外把契约校验器改成**拒绝** `control.feedback_delay_max_us` 这个位置，
并明确提示"放错位置等于这条约束不存在"——静默忽略是这次事故的起点。

顺带修掉一句已不准确的提示：原来 `feedback_delay_max_us ≥ period` 时警告
"等于没有限制"。有了 2 拍判据之后这句是错的：它拦不住一拍以内的死区（融合），
但**仍然约束两拍以上的情形**——跨域夹具正是 1400 µs 被 1000 µs 的上限挡住。

## 12.4 为什么用两份契约而不是改一份

`xdom_loop.contract.json` 的 2500 µs 是这个夹具的**应用要求**，不该为了让测试
变红就篡改它。所以：

| 契约 | 反馈上限 | 期限 | 期望 |
|---|---|---|---|
| `xdom_loop.contract.json` | 2500 µs | 2500 µs | 跨域方案**合法**（死区 1400 在内） |
| `xdom_loop_strict.contract.json` | **1000 µs** | 2500 µs | 跨域方案**被拒**（死区 1400 超限） |

两份契约只差反馈上限，其余（DAG、期限、执行时间）完全相同。于是"拒绝"这件事
只能归因于反馈死区，不能赖到期限或域能力上——这也是负向用例该有的形态。

## 12.5 实测（工具链内部，不是板上）

```
宽契约（2500 µs）：规划器 rc=0 ｜ 验证器 rc=0
  闭合边 stage_plant → stage_sample   间隔 200 µs → 1400 µs（×7.00）
  ⚠ 反馈边 stage_plant→stage_sample 死区 1400 µs，跨域 +1 拍（上限 2500 µs）

严契约（1000 µs）：规划器 rc=3 ｜ 验证器 rc=3   ← 同一份方案、同一句理由
  ❌ [FEEDBACK_DEADZONE] 反馈边 stage_plant→stage_sample 跨组（g1 → g0），
     死区 = 2 拍（z⁻¹ 1 拍 ＋ 跨域 1 拍）＝ 1400 µs，超过上限 1000 µs
```

**"规划器和验证器给出同一个结论"是这一节真正要交付的东西**，不是那条 1400。
以前规划器算 1400、验证器不看，两边都"成功"，只有板上发散。

## 12.6 这一节**没有**证明什么

- 死区在上限内 **≠ 控制稳定**。编译器只能证明"满足声明的时间契约"，
  稳定与否要靠被控对象模型独立分析。文档与拒绝消息都写明了这一点。
- 这条门拦的是"反馈延迟超限"，**不是**"回路一定发散"。xdom_loop 在 1400 µs
  下确实发散了（§11.4），但那是这个夹具的对象特性；换个对象，同样 1400 µs
  可能很稳。工具链不该假装知道对象动力学。
- 逐拍数据版本（第 k 拍读到第几拍的数据）还没有。这是 PR10-F。

## 12.8 给下一站的两条限制

**一、时间模型还是单核顺序递推。** `TemporalModel.schedule()` 用的是

```
S_g = max(φ_g, F_{g-1}) + L
F_g = S_g + Σ C_i
```

这个递推对**单域融合**是对的（同一次释放里串行跑），但它描述不了
"Linux 在 CPU 0,2,3、NuttX 在 CPU 1 **同时**执行"这件事。所以 PR11-B 不能
只是给这个公式加一个通信常数——那等于假设两个域仍然串行。要建的是
**多执行域事件图**：每个域各自约束 CPU 占用，跨域依赖单独约束
"生产完成 → 通信可用 → 目标消费"三个时刻。

本节新增的 `feedback_delays` 之所以要 `sched` 参数代入而不是自己再算一遍，
就是为了将来换成多域时间线时，死区判据能**自动跟着换**，不用改两处。

**二、PR10-F 的两个已知缺陷（还没修）。** 逐拍数据版本要动 IPC 协议之前，
先把这两条记下来：

- `xdom_bridge.py` 生成的订阅循环返回的是**第一条**匹配消息，不是注释写的
  "最近一条"——注释与实现不符。
- 多个通道共用一个接收环时，为找 A 通道可能在遍历中把 B 通道的消息**消费掉**
  （`xipc_pop` 是出队）。环通的实验里没暴露，是因为这个夹具两通道各用一条环。
  正确做法是"每拍先统一排空、按通道更新本地缓存；阶段消费时只查缓存"，
  而不是在共享环上直接找。

> ⚠ 上面两条已在 **§13（PR10-F）** 修复：订阅改成按通道分桶缓存、取最近一条；
> 版本化协议也一并做了（release_id / session_id / publish_tick 三个标识各归其位）。
> 另外 Linux emitter 的 `pending` 裸 bool 仍未替换——那是 PR10-F 之后、
> 严格周期配对实验（PR11-A）之前要做的前置，见 §13.7。

# 13. PR10-F：版本化跨域 IPC —— 三个标识各归其位，订阅不再吞通道

§12.8 记了两条待修缺陷，这一节把它们落地，并把"逐拍追踪"需要的版本化字段补齐。
改动集中在三个文件：`kfusion/runtime/xshm/ecos_xipc.h`（协议与环）、
`kfusion/backend/synthesis/xdom_bridge.py`（生成的桥）、两个宿主发射器
（`linux_kernel_emitter.py` / `nuttx_emitter.py`）。

## 13.1 三个版本标识各映射到哪

PR10-F 要的 `release_id` / `session_id` / `publish_tick` 不强求新发明三个字段，
而是把现有的和新增的明确对上号：

| 标识 | 落点 | 说明 |
|------|------|------|
| `release_id` | 环槽 `seq` | 生产者每发一条 `seq = head+1`，单调递增、随 session 复位。跨域读它即可知"这是第几条"。 |
| `session_id` | 环头 `session` | owner 每轮用 `xipc_counter()`（两侧共享物理计数器，见 §4 时间基准）生成，作为 epoch。 |
| `publish_tick` | 环槽新增 `tick` | **新增**。生产者发布时的控制周期索引，由宿主每周期写入 `ecos_xdom_cycle`。 |

为什么 `publish_tick` 必须新增字段、不能靠 `seq` 凑：跨域按拍追踪要的是"这条值属于
生产者第几个控制周期"，而 `seq` 是环内发布序号（会随环复位、且按发布次数而非周期数
增长）。只有显式戳周期索引，消费者用 `自己周期 − publish_tick` 才算得出跨域延迟拍数
（含 z⁻¹ 一拍 + 跨域一拍，与 PR10-D/PR10-E 的结论呼应）。

## 13.2 扩槽：16 → 20 字节，协议版本 1 → 2

旧槽只有 `seq/kind/a/b`（16 B），放不下 `tick`。改动：

- `XIPC_VERSION` 1 → 2（HELLO 携带的协议号同步变，两侧必须同时重编——本来就共用同一份头）。
- 槽加 `volatile uint32_t tick;`，`XIPC_SLOT_BYTES` 16 → 20。
- 容量约束从"一个环 ≤ 4096"放宽到"≤ peer 片 `XIPC_PEER_STRIDE`（0x3000）"。
  224 槽 × 20 B + 256 B 头 = 4736 B ≤ 12288，**槽数 224 不变**，控制回路的环容量一点没降。
- 新增 `xipc_pub_ticked(r, kind, a, b, tick)`；旧 4 参 `xipc_pub` 保留（管理消息 `tick=0`），
  所以 `root_side.c` 与 `xipc_main.c` 这一版**不用改**。

## 13.3 多通道消费 bug：改成按通道分桶缓存、取最近一条

旧 `ecos_xdom_sub`（PR10-C）是

```c
while (xipc_pop(xr_in, &s)) {
    if (s.kind == XIPC_KIND_DATA && s.a == channel) { *dst = s.b; break; }
}
```

两个毛病（§12.8 已点名）：

1. 返回的是 **FIFO 最旧**匹配消息，不是注释写的"最近一条"——同通道连发两次只会拿到第一次的。
2. 为找本通道，可能把**别的通道**排在它前面的消息 `pop` 掉并丢弃（消费即出队）。
   只要某周期 A 通道消息前恰好排了 B 通道消息，且 `sub(A)` 先于 `sub(B)` 执行，B 就丢失。

新实现：每个域一份**按通道分桶的本地缓存**，一次 `sub` 调用把 in 环**抽干**到各桶
（最近一条覆盖旧的），再从自己的桶取。这样 `sub(A)` 不会饿死 `sub(B)`，且取到的是
本通道最新值。新增 `ecos_xdom_sub_tick(channel, &v, &tick)` 顺带把 `publish_tick` 带出，
供宿主做按拍追踪。

> PC 端无 C 编译器，这份新语义用 `kfusion/scripts/test/xipc_versioned_model.py`
> 纯 Python 复刻并断言（§32 融进融合自测）；该模型也**复现了旧桥的两个 bug**，
> 证明修复不是空谈。板上编译验证见 §13.7。

## 13.4 跨域按拍追踪

宿主每周期把控制周期索引写进全局 `ecos_xdom_cycle`，`ecos_xdom_pub` 把它作为
`publish_tick` 戳进消息。对端在周期 C 调 `ecos_xdom_sub_tick` 拿到值 v 与发布周期 P，
则跨域延迟拍数 = `C − P`。这个值天然包含 PR10-D/PR10-E 论证的"z⁻¹ 一拍 + 跨域一拍"，
于是"发散 / 收敛"不再只能靠看曲线，而能用每拍的延迟拍数直接判定。

宿主侧接线：`linux_kernel_emitter.py` 在每组 `ecos_run_body` 前、`nuttx_emitter.py`
在组循环前各插一行 `ecos_xdom_cycle = periods;`（**仅当方案含跨域时**才生成，
无跨域方案不引用这个全局，避免链接期未定义）。

## 13.5 epoch 统一（已实现，这里点明）

`session` 由 `xipc_counter()` 生成，而 Jailhouse 不陷获/偏移 `CNTPCT`/`CNTVCT`，两侧
读同一个物理计数器（§4 已 grep 确认）。所以 owner 写一次 `session`，对端读到的就是与
生产者**同一个** epoch 令牌——统一 epoch 是既有事实，不是新加的代码。桥新增
`ecos_xdom_epoch()` 把本域所见 `session` 暴露出来，方便宿主在日志里核对两端 epoch 一致。

## 13.6 这一节**没有**证明什么

- 本机没有 C 编译器，C 改动**尚未在 Pi 上编译**，运行时正确性靠 Python 模型等价复刻 +
  融合自测 §32 覆盖；**板上编译 / 环回 ping / 真实跨域回路**仍待 §13.7。
- 协议版本升到 2，意味着 root cell 与 inmate 必须**同时**用新头重编；旧 v1 镜像与新 v2
  镜像混跑会因槽布局不一致而数据错乱。上板前要把 `ecos_xipc.h` 同步到 NuttX 侧并整编。
- 同 §12.6：版本化只证明"携带并核对了时间标识"，**不等于**控制稳定。
