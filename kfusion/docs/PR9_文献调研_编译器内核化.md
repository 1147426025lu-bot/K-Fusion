## 0. 目的、范围与"内核化"两层定义

### 0.1 背景
- PR6/7/8 已完成并推送（`e7352c8`）：融合规划器升级为**失败封闭（fail-closed）的约束优化器**——含不确定性门禁（PR6）、相位感知端到端响应模型（PR7）、控制语义硬约束（PR8）。
- PR9（评审建议）= **kernelized toolchain integration**：把"融合规划 + 代码生成"搬进目标侧运行，弱化对 PC 端交叉工具链的依赖。

### 0.2 "内核化"的两层（必须先分清，否则会与既有工作混淆）
项目里其实已有两种"内核化"，**不要把已完成的当成 PR9**：

| 层 | 含义 | 现状 |
|----|------|------|
| **L1 输出侧内核化** | 融合后的控制逻辑被编译成**内核模块 `.ko`**，载入 root-cell Linux 内核运行 | **已有脚本** `scripts/plc_kernelize__内核化.sh`（`KERNELIZE__内核化流程.md`）；fused IR → `kernel.o` → `.ko` |
| **L2 工具链侧内核化（PR9）** | 把**融合规划器 + 代码生成**本身搬进目标内核 / Jailhouse cell 内运行，支持**板上重融合（on-target re-fusion）** | **未做**，本文调研对象 |

> 本文的"编译器内核化"一律指 **L2**。L1 是 L2 的下游（无论规划器在 PC 还是板上跑，最终产物都经 L1 链路变成 `.ko` / inmate 镜像）。

> **⚠ 2026-10-24 晚修订（请先读 §6）**：第二轮外部审查（针对 `95293b8`）给出了与本文结论**相反**的建议
> ——**暂缓 L2**，把 PR9 重定义为"经过完整验证的端到端内核化闭环"（可信验证 → 时间语义 → `.ko`/NuttX 双后端）。
> 复核后**采纳该建议**，理由见 §6：L2 的代价（TCB 扩大、动态代码加载、故障恢复）不是 ECoS 当前瓶颈，
> 而"板上重融合"作为卖点在有更硬的证据之前不宜作为论文主线。§3–§5 保留作为文献事实，不再作为路线主张。

### 0.3 锚定定义（来自任务 #24）
现状：融合规划器 `fusion_plan` + `fusion_codegen` 是 **PC 端 Python/C 工具链**，输出融合后的 C（如 `fiveloop_main.c`）→ 编译成 root-cell 应用或 NuttX inmate（`nuttx.bin`/`.so`）→ 经 tar/scp 部署到 Pi4 的 Jailhouse cell。
L2 目标：把"融合规划 + 代码生成"搬进 **root cell 内核 / non-root inmate 内核** 运行，使控制 DAG 能在板上/单元内被融合并编译，支持板上重融合与自适配。

## 1. 相关工作中分类

### 1.1 内核内 / 单元内代码生成与 JIT —— PR9 *机制* 最接近
| 工作 | 要点 | 与 L2 关系 |
|------|------|-----------|
| **eBPF**（verifier + JIT，Linux 内核） | 沙箱程序在内核特权上下文运行；加载经**静态验证器**（内存安全、终止、无泄漏）+ **JIT** 编译到原生码；安全来自"数学证明而非信任开发者" | **机制蓝本**：把已验证代码载入内核运行。但面向可观测性/网络/安全，**不面向硬实时控制**，验证器保证*安全*而非*时序* |
| **JitSynth**（Van Geffen, Nelson, Dillig, Wang, Torlak；合成 in-kernel DSL 的验证 JIT） | 首个从 DSL 解释器 + 目标 ISA 合成**验证过**的 JIT 的工具；eBPF→RISC-V 避开 Linux JIT 全部已知 bug，生成 C 可直接跑内核 | 提供"如何造可信内核内代码生成器"的方法论 |
| **Kops**（arXiv 2606.24213, 2026） | 扩展 eBPF 编译管线，用"证明序列 + 原生发射"让用户在**不改动内核核心、不膨胀 TCB** 的前提下引入新操作；Lean 4 证明原生发射 == 证明序列 | L2 的 TCB 控制直接参考：内核内组件要小，新增信任仅限"原生发射" |
| **Multiverse**（Rommel et al., EuroSys 2019） | 编译器辅助的底层系统软件动态变体管理；讨论 in-kernel JIT（绑定已知参数重编译内核例程）与 eBPF 的取舍 | in-kernel JIT 的权衡（分析框架 + 整个编译器进运行时 vs. 预生成变体） |

**小结**：内核内编译/加载代码的*机制*高度成熟（eBPF 生态）。但全部面向**安全/可观测性/网络**，无一面向**硬实时控制**，且输入是手写 C/字节码，**不含"融合规划器输出"作为代码生成输入**。

### 1.2 同步语言与合格（qualified）代码生成器 —— *控制代码生成 + 认证* 最接近
| 工作 | 要点 | 与 K-Fusion 关系 |
|------|------|----------------|
| **Lustre / SCADE**（Ansys；KCG 代码生成器 DO-178C **Level A** 认证） | 同步数据流语言；SCADE 用于空客飞控、TGV、EDF 核安全；有数学语义、有界时间/有界内存；KCG 生成代码可直接纳入飞控免测 | 控制代码生成的工业标杆；但它是**完整建模语言 + 合格代码生成器**，K-Fusion 不是全同步语言 |
| **CompCert**（Rocq/Coq 验证过的 C 编译器）与**翻译验证**（translation validation） | Garion et al., CACM 69(1), 2026："Equation-Directed Axiomatization of Lustre Semantics…" 把 Lustre→C 编译器变成*可认证*编译器（Frama-C + SMT 证明生成代码 == 源语义） | K-Fusion 的 L1/L2 代码生成若要走认证，这是直接借鉴路径 |
| **IEC 61131-3**（CODESYS / TwinCAT / LogicLab） | PLC 五语言标准；扫描周期（scan cycle）执行模型；多任务（优先级/周期/看门狗）；交叉编译到裸机/RTOS | 工程侧控制代码生成；其"扫描周期 + 多任务"模型与 K-Fusion 的"周期任务 + 释放税"同构 |
| **Simulink / Embedded Coder + Polyspace** | 基于模型设计，自动生成生产级 C/C++；Polyspace 形式化静态分析（除零/溢出/越界）作为认证证据；对标 ISO 26262 / DO-178C / IEC 61508 | MBD 全栈；K-Fusion 的"边界选择优化器"是它**没有**的那一层 |

**小结**：控制代码生成从模型出发是成熟领域（SCADE/Simulink/61131-3）。K-Fusion 的*新颖处不在代码生成本身*，而在它前端的**边界选择优化器**（在已分区的控制 DAG 上决定任务边界，受时序 + 控制约束）。

### 1.3 实时任务合成 / 任务合并 —— K-Fusion *融合概念* 最接近
| 工作 | 要点 | 与 K-Fusion 融合的关系 |
|------|------|----------------------|
| **Becker 2024**（ASP-DAC, "Meeting Job-Level Dependencies by Task Merging"） | 用**约束规划**把由 job-level 依赖连接的多周期任务**合并为单任务**，消除运行时依赖实现开销，同时保持端到端时延约束 | **最强概念重合**：同是"合并周期任务以省释放/调度开销"。差异：Becker 为消除 job-level 依赖实现开销；K-Fusion 为省**释放税 G·c** 且保**控制死区语义** |
| **LazyTick**（ACM TECS） | 把多个周期 runnable 映射到**单一周期定时器**，降低释放开销与 WCET 分析的悲观度 | 同一精神（合并释放源 → 降开销/抖动） |
| **AUTOSAR OS** 工程实践 | "Task 合并 vs 拆分"是经验启发（拆太碎→调度开销大；合太多→执行过长；按实时等级而非模块分组）；CPU 利用率建议 ≤70% | 实务侧，非原则性优化器 |
| **deterministic-avionic-scheduler**（开源） | DAG 前序约束 + WCET → **零抖动循环执行表**静态合成（多核、DAG、谐波超周期） | 相关但属静态循环执行，非"融合优化器" |

**小结**："合并周期任务省释放开销"**已被研究**（Becker 2024、LazyTick）。K-Fusion 的差异化在于把合并与**控制死区硬约束 + 不确定性 fail-closed + 相位诚实建模（不把相位坍缩算收益）+ 分区 hypervisor 跨单元部署**耦合。

### 1.4 数据流 → 实时调度合成 + 代码生成 —— *DAG → 任务 + 代码* 最接近
| 工作 | 要点 | 与 K-Fusion 关系 |
|------|------|----------------|
| **ADFG**（CNRS；Fixed Priority Periodic Scheduling Synthesis from SDF） | SDF 图 → 周期性任务调度参数合成（保证缓冲不溢出/不欠载、最大化吞吐、最小化缓冲）；**生成 RTEMS RTOS 实现代码**（POSIX 线程） | **真实先例**：图 → 实时任务 → 代码。但 ADFG 目标是*一致性与吞吐*，K-Fusion 是*融合优化器*且输入含反馈/相位语义 |
| **Khatib 2018**（RTSDFG 博士论文） | 多周期系统通信用"实时同步数据流图"建模；闭式计算任务间最差/最优时延；单处理器非抢占严格周期调度（MILP + 启发式） | 时延界计算与 PR7 端到端模型同族 |
| **Choi & Ha 2017**（ACM TODAES） | SDF 图与独立实时任务共享多处理器时的 **WCRT** 估计（调度时间界分析 + 响应时间分析结合） | WCRT 分析与 K-Fusion 端到端 R 分析互补 |
| **Li et al. 2017**（Sys. Arch.） | 同步程序（SystemJ）在多核可预测核上的**设计空间探索**以静态保证反应时间；全自动映射+调度 | 多核保证反应时间的探索范式可借鉴 |

**小结**："图 → 实时任务 → 代码"有先例（ADFG→RTEMS、Simulink、SCADE）。K-Fusion 差异：输入是**含反馈/相位的控制 DAG**、核心是**融合优化器**、部署在**分区 hypervisor（Jailhouse）跨 cell**。

### 1.5 Jailhouse 工具链与 mixed-criticality —— *部署语境*
| 工作 | 要点 | 与 L2 关系 |
|------|------|-----------|
| **Jailhouse**（Siemens；openEuler 嵌入式构建指南、DeepWiki 构建文档） | 轻量静态分区 hypervisor；root cell（Linux）+ non-root cell（裸机/RTOS inmate）；inmate 手工写 C、交叉编译、经 `jailhouse cell load` 加载 | 部署底座；inmate **代码生成是手工流程**，无"运行时把融合编译器搬进 cell" |
| **Gracioli et al., ECRTS 2019**（"Designing Mixed Criticality Applications on Modern Heterogeneous MPSoC Platforms"） | Jailhouse + Erika Enterprise RTOS + **页着色（page coloring）** 做跨域性能隔离；Xilinx UltraScale+ | mixed-criticality 部署标杆 |
| **Jailhouse-RT** | 实现缓存着色的 Jailhouse 公开分支 | 最接近"Jailhouse 工具链扩展"的工作 `[文献待补：具体论文/实现细节]` |
| **Mancuso et al.** 系列（Lazy Load Scheduling 等） | Jailhouse 用于异构 MPSoC 的 mixed-criticality，页着色隔离 | 同上 |

**小结**：Jailhouse 用于 mixed-criticality 成熟，但 **inmate 工具链是手工的**（写 C、交叉编译、加载）。**"把融合/编译器搬进 Jailhouse cell 在运行时生成控制固件"未见公开先例** `[需进一步确认：检索时 "inmate" 会与"监狱管理系统"同形异义词冲突，已改用 "Jailhouse cell code generation" / "in-cell compiler RTOS" 等词，仍需更窄检索]`。

## 2. 重合度评估（逐点）

| K-Fusion 组成 | 重合方向 | 重合度 | 说明 |
|---------------|---------|--------|------|
| 合并周期任务省释放税（G·c） | §1.3 | **高** | Becker 2024、LazyTick 已研究"合并省释放/调度开销" |
| 从图生成实时任务 + 代码 | §1.4 / §1.2 | **高** | ADFG→RTEMS、Simulink、SCADE 均有 |
| 编译器进内核/单元 | §1.1 | **高** | eBPF JIT、JitSynth 已成熟 |
| **控制死区作为融合硬约束**（PR8） | — | **低** | 未见把"反馈死区绝对上限"作为融合*拒判*条件的工作 |
| **不确定性 fail-closed 门禁**（PR6） | — | **极低** | 未见把 DAG 不确定性（未证依赖/开放接口）作为融合*拒判*条件的工作 |
| **相位诚实端到端**（不把相位坍缩算收益，PR7） | — | **极低** | 未见在融合收益核算中明确剔除"相位坍缩"伪收益的工作 |
| **分区 hypervisor 上 cross-cell 实测融合收益** | §1.5 | **极低** | 数据集层面新颖：Pi4 上省 (N−1)·c、NuttX inmate 6 µs vs root-cell 20 µs |

> 结论：**单点**上 K-Fusion 几乎都有先例；K-Fusion 的新意在于这些点的**特定组合**与**实测证据**（见 §3）。

## 3. 创新性评估（PR9 / L2 的新意）

1. **范式迁移**：把 eBPF 式"内核内加载已验证代码"从**安全**域扩展到**硬实时控制时序**域。输入不是手写 C/字节码，而是**融合优化器的输出（分组后 DAG）**——即"编译器"本身成为内核内可信组件。
2. **内核化融合优化器 = 板上重融合（on-target re-fusion）**：静态 SCADE/Simulink/ADFG 流程都是*离线*生成；L2 让规划器在目标侧运行，DAG/相位/控制约束变化时**无需回 PC 重编译即可重融合**。这是现有工具链**不具备**的能力。
3. **fail-closed + 硬实时约束带入内核化路径**：PR6/7/8 的"可信约束优化器"属性延伸到 L2；内核内验证器类比（类比 eBPF verifier）应校验**时序可行性**（端到端 R 与反馈死区），而非仅内存安全。
4. **cross-cell 代码生成**：同一分组 DAG 生成 root-cell Linux（`.ko`，经 L1）与 non-root NuttX inmate（`nuttx.bin`）——多目标代码生成来自同一优化器（项目已有 `fiveloop_main.c` 双后端雏形）。
5. **实测数据集新颖**：在 Pi4 + Jailhouse 上给出融合收益的**板上实测**（省 (N−1)·c 且 ∝ c；NuttX inmate 6 µs vs root-cell 20 µs 确定性开销），这是现有文献缺的硬证据。

> **诚实定位**：K-Fusion 不是"释放税节省 / 图→代码 / 编译器进内核"任一单点的首创；其贡献是 **fail-closed 约束优化器 + 控制死区硬约束 + 相位诚实建模 + 分区 hypervisor 跨单元实测** 的**组合**，以及 L2 内核化带来的**板上重融合**能力。论文中必须这样定位，不能把 Becker 2024 / ADFG / eBPF 的已有成果表述为 K-Fusion 首创。

## 4. PR9（L2）设计建议（基于文献）

1. **分层、最小化 TCB**（借 Kops / Multiverse 教训）：内核内只放**规划器逻辑**（小、纯函数式、易验证）+ **预验证模板实例化**做代码生成（类比 eBPF 的"证明序列"），**不要把完整 C 编译器搬进内核**。代码发射用固定模板 + 参数填充，原生发射部分作为唯一新增信任基。
2. **时序验证器**（类比 eBPF verifier，但校验对象不同）：内核内/加载前校验 PR7 的端到端 R 与 PR8 的反馈死区硬约束（**时序可行性**），而非内存安全。可复用现有 `fusion_plan` 的 `solve_exhaustive` + 约束检查作为验证核心。
3. **认证路径**：代码生成侧借 **CompCert / translation validation**（§1.2）；规划器侧用 **RTA 式**证明（§1.4 Choi & Ha）。L1 的 `.ko` 链路已存在，L2 在其前插入"在目标侧运行规划器"一步。
4. **保留双后端**：root-cell `.ko` 与 inmate `nuttx.bin` 共用同一分组 DAG 输出（现有 `fiveloop_main.c` 已是双后端雏形）。
5. **防 footgun**：内核化重融合**必须保留** PR6/7/8 的硬约束与 fail-closed——绝不能让"板上重融合"变成绕过约束的口子（PR8 已证明融合*可能损害*控制语义）。

## 5. 风险与待补

- **认证缺口**：eBPF verifier 保证*安全*，K-Fusion 需*时序验证*。借 CompCert/translation validation（代码侧）+ RTA（规划侧）。
- **TCB 增长**（Kops 明确指出）：保持内核内组件最小；新增信任仅限"原生发射/模板实例化"。
- **收益有界**：释放税节省 ∝ c（线性），且 PR8 证明融合可能损害控制语义 → L2 重融合必须保留硬约束，不能为了"自动重融合"牺牲控制正确性。
- **"编译器进 Jailhouse cell"先例**：未见公开工作 `[需进一步确认]`；检索时避开 "inmate" 歧义。

### 6.1 结论变化

| 项 | 本文原判断（§3） | 修订后 |
|---|---|---|
| L1 输出侧（融合 IR → `.ko` / NuttX 程序） | 应坚持 | **仍应坚持**，且是下一步的主战场 |
| L2 工具链侧（规划器/代码生成进内核） | 作为 PR9 核心，卖点是"板上重融合" | **暂缓**；不作为当前研究瓶颈 |
| PR9 的含义 | "编译器内核化" | **"可信的端到端内核化闭环"**：验证 → 时间语义 → 双后端代码生成 |

### 6.2 为什么改

1. **研究目标错位**：K-Fusion 要证明的是"PLC 周期任务能被更可预测地执行并在约束下被合法融合"，
   不是"如何在内核里跑一个编译器"。后者会引入 TCB 扩大、动态代码加载、内存管理、故障恢复、
   实时执行隔离——任何一项都足以单独成篇，但不直接提升 ECoS 的价值。
2. **现有机制已够用**：Linux 模块加载 + 签名允许"用户态准备产物、内核加载时做完整性检查"，
   不要求编译器驻留内核。也就是说 L2 想解决的问题，现有机制成本更低地解决了。
3. **新颖性不增反降**：Becker 2024（ASP-DAC, task merging）已处理任务合并与端到端约束；
   eBPF verifier/JIT、JitSynth、Kops 已覆盖"编译器/验证器进内核"。把 L2 叠上去，
   更像技术拼凑，而不是把已有工作推进一格。
4. **真正的瓶颈不在那里**：本轮实测发现，最严重的问题恰恰是**可信性**——一份完全倒序的
   执行方案能通过 `--verify` 并一路生成代码（见 `FUSION__单域融合规划与实测.md` §5.11）。
   在验证器不可信时谈"板上自动重融合"，等于把不安全的决策自动化。

### 6.3 修订后的路线（本轮已完成前两项的"可信"部分）

```
PR9-A 全局方案验证器（独立 PlanVerifier，生成器强制消费）   ✅ 已完成
PR9-B 时间/控制语义 v4（绝对周期窗口 + 期限 + 证据级别）      ✅ 已完成
PR9-C 双后端内核化闭环（LLVM→Plan→Linux .ko / NuttX）        ⬜ 未做（ecos_build 现如实 rc=4）
PR10  跨域 IPC 最小运行时（IVSHMEM 发布-订阅协议）            ⬜ 未开始
PR11  跨域联合优化（部署 × 融合联合求解，CP-SAT / 精确枚举做基准）⬜ 未开始
```

### 6.4 若将来重启 L2，前置条件

- 先证明"用户态规划 + 预编译变体 + 内核加载时校验"**不能满足**需求（例如重融合必须在
  微秒级完成、或必须离线自主运行）；
- 且必须复用 PR9-A 的验证器语义（同一套 R / 死区 / 窗口判据），不允许"板上重融合"
  成为绕过硬约束的口子。
