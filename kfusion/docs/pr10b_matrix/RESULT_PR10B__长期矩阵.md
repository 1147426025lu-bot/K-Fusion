# PR-10B：同源两种部署的长期实测矩阵

日期：2026-10-28　机器：Pi4（内核 5.15.86 aarch64，1 ms 周期，deadline 1 ms）
脚本：`kfusion/scripts/pr10b_matrix__矩阵.py`

## 矩阵怎么造出来的

同一份 `kfusion/examples/ecos/mixed_pid_stateful__积分混合.c`，用**两套成本量级**让
STKP 各选一次。哪一边赢由成本决定，不由脚本指定——脚本只负责把选出来的方案跑起来：

| 场景 | 成本输入（域级量级） | STKP 选中 | 实际跑的部署 |
|---|---|---|---|
| `user_only` | 用户 5 µs / 内核 50 µs / ioctl 30 µs | `B` | 全用户态（gold 模式） |
| `partial_kernel` | 用户 5 µs / 内核 0.05 µs / ioctl 0.3 µs | `STKP:L[sample]\|L[pid]\|L[sink]` | 中间组进内核（mixed / UKU） |

两个格子都走完整流水线（stage_extract → TEIR → STKP → 验证器 → 码生成 → 编译），
**没有手写的对照实现**——否则比较的是两份代码，不是部署方式。

## 结果

| 场景 | 拍数 | response p50 | p99 | max | 超期 |
|---|---|---|---|---|---|
| user_only | 200 | 63.0 µs | 78.0 µs | 96.9 µs | 0/200 |
| user_only | **20000** | 63.0 µs | 76.0 µs | **173.5 µs** | 0/20000 |
| partial_kernel | 200 | 67.0 µs | 85.0 µs | 92.3 µs | 0/200 |
| partial_kernel | **20000** | 67.0 µs | 83.0 µs | **168.5 µs** | 0/20000 |

数据年龄（代理指标，见下）：mixed 的 `ioctl` 往返 p50 = **2.0 µs**，max = 10.5 µs（2 万拍）。

## 怎么读这张表（严格版）

1. **中位时延：内核化更差，差约 4 µs。** 这就是 UKU 的同步 ioctl 代价——每拍多一次
   陷入/唤醒。这不是噪声，p50 在 200 拍和 2 万拍上完全一致（67 vs 63）。

2. **尾部：mixed 略好，但不足以作为结论。** 2 万拍时 max 168.5 vs 173.5（差 5 µs，约 3%），
   p99 也是 83 vs 76——**方向自相矛盾**（p99 是 user 更好，max 是 mixed 更好）。
   单次运行、单机、单份源码，**不能声称「内核化降低抖动」**。要下这个结论至少需要
   多次重复 + 多负载 + 统计检验。

3. **超期：两边都是 0。** 说明这两个部署在 1 ms 周期下都不可观测地安全——
   **这恰恰是问题**：当前负载太轻，区分不出部署方式的实时性差异。要做出差异得加压
   （缩短周期、加背景负载、或换更长的计算链）。

4. **数据年龄**：UKU 是同步 ioctl，用户写 `g_in` 到内核读到的间隔落在一次调用内，
   所以只能拿 `ioctl` 往返作代理（p50 2 µs）。**这个数字不能和 PR11 的 xipc 投递年龄并列**，
   两者量的不是一回事。

## 这份结果对论文意味着什么

- 它**不支持**「内核化更快」或「内核化抖动更小」这类主张，包括混合部署。
- 它**支持**的是：同一份源码，在验证器允许的前提下，能自动产出两种**功能一致**
  （输出逐拍一致、会话状态一致）的部署，并给出可比的实测分布——这是「选择性内核化」
  这个能力本身，而不是性能收益。
- 下一步要拿到性能结论，缺的不是更多部署形式，而是**让负载有区分度**（PR-10B 第二轮：
  加压 + 重复实验 + 统计检验）。

## 诚实边界

- 全部是这台机器的实测，**不是 WCET**，长跑只提高样本量，不提供上界证明。
- 每个格子只有一次长跑，没有重复实验，因此不报置信区间。
- 成本输入是**场景量级假设**（写进 `cells/*/stage_cost.json`），不是逐阶段实测值；
  换掉它会改入选方案。
- `gen/`（构建产物）不入库。
