# PR-10E：ms 级尖峰的机制分解——100% 的延迟发生在「等调度」，不在执行

日期：2026-10-28
数据：`pr10e_baseline/baseline.json` + `runs_*/rNN.csv.gz`（4 条件 × 10 轮 × 5000 拍，周期/期限 1000 µs，CPU3 亲和）
对应问题：PR-10D 遗留的「为什么相同配置一次 12.41 µs、另一次 23.30 µs」，以及「毫秒级尾部尖峰来自 IRQ、调度还是锁竞争」

---

## 一、方法：用 wall-time 分解代替 CPU clock（因为后者太贵）

原计划给驱动加 `CLOCK_THREAD_CPUTIME_ID` 测「本拍真正在 CPU 上的时间」。实测发现不能用：

```
CLOCK_MONOTONIC      :  130.4 ns/次
CLOCK_THREAD_CPUTIME : 2510.4 ns/次      ← 贵 19 倍，没有 vDSO 快路径
```

每拍要调 2 次 → 额外 **5.0 µs**。而我们要测的 `work`（执行时间）本身只有 **1.3 µs**——
等于把被测量放大 5 倍。这不是「加了点噪声」，是**指标失效**。
（验证：加了该探针后 p50 从 62.65 涨到 66.26；去掉后回到 62.91，见下。）

因此改用 **wall-time 分解**，只用已有的 `CLOCK_MONOTONIC`（零额外开销）：

```
resp      = f − r     从「名义释放时刻」到「本拍结束」   ← 契约关心的量
start_lat = s − r     从名义释放到「真正开始执行」      ← 等调度/唤醒延迟
work      = f − s     从开始执行到结束（wall）          ← 执行本身
resp = start_lat + work
```

`start_lat` 与 `work` 一分开，「慢」是哪一种立刻分晓，而且**不需要 CPU clock**。

## 四、结论

**1. 毫秒级尖峰的机制是「线程没被及时调度上 CPU」，不是「算得慢」。**

超期拍的 `work` 是 1.3–2.6 µs（用户态）/ 4.7–16.7 µs（mixed），与**同轮正常拍完全相同**
（1.3 µs / 4.3 µs）。而 `resp` 的 1000–3100 µs 几乎全部落在 `start_lat`。

换句话说：那一拍**根本没开始跑**，在跑之前就晚了 1–3 ms。

**2. 这条对「内核化能不能解决尖峰」给出了否定答案。**

内核化减少的是 `work`（执行路径），而 100% 的延迟在 `start_lat`。
**优化 `work` 对 ms 级尖峰没有任何效果**——这解释了 PR-10B/10C 为什么一直测不到收益。

**3. FIFO 99 下两部署都是 0 超期（10/10 轮）。**

同一份二进制、同一台机器、同一负载，只换调度类就从 33 拍超期变成 0。
**调度类是 ms 级尖峰的唯一开关**，与部署方式无关。

**4. 由此，「毫秒级尖峰」不是 K-Fusion 的编译问题，是调度配置问题。**

编译器能做的正确事情不是「把计算搬进内核以降低延迟」，而是
**判断该任务在给定调度配置下是否可行**，并把调度类作为部署决策的自变量
（评审已提出，此处补上每拍级证据）。

## 五、诚实边界

- **仍不知道「被谁抢占」**。本方法只能区分「等调度」与「在跑」，无法给出抢占者。
  那需要 ftrace 的 `sched_switch`/`sched_wakeup`（阶段 D），而 **p1 分区只有 32 MB、
  装不下第二个内核**，本机无法提供。按验收第 7 条，这一项标**未归因**。
- **IRQ 屏蔽这一路径未被排除**。若某拍 IRQ 被长时间屏蔽，线程根本收不到唤醒，
  也会表现为 `start_lat` 巨大。区分它同样需要 tracing。**因此「等调度」应精确表述为
  「从名义释放到真正开始执行之间的时间」，其中调度与 IRQ 屏蔽的占比未分解。**
- 板上同时运行着 `cursor-server`（约 23% CPU，用户远程开发用）。CFS 下的超期可能
  部分由它造成；但 **FIFO 99 下 0 超期**说明 RT 优先级足以压过它。该进程未被停掉，
  因为它是用户正在使用的工具。
- 单机、单源码、10 轮；不报显著性检验。逐拍数据已入库，可复核。
- 实测非 WCET。
