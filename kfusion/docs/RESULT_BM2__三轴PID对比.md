# BM2（三轴级联 PID）在 NuttX 域的对比：pass 的真实代价是 0

> 2026-10-21 · Pi4B / Jailhouse 非根 cell / NuttX / 1 kHz / n=100 000
> 命令：`bm2pid -l 100000`（与 cyclictest `-l 100000` 同窗口）
> **本文替换了早前版本**：早前把 `+18%` 记成"pass 自身代价"，是错的，根因已定位（见 §2.2）。

---

## 1. 六个版本的结果

| 版本 | exec avg | exec max | 抖动 p50 / max | 控制质量 |
|---|---|---|---|---|
| **A. gcc -Os 基线**（NuttX 默认构建） | **0.965 µs** | 2.000 µs | 6 / 7 µs | 基准 |
| **B. clang -O2，不过 pass**（contract=off） | **1.203 µs** | 1.648 µs | 5 / 6 µs | **逐位相同** |
| C. clang + pass，**`--hot main`**（冻结整份程序） | 1.417 µs | 2.445 µs | 6 / 7 µs | **逐位相同** |
| D. clang + pass，不冻结，contract=off | 1.205 µs | 1.685 µs | 5 / 9 µs | **逐位相同** |
| **E. clang + pass，不冻结，contract=fast** | **1.154 µs** | 1.833 µs | 5 / 6 µs | **逐位相同** |
| F1. clang + pass，`-Oz` | 1.296 µs | 1.593 µs | — | **逐位相同** |
| F2. clang + pass，`-O1` | 1.362 µs | 1.852 µs | — | **逐位相同** |
| **T1. pass + 任务函数独立，不冻结** | **1.184 µs** | 1.852 µs | — | **逐位相同** |
| **T2. pass + 冻结独立任务函数** | **1.425 µs** | 2.648 µs | — | **逐位相同** |

T1/T2 是 §2.3.1 的严谨对照（唯一差别 `optnone`）；其余各组见对应小节。

控制质量的三个数（所有版本完全一致到 9 位小数）：

```
axis0 pos=1.003868946  err_ms=9.166907e-01
axis1 pos=-2.501873021 err_ms=2.961862e-01
axis2 pos=3.999878283  err_ms=6.975936e-02
```

**D → E 只改了一个编译选项**（`-ffp-contract=off → fast`），就快了 4.2%，且数值仍然逐位相同。
**E 是当前最优的 clang 配置**，也是脚本现在的默认值。

## 2. 结论

### 2.1 数值行为完全保持

所有版本（含过 pass 的）控制量**逐位相同到 9 位小数**。
在 double + 硬件 FPU 的路径上，内核化没有改变任何数值结果——这条对"编译器是否会悄悄改控制行为"的质疑是直接回答。

### 2.2 pass 的真实代价是 **+0.17%**（噪声级），不是 +18%

```
B (clang 无 pass)   1.203 µs
D (clang + pass)    1.205 µs   → +0.002 µs = +0.17%
```

**指令级同样是 1:1**：

```
B: base.o   6872 字节，580 条指令，mov/add 类 155
D: fused.o  6880 字节，580 条指令，mov/add 类 155
```

只差 8 字节，来自符号名变长（`printf`→`plc_printk`，`clock_gettime`→`plc_ktime_get_ts`）。

**早前那个 +18% / +133 条指令是怎么来的？**

`--hot main` 被传给了 `PLCLowJitterPass`，它按"冻结实时任务函数"的语义给 `main` 加了三个属性：

```llvm
attributes #0 = { noinline nounwind optnone ... "plc-low-jitter"="true" }
;                          ^^^^^^^
```

`optnone` 会让 `llc` **完全跳过该函数的优化**。而 BM2 的 `scan_cycle` 是 `static` 且只有一个调用点，`-O2` 下已被内联进 `main` —— 于是**整份程序被冻结**。

这也解释了当时那个想不通的现象：*"pass 之后再跑 `default<O2>`，指令数一个都没变"* —— `optnone` 函数被优化器直接跳过。

**归因更正（撤回旧表）**：

| 段 | 旧说法 | 实际 |
|---|---|---|
| gcc -Os → clang -O2 | +25%，编译器差异 | ✅ 正确（+25%，与 K-Fusion 无关） |
| clang → clang + pass | ~~+18%，pass 自身~~ | ❌ **+0.17%**；那 18% 是 `--hot main` 的 `optnone` 冻结 |

### 2.3 `PLCLowJitterPass` 的冻结代价：**+17.6%**（这是设计选择，不是 bug）

`PLCLowJitterPass` 给目标函数加 `noinline + optnone`，意图是**冻结机器码形态，让时间行为可静态预测**（RTSS 风格的 WCET 友好）。这条路本身有代价，而且现在有数字了：

```
D (不冻结)   1.205 µs / exec max 1.685 µs / p50 5 µs
C (冻结)     1.417 µs / exec max 2.445 µs / p50 6 µs
             → +17.6% 均值，+45% 最坏值，p50 回退 1 µs
```

**这是一个可写进论文的 trade-off 数据点：时间可预测性不是免费的。**
但要成立，前提是**只冻结真正的实时任务函数**，不能冻结 `main`（否则连冷路径一起冻，且失去所有标量优化）。

**因此 `--hot` 的正确用法是**：
- 想要"pass 的真实代价" → **不要给 `--hot`**；
- 想要"WCET 冻结" → 给独立的任务函数（如 cyclictest 的 `testthread`），**绝不给 `main`**。

> 脚本已加硬警告：`--hot` 里出现 `main` 时打印 `[WARN]` 并说明后果。

### 2.3.1 严谨对照：只冻结独立任务函数，代价是 **+20.4%**

上面的 1.417 是"冻结整份程序"，不够干净（它也禁止了冷路径的优化）。为此做了一个**唯一变量**的对照：

做法：给 BM2 源码加一个可开关属性（`-DBM2_SCAN_ATTR=__attribute__((noinline))`，见 `bm2pid_main.c`），
让 `scan_cycle` 保持独立存在（`-O2` 下它本来会被内联）；然后**同一份 `.i`、同一组选项**（`-O2 / fast / +fp-armv8`），
只改 `--hot` 的有无：

| | 函数数 | `optnone` 落点 | fused.o | exec avg | exec max |
|---|---|---|---|---|---|
| **T1 不冻结** | 2（`main` + `scan_cycle`） | 无 | 6832 B | **1.184 µs** | 1.852 µs |
| **T2 冻结 `scan_cycle`** | 2 | **仅 `scan_cycle`** | 8536 B | **1.425 µs** | 2.648 µs |
| | | | | **+20.4%** | **+43%** |

属性核验（`grep '^attributes #' cyc.kll`）：

```llvm
define dso_local i32 @main(...)          -> 组 #0（无 optnone）
define internal fastcc void @scan_cycle() -> 组 #3（含 optnone + "plc-low-jitter"="true"）
```

**这是本次最干净的一个结论**：同源码、同优化选项、同 IR 来源，唯一差别就是 `scan_cycle` 上多了一个 `optnone`。
**冻结一个独立的实时任务函数，代价是 20.4% 的执行时间、43% 的最坏执行时间。**

顺带得到两条副产品：

- **冻结粒度不影响结论**：冻结整个 `main` 是 +17.6%，冻结独立任务函数是 +20.4%，量级相同 →
  代价来自**热循环失去优化**，而不是"冻结范围太大"。
- **`noinline` 本身很便宜**：内联版 1.154 → 独立版 1.184，**+2.6%**（一次函数调用往返）。
  所以"为了可分析性保留函数边界"本身几乎不要钱，**贵的是 `optnone`**。

**论文里的用法**：`optnone` 冻结可以作为"时间可预测性"的购买项，但必须明码标价——
**20.4% 的执行时间换一个机器码形态固定、可做静态 WCET 分析的热函数**。

### 2.3.2 一个意外但很硬的推论：执行时间差 20.4%，抖动一模一样

T1 与 T2 的抖动直方图**逐桶相同**：

```
T1（1.184 µs 执行）:  6 µs × 99 999, 7 µs × 1
T2（1.425 µs 执行）:  6 µs × 99 999, 7 µs × 1
```

执行时间差 **20.4%**、最坏执行时间差 **43%**，而唤醒抖动**一个字节都没变**。

原因很直接：抖动 = 实际唤醒时刻 − 标称截止时刻，由**调度器与中断**决定；
只要单周期执行时间（1.2–1.4 µs）远小于周期（1000 µs），它对抖动就没有可观测影响。

**这条正好钉死了主线的核心论点**：抖动由运行域/架构决定，编译器层的改动（哪怕 +/-20% 执行时间）
改变的是"算得多快"，不是"醒得多准"。也解释了为什么"内核化让抖动更小"不能主张——
不是实现不够好，而是**这个量纲上编译器没有作用面**。

### 2.4 一个方法论教训

`optnone` 这种"优化开关"不会报错、不会改变语义、只是让代码变慢 —— 它和之前那两个"静默黑洞化"缺陷（`getopt`、`__errno`）属于同一类风险：**编译产物看起来正常，但性能/语义已被悄悄改变**。

判别办法很简单，必须成为常规检查：**对照 `attributes` 行 + 指令数**。
本次就是靠 `diff <(grep '^attributes #' pre.ll) <(grep '^attributes #' kll)` 一行定位的。

### 2.5 FixedPoint 对 NuttX 后端是多余的

`-mattr=-fp-armv8,-neon` 是**内核模块**的约束（内核态不能用 FPU）。
NuttX 后端是**用户态**，FPU 完全可用：改成 `+fp-armv8,+neon` 后，产物引用从 9 个软浮点符号（`__adddf3/__divdf3/...`）降为 **0**（aarch64 的 libgcc 里根本没有这些）。

### 2.6 剩下的 19.6% 差距：clang vs gcc，与内核化无关

E（1.154）与 A（0.965）之间还有 19.6%。这是**编译器后端差异**，证据如下：

| | 总指令 | FP 运算 | ldr/str | 栈帧 |
|---|---|---|---|---|
| gcc -Os | **388** | **23** | 98 | **无** |
| clang -O2（contract=off） | 580 | 67 | 131 | `sub sp,#0xd0` |
| clang -O2（contract=fast） | 560 | 51（16 条 `fmadd`） | 131 | `sub sp,#0xd0` |

三点解释：

1. **FMA 融合**：gcc 默认 `-ffp-contract=fast`，跨语句把 `acc += c[i]*y[i]` 融成 `fmadd`；
   clang 的 `on` 只在同一表达式内融合，`off` 完全不融合。→ 用 `fast` 后 FP 指令从 67 降到 51。
2. **栈帧**：gcc 版一个栈帧都没有（`sub sp` 出现 0 次），clang 版有 208 字节栈。
   显式加 `-fomit-frame-pointer` 只省 4 条（556 vs 560），因为栈空间本身仍被需要。
   gcc 能做到无栈帧，推测是它在 `-Os` 下把 `N_AXES=3` 的轴循环完全展开了。
3. **指令数 ≠ 性能**：`-Oz` 只有 399 条却最慢之一（1.296），`-O1` 460 条更慢（1.362）。
   `-Oz`/`-O1` 关掉了调度与展开，IPC 下降抵消了指令数的优势。**这个负结果本身值得记一笔**：
   不能用代码体积当性能代理。

**所以论文里的正确表述是**：同编译器内 A/B 证明内核化零代价（+0.17%）；跨编译器（gcc→clang）有 19.6% 差距，属后端代码生成差异，与 pass 无关。**不能拿 E 与 A 直接比而暗示"内核化拖慢了 19.6%"**。

## 3. 这次跑出来的四个 pass 缺陷（都由 BM2 触发）

| # | 缺陷 | 表现 | 为什么之前没发现 |
|---|---|---|---|
| 1 | **`llvm.fmuladd` 未处理** | 操作数转成 i64 但签名仍是 double → IR 非法 → `opt` abort | cyclictest 的浮点都在直线代码里，没有乘加融合；FIR/PID 的 `acc += c*y` 必然产生 |
| 2 | **PHI 节点处支配关系违规** | `Instruction does not dominate all uses` → 验证器 abort | 同上；控制环的积分项是 loop-carried PHI |
| 3 | **`getopt` 被黑洞化** | 返回 0 → `while((c=getopt())!=-1)` 永真 → 直接打 usage 退出 | cyclictest 用 `getopt_long`，在保留名单里 |
| 4 | **`__errno` 被黑洞化** | NuttX 的 `errno` 是 `*__errno()`，被换成从地址 0 读 | 之前没触发；**新加的 stderr 警告当场抓到了它** |

缺陷 1/2 目前用 `PLC_FUSION_FIXED_POINT=0` 绕过（NuttX 后端本来也不需要定点化）；
缺陷 3/4 已加入 `isPreservedExternal()` 的 kKeep。

## 5. 抖动的读法（避免误用）

- **BM2 的 5–6 µs 不能和 cyclictest 的 3/4/9 µs 直接比**：两者 deadline 记账方式不同（BM2 每周期先算 deadline 再睡，睡前有约 1 µs 工作），属于**仪器差异**，不是控制律的代价。
- **只有同负载的 A/B（基线 vs 过 pass）才有可比性**。
- D 版那一格 `max 9 µs` 是 10 万次里的**单次事件**（p50 仍 5 µs），与 A/B 的 6–7 µs 同量级，不构成趋势。

## 6. 待办

1. **修 FixedPoint 的 fmuladd 与 PHI 两个 bug**（若要让内核模块后端支持真实控制律，这是必需的）。
   注：`-ffp-contract=fast` 产出的是 `fmul contract`（20 处），**不生成 `llvm.fmuladd` intrinsic**，
   所以默认 `fast` 之后定点化路径不会再被这个 bug 卡住；但 `on` 仍会生成（23 处），修 pass 仍然要做。
2. 把 `-mattr` / `--hot` / `FP_CONTRACT` 的选择写进 manifest（当前靠环境变量传）：
   内核态 `-fp-armv8`，用户态 `+fp-armv8`；`--hot` 只给独立任务函数；`FP_CONTRACT=fast`。
3. 若要做"冻结 vs 不冻结"的正式对比，需要先给 `scan_cycle` 加 `noinline` 让它独立存在
   （`-O2` 下它被内联进 `main`，无法单独冻结；`-Oz` 下它会保持独立，可用来做这个对比）。
4. 若要追平 gcc 那 19.6%：可尝试 `-fno-math-errno`（无效果，已试）、轴循环手工展开、
   或接受"gcc 后端在此工作负载上更优"的结论。**优先级低**——它不影响内核化零代价的结论。

---

## 7. 一句话总结

**编译期内核化在 NuttX 域是零代价的（同编译器 A/B：+0.17%）；
那个看起来像代价的 +18%，是我们误把 `main` 当实时任务函数冻结（`optnone`）造成的；
而 clang 与 gcc 之间的 19.6%，是后端代码生成差异，不是内核化的账。**

## 8. 跨域对照：同一份源码，Linux root cell vs NuttX cell

这是主线「同一产物跨域归因」在**真实控制律**上的旁证。

### 8.1 方法：零改动编译到两个域

`bm2pid_main.c` 除了一处 `#ifdef __NuttX__ → #include <nuttx/config.h>` 之外，**全是标准 POSIX**
（`clock_gettime / clock_nanosleep / printf / getopt / stdint`），没有任何 NuttX 专有调用。

```
# NuttX 域：作为 NuttX builtin app（NuttX 构建系统自动传 -Dmain=bm2pid_main）
apps/benchmarks/bm2pid/bm2pid_main.c

# Linux 域：同文件，不加 __NuttX__，一条命令
gcc -O2 -o bm2pid_linux bm2pid_main.c -lm
chrt -f 99 taskset -c 3 ./bm2pid_linux -l 100000
```

**同一份源码、同一套算法、同一组参数**，唯一差别是运行域。NuttX 侧靠 app 的
`PRIORITY=200`（NuttX 数值越大优先级越高），Linux 侧靠 `chrt -f 99`（Linux FIFO 上限）。

> ⚠️ 优先级数值不可跨 OS 直接对齐，两侧都取**各自最高可用档**，这是可比较的唯一合理设定。

| | #2 | 17 | **20** | 23 | 23 | 32 | **47** | 1.156 | 2.296 |

| | pass（任务独立） | 6 | **6** | 6 | 6 | 6 | **7** | 1.184 | 1.852 |

（单位 µs；两侧控制质量三轴末位**逐位相同**：`1.003868946 / -2.501873021 / 3.999878283`）

### 8.3 三条结论

**① 执行时间几乎相同，抖动差 3–18 倍。**
Linux 的 exec avg 1.171–1.239 µs vs NuttX 0.965–1.184 µs，差距在 ±10% 内（且方向不稳定，
取决于编译器与内联策略）。而抖动中位差 3.3×、极值差最高 18×。

**这是「抖动与执行时间脱钩」的第二个独立证据**（第一个是 §2.3.2 的 T1/T2 对照：
执行时间差 20.4%、抖动逐桶相同）。两个实验方向相反、结论一致：

> 抖动由**运行域**（调度器、中断、是否有其他负载共享核）决定；
> 代码快慢只影响「一个周期算多久」，不影响「什么时候被唤醒」。

**② 控制质量逐位相同 → 比的是同一个算法，不是两个程序。**
六轮测量的三轴末位完全一致。所以抖动差异**不能**归因于"Linux 版本算得不一样"。

**③ 这条数据给 34× 归因链补上了「真实负载」的旁证。**
此前 34×（268 → 7.834 µs）是 cyclictest 上的结果——一个纯计时程序。
现在同一个**带控制律、带 FIR 滤波、带级联 PID** 的负载，在 Linux（20 µs 中位）与
隔离 cell（6 µs 中位）之间也复现了同一量级的差距（3.3×–18×），说明那条归因链
**不是 cyclictest 特有现象**。

> ⚠️ **口径纪律**：这是 100 s 窗口（10 万周期）的数据，**不可**与本项目 1 h / 8 h 的
> cyclictest 极值并列比较（§9.5 的 760 µs 是 1 h 窗口）。这里只用同窗口（100 s）的
> 两侧数字互相比较。

### 8.4 一个旁支观察：Linux 侧的抖动主体是「恒定的 20 µs」→ 已查实是 hypervisor（见 §8.5）

Linux 的 CDF 在 20 µs 处陡升（约 67–71% 的样本落在 20 µs 这一桶），而不是从 0 缓慢爬升。
这不是随机调度（随机调度会给出平滑分布），而是**固定唤醒延迟**。

2026-10-22 用 A/B/A 把它定位到了 hypervisor 上：**不是 Linux，也不是 BM2**。

### 8.5 「20 µs」的因果：hypervisor 的确定性开销（2026-10-22 补测）

**方法**：同一块板、同一份 `bm2pid_main.c`、同一个 `gcc -O2` 二进制、CPU3 + FIFO 99 + 1 kHz，
**唯一变量 = hypervisor 开/关**（`jailhouse enable/disable`，其余状态不变）；每次 60 000 周期；
测前 `ip link set wlan0 down`（理由见 §8.6）。

| 条件 | 轮次 | min | **p50** | p99 | max | exec avg |
|---|---|---|---|---|---|---|
| **HV 关**（裸 Linux） | #1 | 9 | **11** | 29 | 88 | 0.977 |
| | #2 | 8 | **11** | 20 | 55 | 0.956 |
| **HV 开**（root cell） | #1 | 16 | **20** | 44 | 137 | 1.179 |
| | #2 | 15 | **20** | 36 | 101 | 1.254 |
| | #3 | 16 | **20** | 44 | 127 | 1.205 |

（µs）

三条读数：

1. **p50 11 → 20 µs，三次重复全部落在同一档**。是平台，不是抖动。
2. **min 8–9 → 15–16 µs**，与 p50 同幅度平移 → 整条分布被平移，不是尾部变重。
3. **exec avg 0.96–0.98 → 1.18–1.25（+23%）**。控制律代码一行没改，
   `clock_gettime / clock_nanosleep` 所在路径却慢了 → 开销在**陷入/系统调用**一侧。

   > ⚠️ 这 +23% **不一定**是"控制律算得更慢"：exec 是用两次 `clock_gettime` 夹出来的，
   > 每次约 +0.1 µs 的陷入成本就能解释 0.2 µs 的增量（0.96 → 1.16）。
   > 现有数据分不开"计算变慢"与"测量变慢"，**不主张前者**。

→ **root cell 相对裸 Linux 有约 +9 µs 的确定性成本，由 hypervisor 引入。**

这条结论同时解释了 §8.2 里那个"20 µs 陡升"：它就是这 9 µs 加上裸 Linux 自身的唤醒路径（≈11 µs）。

> ⚠️ **口径修正**：§8.2 的 3.3×（20 vs 6）**不能**整体记成"隔离层收益"。
> 它内含两段：Linux 自身唤醒路径 ≈11 µs + hypervisor 转发 ≈9 µs。
> 同一 hypervisor 下的 NuttX cell 只有 6 µs，说明**裸机 cell 不付这 9 µs**——
> 所以这 9 µs 是"**Linux 在 EL2 之下跑**"的代价，不是 hypervisor 的固有开销，更不是 NuttX 的功劳。
> ⚠️ 机制（IRQ 由 EL2 转发 vs 系统寄存器陷入）**未测**，本文只陈述"开关 hypervisor ⇒ +9 µs"这个因果事实。

### 8.6 方法学教训：测 BM2 必须关无线

| 条件 | p50（重复） |
|---|---|
| HV 关 + 无线开 | 11（单次） |
| HV 开 + 无线开 | **21 / 23 / 30（离散，不可复现）** |
| HV 开 + 无线关 | **20 / 20 / 20（稳定）** |

原因：`irq 12`（SDIO/mmc）的中断计数落在 **CPU3** 上——`bm2_linux_diag` 的 C 项实测
`irq 12: cpu3=51237`，brcmfmac 的 SDIO 流量直接打在被测核上。

→ 本项目约定：**凡 BM2 测量，先 `ip link set wlan0 down`**；控制改用串口（COM11）。
反过来说，§8.2 的 100 s 数据（p50 20、exec 1.156–1.239）就是在"无线关 + HV 开"下取的，
本次复测与之逐项吻合，**历史数据自洽**。

## 9. BM2 的 1 h 同窗口（2026-10-22）

**为什么必须做**：§8.2 只有 100 s，极值不敢与 cyclictest 的 1 h 极值（root 760 µs / inmate 9 µs）
