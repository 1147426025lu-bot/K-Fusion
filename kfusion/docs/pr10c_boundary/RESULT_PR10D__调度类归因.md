# PR-10D：异常与延迟归因（并更正 PR-10C 第二步的结论）

日期：2026-10-28　机器：Pi4（内核 5.15.86 aarch64，周期 1000 µs，每格 5000 拍）

## 先说不能做的事

计划里写的是用 `rtla timerlat` 拆分 IRQ 延迟与线程延迟。**这块板子做不到**：
当前内核 `# CONFIG_FTRACE is not set`（内核树 `/root/linux-5.15.86/.config` 实证），
`CONFIG_TIMERLAT_TRACER` / `CONFIG_OSNOISE_TRACER` 均未设置，tracefs 也挂不上。
所以 **ftrace 级别的归因（IRQ vs 调度 vs 迁移各占多少）本轮没有做，也不会编。**

改用不依赖 trace 的**受控消融**：只改调度类，其余不动。

## 结论（含一条对上一轮的更正）

**1. 第一主因是调度类，不是内核化。**
同一个用户态驱动，仅把它放进 `SCHED_FIFO 99`：start_lat **63.57 → 12.47 µs（5.1×）**。
这跟"计算放哪"完全无关。

**2. 更正 PR-10C 第二步的归因。**
我在 `RESULT_PR10C2` 里把 4.7× 解释成"内核线程唤醒路径比用户态唤醒短"。
**这个解释是错的。** 真实原因是：内核线程天生是 `SCHED_FIFO 99`，
而我们的用户态驱动跑在 CFS（代码里根本没设调度策略，`grep sched_setscheduler` = 0）。
一旦把用户态驱动也设成 FIFO，两者在 start_lat 上**基本一致**（12.47 vs 13.33 µs）。

**3. FIFO 补齐后，三种部署真正的差异只剩 ioctl 的 ~3 µs。**
- 全用户态 FIFO：response 13.38 µs
- 部分内核化 FIFO：response 16.55 µs（多出的 3.17 µs ≈ 实测 ioctl 2.97 µs）
- 内核自主：response 14.39 µs

**4. 因此"内核化降低时延"这条路在当前负载上已经封闭。**
1 ms 周期下，只要用 RT 优先级，用户态部署就够用（13.4 µs vs 期限 1000 µs，余量 75×）。
内核化带来的净变化是 **+3 µs**（部分内核化）或 **≈0**（自主执行）。
这比 PR-10B/C 的结论更强：不是"内核化不够快"，而是**它在这个场景里根本不必要**。

**5. 平台地板 ≈ 10–14 µs，我们的驱动在 FIFO 下已经贴住。**
`cyclictest -p99` 的 Min 9 / Avg 14 / Max 120 µs 与我们的 FIFO 驱动（min 9.6 / avg 12.5 / p99 22）
同一量级 ⇒ 剩下这点延迟是**平台属性**（IRQ 处理 + 唤醒 + 计时器），不是我们代码的问题。

**6. 尾部差异仍在，但方向不利于内核化。**
CFS 下部分内核化的 max 到 1233 µs 并吃 2 次超期，而全用户态 178 µs / 0 次；
FIFO 下两者都收敛（96.5 vs 43.0 µs）。**加一次 ioctl 就多一段可被争抢的路径**，
这与 PR-10B 观测一致。

## 对论文/部署决策的影响

- `J(d) = αQ₉₉ + βR_miss + γC_boundary` 里，**必须先固定调度类再比较部署**，
  否则会把"调度类差异（5×）"误记到"部署差异（3 µs）"账上——我上一轮就是这么错的。
- 决策变量的优先级应重排：
  1) 是否允许 RT 优先级（影响 50 µs 量级）
  2) 是否需要内核保序 / 硬件直写 / 跨域版本（结构性需求）
  3) 跨界次数（影响 3 µs 量级）
- **不要**把"降时延"写成内核化的卖点。

## 诚实边界

- 每格**单轮 5000 拍**，没有重复实验，不做显著性声明；这是量级对照。
- `chrt -f 99` 会饿死其他任务，5 秒窗口内可接受，但这不是长时间运行的配置。
- **没有 ftrace**：剩余 ~12 µs 里 IRQ / 唤醒 / 迁移各占多少**仍然未知**。
  要做需要重编内核（开 `CONFIG_FTRACE` + `CONFIG_TIMERLAT_TRACER`），那是另一个决策，
  且有把板子搞到起不来的风险，需先备份可用内核。
- `cyclictest` 输出的是 Min/Act/Avg/Max，没有 p99，列在同一张表里只为量级参照，
  不做逐项比较。
- 实测不是 WCET。
