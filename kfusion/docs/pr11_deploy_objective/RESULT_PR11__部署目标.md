# RESULT PR-11：把「等调度」纳入部署决策

**一句话**：在同一个 PID 三阶段任务上，把调度类（CFS / FIFO99）作为决策变量加进
部署选择后，目标函数从 **78.270 µs 降到 29.471 µs（−48.799 µs，−62.3%）**；
而 STKP 按模型选出的混合方案在实测尾部上比全用户态**差 5.171 µs**——
编译器原来那句话「混合更优」在这台机器上不成立。

---

## 1. 为什么必须加这一维

前三个 PR 已经把结论钉死了：

| 结论 | 来源 | 含义 |
|---|---|---|
| 4.7× 差异来自调度类，不是内核化 | PR-10D | FIFO 补齐后三部署 start_lat 同量级 |
| 毫秒尖峰 100% 在「等调度」 | PR-10E-C | 超期拍 work == 正常拍 work，缺的全是 start_lat |
| 内核化只减 work，不减 start_lat | PR-10B / 10C | 所以内核化对超期无效 |

三条合起来是一个结构性缺陷：**部署决策空间里少了「调度类」这一维**。
只按预测执行时间排序，会选出一个在 CFS 下必然吃 63 µs 等待的方案，
而把线程设成 FIFO 就白拿 ≈51 µs。这个量比候选之间的差（5 µs）大一个数量级。

## 2. 形式化与三条不许含糊的边界

```
J(d,s) = α·Q99_resp(d,s) + β·R_miss(d,s) + γ·C_boundary(d)
```

- `d` 是 STKP 候选（分组 × 域），`s` 是调度类。`s` 不是 `d` 的属性。
- **Q99 / R_miss 只能是实测**，且必须带轮数与总拍数；缺测 = 该 `(d,s)` 不可排名。
- **形状必须匹配**：Q99 是执行形状相关的量，3 组不融合测出来的尾部不许借给
  1 组全融合的候选（见 §5 不可排名清单）。
- **R_miss 用 Wilson 区间**：5 万拍里 33 次事件，点估计不稳，可切 `--miss-bound upper`。
- **γ 默认 0**：Q99 已是端到端响应，里面**已含**边界往返；γ>0 表达的是
  「多一次跨界的结构代价/故障面/审计成本」，不是再加一次时延。默认 0 是为了
  避免重复计数被当成物理时延。
- J 是**加权标量化**，权重是策略输入，量纲不齐（µs 与无量纲率）。它不是 WCET，
  也不宣称硬实时可调度性；它只在**已通过 verify 的候选之间**排序。

## 4. 决策结果

候选集取 PR-10E 本人的 STKP 输出（`candidates_pr10e_stkp.json`，5 个 deployable），
deadline 1000 µs，α=1。

**旧决策空间（只能选部署，调度类固定 CFS）：**

| 候选 | 部署 | Q99 | J |
|---|---|---|---|
| A（L\|L\|L，全用户态，3 组） | user_only | 78.27 | **78.270** ← 入选 |
| STKP 混合（L\|L\|L，mixed，1 跨界） | partial_kernel | 83.37 | 83.367 |

**联合决策（调度类成为变量）：**

| 候选 | 部署 | 调度类 | Q99 | R_miss | C_bd | J |
|---|---|---|---|---|---|---|
| A | user_only | fifo99 | 29.47 | 0 | 0.00 | **29.471** ← 入选 |
| STKP 混合 | partial_kernel | fifo99 | 34.64 | 0 | 2.00 | 34.642 |
| A | user_only | cfs | 78.27 | 0.000660 | 0.00 | 78.270 |
| STKP 混合 | partial_kernel | cfs | 83.37 | 0.000660 | 2.00 | 83.367 |

两个维度各自的贡献：

- **调度类**：78.270 → 29.471，**−48.799 µs（占旧 J 的 62.3%）**。
- **部署形态**（同一调度类内）：29.471 → 34.642，**混合反而更差 5.171 µs**。

## 5. 关键发现：模型与实测方向相反

STKP 用钳定成本（用户 5.0 / 内核 0.05 / ioctl 0.3 µs）评出
`STKP:L[sample]|L[pid]|L[sink] mixed Ĉ=31.05`，比全用户态融合 B（Ĉ=36.0）优 4.95 µs，
因此把它选为生成输入。实测结果是反的：

| 量 | 模型口径 | 实测 |
|---|---|---|
| 混合 vs 全用户态 | 混合优 4.95 µs | 混合**差** 5.17 µs |
| 边界单价 | 钳定 0.3 µs | 实测 2.0 µs（p50），p99 5~6 µs |
| 分析形状 A 的耗时 | Ĉ=78.0 µs | Q99 = 29.47 µs（FIFO）/ 78.27 µs（CFS） |

第三行是根因：`c=21 µs/组` 这个常数里不含调度等待，而实测 start_lat 在 CFS 下
是 62.9 µs、FIFO 下 11.9 µs。**同一份代码、同一个 binary，换一个调度类就差 51 µs**——
候选之间的差只有 5 µs。所以在 CFS 下按模型排出来的候选顺序本身不可信，
不是「模型参数要调准」的问题，是**少了一个维度**。

## 6. 敏感性（同一份画像，只改权重）

| 配置 | 入选 | J | 说明 |
|---|---|---|---|
| α=1 β=0 γ=0 | A@fifo99 | 29.471 | 只看 Q99 |
| α=1 β=1e5 γ=0（点估计） | A@fifo99 | 29.471 | 1% 超期折 1000 µs；CFS 被压到 149.367 |
| α=1 β=1e5（Wilson 上界） | A@fifo99 | 37.154 | FIFO 也要吃 7.683 µs 上界罚，仍赢 |
| α=1 β=1e5 γ=1 | A@fifo99 | 29.471 | 混合再加 2 µs，差到 7.17 µs |

四组配置入选不变，差值随权重单调变化——结论不是权重凑出来的。

## 7. 不可排名清单（fail-closed，不是漏掉）

| 候选 | 原因 |
|---|---|
| B（L[sample+pid+sink]，全融合，1 组） | 形状不匹配：实测是 3 组不融合，融合改变执行结构，Q99 不可借用 |
| L[sample+pid]\|L[sink]（2 组） | 同上，2 组 ≠ 3 组 |
| L[sample]\|L[pid+sink]（2 组） | 同上 |
| 任何 `linux_kernel` 候选 | PR-10E-A 基线网格未含内核自主部署；PR-10C2 是另一份构建/口径，按「同一二进制只改一个变量」不得混用 |

这不是保守过头：**要给这 4 类候选排名，必须先按各自形状重测 10 轮**，
否则就是把 A 的尾部借给一个执行结构不同的方案。

## 8. 未归因 / 必须一起读的保留意见

1. **33 == 33 是可疑巧合**。两个部署在 CFS 下总超期数完全相同（各 33/50000），
   但分布不同（user 7/10 轮有超期，mixed 10/10 轮）。总数相同很可能是同一批
   环境扰动所致，**不能据此说「内核化不改变超期率」**，只能说「本次测量分不出」。
   要分得出得换独立时段重复。
2. **换考核量结论会反过来**。按最差 resp max，user CFS 是 11.786 ms，mixed CFS
   只有 3.470 ms——混合明显更好。J 用 Q99 是评审给定口径，不是唯一口径。
   尾部四种量（p99 中位 / max 中位 / 最差 max / 超期）是四种不同风险，不可互换。
3. **Q99 看不见 11.8 ms**。p99 = 78 µs，11.8 ms 那一拍在 0.02% 之外；它只通过
   R_miss 现身。所以 α 单独用不足以表达「偶发大尖峰」的风险。
4. **谁抢了 CPU 仍未归因**。PR-10E-B 的 tracing 内核构建成功（5.15.86-trace，
   31 MB Image，95 ko，0 error）但 p1 只有 32 MB，装不下两个内核，
   sched_switch 归因仍缺。
5. **混合的跨界数按 1 计**。`handoff_channels=1`，但中段进内核两侧各有一次跨界；
   若按 2 计，混合再加 2 µs，入选不变。
6. **`--miss-bound upper` 对 FIFO 也罚 7.683 µs**。0 事件不等于 0 风险，
   Wilson 上界把它显式化了；这是特性不是 bug。

```bash
  --boundary kfusion/docs/pr10c_boundary/boundary.json \

  --profile ... --stkp ... --deadline 1000 -o .../decision_a1_b0_g0.json

# 自测（11 项，纯合成，不读仓库数据）
python3 kfusion/scripts/pr11_deploy_objective__部署目标.py selftest
```

产物：`sched_profile.json`、`decision_{cfs_only,a1_b0_g0,a1_b1e5_g0,a1_b1e5_upper,a1_b1e5_g1}.json`、
`candidates_pr10e_stkp.json`（Pi 上 gen_uku/stkp.json 原样取回，sha256 记在决策文件里）。

**跨平台复现**：同一命令在 Pi（Linux python3，`9c3507b`）上重跑，入选与 J 序列
`[29.471, 34.642, 78.270, 83.367]` 逐项一致；selftest 11 项同样全过。

## 10. 诚实边界

- 只证明「在这台 Pi4、这个 5.15.86 非 RT 内核、这批 10 轮测量下」的排序；
  换板、换内核、换负载都没测。
- Q99 是**典型一轮的 p99 取中位数**，不是 10 轮混池 p99（混池会掩盖单轮劣化）。
- 这不是可调度性判定。验证器仍只能叫「基于模型的可行性筛选器」；
  J 只在已通过 verify 的候选之间排序，不证明任何候选满足硬实时。
- 权重不具物理意义，不构成「最优部署」的证明——它证明的是
  **不把调度类放进决策空间会系统性选错**。
